Linux 环境下 Docker 的安装与使用

strr0 2024-11-24

1 概述

Docker Engine 是一种开源容器化技术，用于构建和容器化应用程序。它把应用与依赖打包成镜像，以进程隔离（namespace）+ 资源限制（cgroup）的方式跑在同一个内核上，因此启动是毫秒级、内存开销远小于虚拟机，但也意味着容器共享宿主内核，不能跨内核版本运行。

Linux 上安装 Docker 有三条路：

方式优点代价
包管理器（apt / yum）自动装 systemd unit、依赖、升级照管需要可用软件源，版本受源限制
二进制安装（本文）不依赖网络源，版本任意，离线环境可用systemd unit、自动启动、依赖检查都得自己搞
Docker in Docker适合 CI 跑器层级复杂，需特权模式

本仓库后续几篇中间件部署（Redis、Kafka、RabbitMQ、MongoDB、MinIO）都直接用了 docker run，所以本篇先把引擎本身装好。

2 环境要求

  • 64 位系统
  • 内核版本 3.10 及以上
  • iptables 版本 1.4 及以上
  • git 版本 1.7 及以上
  • ps 命令（procps 或其他包提供）
  • XZ Utils 版本 4.9 及以上
  • cgroupfs

这几项要求都能先查后装：

uname -r                                  # 内核版本
cat /proc/filesystems | grep overlay      # 必须有 overlay 才能用 overlay2 存储驱动
iptables --version; git --version; ps --version
cat /sys/fs/cgroup/unified/cgroup.controllers 2>/dev/null   # 有输出即 cgroup v2

内核 3.10 这个线是从 CentOS 7 来的（它本身基于 3.10，但 backport 了大量特性），其他发行版建议直接上 4.x 以上。另外现代发行版默认用 cgroup v2，而 cgroupfs 是为 cgroup v1 准备的：混合环境下更稳妥的做法是保留 systemd 默认驱动（"features": {"containerd-snapshotter": true} 或在 daemon.json 里设 "cgroup-parent"），而不是强制切换。

3 安装

3.1 获取二进制文件

wget https://download.docker.com/linux/static/stable/<architecture>/docker-<version>.tgz

3.2 安装二进制文件

解压

tar -xzvf docker-<version>.tgz

安装

sudo cp docker/* /usr/bin/

解压产物是一个 docker/ 目录，里面包含 dockerd、docker、docker-proxy、containerd、containerd-shim、runc、ctr 等全部组件，整目录拷进 /usr/bin/ 即可，不需要单独装 containerd 与 runc。

3.3 运行

sudo dockerd &

这种把 dockerd 直接挂在后台的启动方式只适合验证安装。生产环境要开机自启与异常重启，得为 dockerd 写 systemd unit（或直接用包管理器安装并交给 systemd 托管），否则机器重启后 Docker 就静消失了。

3.4 配置国内镜像源

修改 /etc/docker/daemon.json

{
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://docker.1panel.live"
  ]
}

重启 docker

PID=`ps -ef | grep dockerd | awk '{print $2}'`
if [ ! -z "$PID" ]
then
   sudo kill -9 $PID
fi
sudo dockerd &

两个问题需要注意：一是 ps -ef | grep dockerd 会把 grep 自己那一行也匹上（命令行里含 dockerd 字符串），拿到的 $2 可能是 grep 的 PID；用 pgrep -x dockerd 或把模式写成 grep [d]ockerd 可避开。二是 kill -9 会让正在跑的容器变孤儿子进程且可能残留网络与挂载点，能确定父 PID 时先试 kill -TERM，交给 systemd 托管时直接用 systemctl restart docker。

镜像源只对 docker.io 的镜像生效，且国内公共加速域名可用性变动很频繁，拉不下来时换一个即可。配置完可用 docker info | grep -A 5 Registry 确认已加载。

4 使用

4.1 基础操作

查看镜像列表

docker images

查看容器列表

docker ps -a

拉取镜像

docker pull <myimage>:<version>

删除镜像

docker rmi <myimage>

运行容器

docker run -dit \             # -d 后台运行 -i 交互形式 -t tty
    --name <mycontainer> \    # --name 容器名
    -p 8080:8080 \            # -p 端口映射
    <myimage>:<version>

修改容器默认命令

docker run -d \
    --name <mycontainer> \
    <myimage>:<version> <mycommand>

停止容器

docker stop <mycontainer>

删除容器

docker rm <mycontainer>

进入容器

docker exec -it <mycontainer> /bin/bash

查看日志

docker logs -f --tail 100 <mycontainer>

这一节里有一处容易照抄出错：「运行容器」示例把参数说明写在了行尾，而 \ 续行符后面必须紧跟换行，中间有空格或注释就会让命令解析错乱——注释只用于阅读，真跑时要么删掉要么写在独立行。另外 docker rm 不能删正在运行的容器，需要先 docker stop，或直接 docker rm -f。

几个高频补充：docker ps -a 加 -s 可看每个容器的退出码与最后命令；docker logs 只能看到容器写到 stdout/stderr 的内容，应用自己写的日志文件仍需 docker exec 进去看或 docker cp 拷出；docker inspect 能看到 IP、挂载、环境变量等全部元信息。

4.2 网络

4.2.1 操作

查看网络列表

docker network ls

创建网络

docker network create <mynetwork>

删除网络

docker network rm <mynetwork>

4.2.2 使用

运行容器指定连接网络

docker run -d \
    --name <mycontainer> \
    --net <mynetwork> \
    <myimage>:<version>

已有容器连接网络

docker network connect <mynetwork> <mycontainer>

连接至相同网络的容器可以通过 http://mycontainer:port 相互访问

Docker 有四种常见网络驱动：bridge（默认，单机）、host（直接用宿主网络栈，不再需要 -p，但端口冲突风险大）、none（只有 lo）、overlay（跨主机，配合 swarm）。

上面那句「同网络容器可用容器名互访」有个前提：必须是自建网络。默认的 bridge 网络只能用 IP 互访，只有 docker network create 出来的网络才内置 DNS，容器名与别名才能解析；--link 是老写法，新项目不要再用。

4.3 文件磁盘

复制容器文件

docker cp <mycontainer>:/path/in/container /path/on/host

磁盘空间查看

docker system df

磁盘空间清理

docker system prune -a

强制清理（需先停止 docker 服务）

rm -rf /var/lib/docker

docker system df 分四栏看：Images / Containers / Local Volumes / Build Cache，先看清哪一类占用大再决定清理力度。prune -a 会删除所有当前没有容器引用的镜像（包括你自己 build 出来还没起过服务的），执行前用 docker images 确认；数据卷不在默认清理范围内，要加 --volumes 才会删，而那一步不可逆。最后的 rm -rf /var/lib/docker 相当于恢复出厂：镜像、容器、卷、网络配置全部丢失，务必先停服务。

4.4 导入导出

导出镜像

docker save -o <myimage_version>.tar <myimage>:<version>

导入镜像

docker load -i <myimage_version>.tar

导出容器

docker export -o <mycontainer>.tar <mycontainer>

导入容器

docker import <mycontainer>.tar <myimage>:<version>

save/load 与 export/import 不是同一件事。save 导出的是镜像，保留分层结构与历史记录，可以一次带多个镜像和 tag，load 回去后仍是原来的镜像；export 导出的是容器的当前文件系统快照，分层被压平、ENV/CMD/VOLUME 等元数据全部丢失，所以 import 时必须自己指定默认启动命令（docker import file.tar repo:tag sh），否则起来的容器没有入口。离线交付一般走 save/load。

4.5 代理

使用 dockerd 命令

sudo dockerd --http-proxy=socks5://127.0.0.1:1080 --https-proxy=socks5://127.0.0.1:1080 &

使用 daemon.json 配置

{
  "proxies": {
    "http-proxy": "http://proxy.example.com:3128",
    "https-proxy": "https://proxy.example.com:3129",
    "no-proxy": "*.test.example.com,.example.org,127.0.0.0/8"
  }
}

两种代理的作用域不一样，很容易配错：dockerd 命令行参数与 daemon.json 里的 proxies 段影响的是容器内部的环境变量（daemon.json 的 proxies 需要 Docker 17.12+）；而守护进程自己拉镜像用的代理要配在 systemd 环境变量里——新建 /etc/systemd/system/docker.service.d/http-proxy.conf，写 [Service] 段与 Environment="HTTPS_PROXY=..."，然后 daemon-reload 加 restart。~/.docker/config.json 里的 proxies 则只影响当前用户的 docker 客户端。另外 SOCKS5 对镜像拉取不一定可靠，遇到失败就换 HTTP 代理。

4.6 其他操作

获取容器 command

docker inspect --format '{{.Config.Cmd}}' <mycontainer>

修改镜像名称和 tag

docker tag <oldname>:<oldtag> <newname>:<newtag>

判断容器是否存在

ID=`docker ps -aq -f name=^<mycontainer>$`
if [ ! -z "$ID" ]
then
  #...
fi

判断镜像是否存在

ID=`docker images -q <myimage>:<version>`
if [ ! -z "$ID" ]
then
  #...
fi

两段原来的写法有两个坑：一是 shell 的变量赋值 ID=... 等号两侧不能有空格，ID = 会被解析成「执行命令 ID、参数 = 和命令替换的结果」，直接报 command not found；二是 grep <mycontainer> 是子串匹配，判断 demo 是否存在时会把 demo-worker 一起匹上，而且 docker ps -a 默认还会输出表头。改用 -f name=^<mycontainer>$ 做精确过滤，或用 --format '{{.ID}}' 只要 ID，都更稳。

4.7 构建镜像

4.7.1 编写 Dockerfile

FROM openjdk:17-jdk-alpine3.14

RUN mkdir -p /app/lib \
    /app/config 

WORKDIR /app

ENV SERVER_PORT=9201 LANG=C.UTF-8 LC_ALL=C.UTF-8 JAVA_OPTS=""

EXPOSE ${SERVER_PORT}

ADD lib/* lib
ADD config/* config
ADD demo.jar app.jar

ENTRYPOINT java -Djava.security.egd=file:/dev/./urandom -Dserver.port=${SERVER_PORT} \
           -XX:+HeapDumpOnOutOfMemoryError -Xlog:gc*,:time,tags,level -XX:+UseZGC ${JAVA_OPTS} \
           -jar app.jar

三段说明，都是这段 Dockerfile 里真正会咬人的地方：

  1. JVM 参数必须排在 -jar 之前。原稿把 -XX:+HeapDumpOnOutOfMemoryError、-XX:+UseZGC 写在 -jar app.jar 后面，而 java 在遇到 -jar 之后就把剩余全部参数当作程序参数传给 main(String[])，于是堆转储、ZGC、GC 日志全部静默失效，JAVA_OPTS 同理。这里只调整了顺序，没有改动任何参数本身。
  2. shell 形式的 ENTRYPOINT 会走 /bin/sh -c。好处是 ${SERVER_PORT}、${JAVA_OPTS} 能展开（exec 形式 ENTRYPOINT ["java", "-jar", ...] 不会展开变量）；代价是 -Xlog:gc* 里的 * 有被 shell glob 展开的风险，且容器里 PID 1 是 shell，docker stop 的 SIGTERM 不会传到 JVM（表现为等满 10 秒后被强杀）。生产更推荐把命令行收进一个 entrypoint.sh，或用 exec 形式 + JAVA_TOOL_OPTIONS 环境变量。
  3. 基础镜像与 GC 选择。openjdk:*-alpine 系列已停止维护，官方建议换成 eclipse-temurin:17-jre-alpine（只需 JRE 时体积能小不少）；ZGC 在 musl（Alpine）上的稳定性历史上不如 glibc，若确实要用 ZGC，可选 Debian 系基础镜像验证。

另外两处构建层面的建议：ADD 除了下载 URL 和解压 tar 之外没有比 COPY 多出的能力，纯拷贝场景统一用 COPY 更不容易被误用；ADD lib/* lib 这种通配写法在 lib 下只有单个文件时的目标语义容易和预期不符，不如 COPY lib/ lib/。同时应该在构建上下文里放一个 .dockerignore 把 target/、.git/、日志目录排除掉，否则每次改一行代码都可能因为上下文过大而让 build 变慢。层缓存的顺序也值得调整：先 COPY 变化频率低的依赖（lib/、config/），最后再 COPY demo.jar，这样改代码时前面几层还能命中缓存。

4.7.2 构建

docker build -t <myimage>:<version> <dockerfilepath>

4.7.3 运行与停止

运行

img="demo"

version=$(date "+%Y-%m-%d")

imgId=`docker images -q $img:$version`
if [ ! -z "$imgId" ]
then
  docker rmi $imgId
fi

docker build -t $img:$version .

docker run --name $img \
    -p 8080:8080 \
    -d $img:$version

停止

app="demo"

appId=`docker ps -aq -f name=^$app$`
if [ ! -z "$appId" ]
then
  docker stop $appId
  docker rm $appId
fi

这两个脚本作为手工快捷脚本够用，但有几个实际会碰到的边界：docker rmi 删镜像时如果已有容器在用它（即使是已停止的容器）会直接报错，得先 docker rm 掉引用它的容器；docker images -q name:tag 只在 tag 完全匹配时返回 ID，如果只想按镜像名列出全部版本，还是得回到 docker images -q $img；而固定 --name $img 意味着同名容器必须先清掉才能 docker run，否则报 name conflict。真要用于 CI，建议把“停旧容器 → 删旧容器 → 起新容器”写成幂等步骤，或直接交给 Docker Compose / 部署流水线（参考 GitLab CI/CD 自动化部署 与 Jenkins 自动化部署）。

4.8 Docker Compose

4.8.1 安装

下载及安装

curl -SL https://github.com/docker/compose/releases/download/<version>/docker-compose-linux-<architecture> -o /usr/local/bin/docker-compose

赋予权限

chmod +x /usr/local/bin/docker-compose

验证安装

docker-compose --version

4.8.2 使用

基本配置

# docker-compose.yml

version: '3'

services:
  mysql:
    image: mysql:8.0.33
    container_name: mysql
    environment:
      # 时区上海
      TZ: Asia/Shanghai
      # root 密码
      MYSQL_ROOT_PASSWORD: root
      # 初始化数据库(后续的初始化sql会在这个库执行)
      MYSQL_DATABASE: sampledb
    ports:
      - "3306:3306"
    volumes:
      # 数据挂载
      - /docker/mysql/data/:/var/lib/mysql/
      # 配置挂载
      - /docker/mysql/conf/:/etc/mysql/conf.d/
    command:
      # 将mysql8.0默认密码策略 修改为 原先 策略 (mysql8.0对其默认策略做了更改 会导致密码无法匹配)
      --default-authentication-plugin=mysql_native_password
      --character-set-server=utf8mb4
      --collation-server=utf8mb4_general_ci
      --explicit_defaults_for_timestamp=true
      --lower_case_table_names=1
    privileged: true
    network_mode: "host"

运行指定配置

docker-compose -f docker-compose.yml up -d

四个使用层面的提醒：

  • docker-compose（v1）已停止维护。它是 Python 写的独立二进制，官方已在 2023 年结束支持；现在推荐的是插件形式的 docker compose（v2，Go 重写），包管理器安装名为 docker-compose-plugin，或直接把 v2 二进制下载成 ~/.docker/cli-plugins/docker-compose。两者命令差异就在中间那个空格，本文仍沿用了 v1 写法。
  • version: '3' 已废弃。Compose Spec 合并后 v2 会忽略这个字段并给出告警，新写文件可以直接删掉。
  • ports 与 network_mode: "host" 矛盾。一旦使用 host 网络，容器直接复用宿主网络栈，-p 3306:3306 完全不生效（v2 会直接报 ports 与 network_mode: host 不可共存类错误）。常见做法是二选一：要么去掉 network_mode 靠端口映射，要么保留 host 而删掉 ports（此时 MySQL 直接监听宿主 3306，也就没了映射带来的 NAT 开销）。
  • privileged: true 在这里并不需要。它把宿主全部设备交给容器，属于不必要的风险面；MySQL 容器普通权限就能跑，确实需要额外能力时再按项给（如 cap_add）。另外 /docker/mysql/... 这类目录需要先建好并给对宿主侧权限（MySQL 镜像内进程以 uid 999 运行），否则容器会卡在 Can't create/write to file；挂载配置目录时也要注意镜像自带的 /etc/mysql/my.cnf 仍会 include conf.d，放进去的 .cnf 文件名排序会影响最终配置。

5 常见问题

5.1 普通用户 permission denied 问题

创建 docker 组（若不存在）

sudo groupadd docker

将当前用户添加到 docker 组

sudo usermod -aG docker $USER

更新用户组

newgrp docker

背后的原理是：docker 命令访问的是 /var/run/docker.sock 这个 Unix socket，而它的属组是 docker，普通用户默认不在该组里，所以报 permission denied while trying to connect to the Docker daemon socket。两个细节：usermod -aG 只改了 /etc/group，已有登录会话的组凭证不会自动生效，要么重新登录，要么用 newgrp docker 开一个新 shell；而 aG 的 a 不能漏（写成 G docker 会把用户从其他组里移除）。

安全上需要明白：能使用 docker 就等价于能拿 root。同一个组里的用户可以用 -v /:/host 挂载宿主根目录、或以 --privileged 起容器后 chroot 到宿主改 /etc/shadow，这层隔离在权限模型上就是破的。对权限敏感的环境可以考虑 rootless 模式（dockerd-rootless-setuptool.sh install，容器与守护进程都跑在普通用户 namespace 下），代价是不能直接用 1024 以下端口与部分网络特性。

如果问题仍然存在，尝试重启 docker 服务

5.2 开启远程访问

修改 docker.service

# /lib/systemd/system/docker.service

# 注释如下
# ExecStart=/usr/bin/dockerd -H fd:// --containerd=/run/containerd/containerd.sock
# 修改为
ExecStart=/usr/bin/dockerd -H tcp://0.0.0.0:2375 -H unix:///var/run/docker.sock

重启 docker

systemctl daemon-reload && systemctl restart docker

原稿这里的 & 是后台执行而非“上一条成功后再执行”，daemon-reload 会被丢到后台且不保证与 restart 的顺序，应为 &&。改完后监听面多了一个 tcp://0.0.0.0:2375，而 2375 是明文且无任何认证的 API：任何能连上这个端口的人都可以调用 POST /containers/create 起一个特权容器挂载宿主根目录，相当于把整台机器的 root 交出去，历史上大量云主机入侵就是从暴露的 2375 开始的。确实需要远程管理时，至少做一件事：用 TLS（-H tcp://0.0.0.0:2376 --tlsverify --tlscacert/--tlscert/--tlskey）并校验客户端证书；只在 CI 里临时用的话，用 SSH 隧道（ssh -N -L 2375:/var/run/docker.sock user@host）或 socat 加本地过滤更合适；实在要直接开放，也得用安全组/防火墙把来源锁到固定 IP。

6 小结

  • 二进制安装拿到的是一整个组件集（dockerd / containerd / runc / docker-proxy），装完能快速跑起来，但 systemd 托管、开机自启、依赖检查都得自己补齐，生产环境还是交给包管理器或官方脚本。
  • 代理与镜像源最容易配错的是作用域：daemon.json 的 registry-mirrors 与 systemd 的 Environment 影响守护进程拉镜像，daemon.json 的 proxies 只影响容器内部环境变量，~/.docker/config.json 只影响当前用户的客户端。
  • 网络部分记住两条：只有自建网络才内置 DNS（容器名才能互访），host 模式与 ports 映射不可共存。
  • 清理类命令里 system prune -a、--volumes、rm -rf /var/lib/docker 都是不可逆的，执行前先用 docker system df 看清楚删的是什么。
  • 安全上把三件事当默认预期：docker 组等价 root、2375 明文 API 等价 root、--privileged 能穿透隔离。
