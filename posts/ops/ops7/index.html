Linux 环境下 ByConity 的安装与使用

strr0 2023-10-11

1 概述

ByConity 是面向现代数据仓库架构设计的云原生数仓：存算分离，计算层按读/写 worker 拆分并支持弹性扩缩容、资源隔离与多仓库（warehouse）隔离，元数据层提供强一致的事务与 Schema 变更。它是从 ClickHouse 分叉出来的，兼容 ClickHouse 的协议与工具（clickhouse-client、HTTP 8123、JDBC），同时支持标准 SQL（ANSI 方言）。

本文用到的组件分工如下，后面排查问题全靠这张表：

组件容器/角色作用端口
Serverserver-0SQL 解析与规划、对外入口（兼容 ClickHouse）HTTP 8123、TCP 52145
Daemon Managerdaemon-manager-0worker 管理与调度、事务协调—
TSOtso-0全局时间戳（强一致快照读的基础）—
Workerworker-default-0 / worker-write-0真正执行查询与写入的计算节点，可按 warehouse 分组—
元数据fdb-0（FoundationDB）表/分区/事务元数据，强一致 KV单节点演示用 7.1.24
数据hdfs-namenode / hdfs-datanode对象存储的本地替代（也可用 S3）9870/8020

选型前要知道两件事。第一，byconity/byconity:0.1.0-GA 是 2023 年的首个正式版本，项目后续的发布与响应节奏明显放缓，把它引入生产前请先评估上游维护风险（同类需求也可以直接看 ClickHouse + 存算分离方案或 StarRocks/Doris）。第二，本文的 Docker Compose 部署是单机演示拓扑：HDFS、FoundationDB 都只起了一个节点，没有任何冗余，不适合直接拿去当生产集群用。

2 在 Docker 中部署

2.1 环境要求

  • Docker
  • Docker Compose

宿主机侧具体安装参考 Linux 环境下 Docker 的安装与使用；这套拓扑至少需要 8G 以上内存与较大的磁盘（HDFS 数据与镜像本身都要占空间），先 docker system df 看一下余量。

2.2 docker 镜像（可提前拉取镜像）

docker pull gchq/hdfs:3.3
docker pull foundationdb/foundationdb:7.1.24
docker pull byconity/byconity:0.1.0-GA

三个镜像分别对应元数据（FoundationDB）、数据层（HDFS）与计算层（ByConity），提前拉取是因为 docker-compose up 默认会等全部镜像就绪才起容器，国内环境拉 Docker Hub 经常直接超时（镜像源配置见 Docker 安装 的 3.4）。

2.3 运行 ByConity

从 github 获取源代码

git clone https://github.com/ByConity/byconity-docker.git

使用 docker-compose 运行 ByConity

cd byconity-docker
docker-compose up -d

cd 后面那句注释应该写在正文里而不是命令里（原稿括号内的中文会让整行命令直接执行失败）。仓库名是 byconity-docker，先 ls 确认解压/克隆出来的目录名。起来后先 docker-compose ps 确认容器都是 Up，再看日志 docker-compose logs -f server（server 会等 HDFS 与 FoundationDB 就绪才启动，前期看到 retry 日志属正常）。另外 docker-compose 是已停维护的 v1，新版写成 docker compose，两种写法在这个例子里等价（区别见 Docker 安装 的 4.8）。

测试 server 是否正常工作（返回 1）

curl '127.0.0.1:8123/?query=select%20count()%20from%20system.one'

测试 read worker 是否正常工作（返回 1）

curl '127.0.0.1:8123/?query=select%20count()%20from%20cnch(`vw_default`,system,one)'

测试 write worker 是否正常工作（返回 1）

curl '127.0.0.1:8123/?query=select%20count()%20from%20cnch(`vw_write`,system,one)'

三个测试递进的关系值得说清：第一个只验证 server 本身能解析并回答（system.one 在 server 本地就能返）；后两个用 cnch() 表函数把查询强制下发到指定 warehouse 的 worker（vw_default 读、vw_write 写），返回 1 才能证明“worker 已注册到 Daemon Manager 且能访问存储与元数据”。如果第一个返 1、后两个报错，问题就在 worker 侧（启动失败、连不上 HDFS/FDB）而不是网络。命令里的 %20 是空格的 URL 编码，写反引号的库名在双引号包裹的 URL 里会被 shell 当命令替换，这里用的是单引号所以安全。

2.4 使用 ByConity 客户端

在 hdfs 创建 clickhouse 用户

./hdfs/create_users.sh

进入 docker 容器的 clickhouse

docker exec -it server-0 clickhouse-client --port 52145

执行语句测试

SHOW DATABASES;

复制 docker 客户端至容器外部

mkdir bin
docker cp server-0:/opt/byconity/bin/clickhouse bin

create_users.sh 干的事是在 HDFS 上建 clickhouse 用户目录（对应 2.8.4 那个报错），必须先跑它再建库建表，否则写入时会卡在 HDFS 权限。--port 52145 是 server 的 TCP 端口（不是 HTTP 的 8123），容器内直接用默认 host 就行。把二进制 docker cp 到宿主机的 bin/ 是为了后续不依赖容器也能连（一个 clickhouse 文件就包含 client/server 多个子命令）；拷出来后记得 chmod +x bin/clickhouse。

2.5 验证部署

连接到 ByConity server

bin/clickhouse client --host=<your_server_host> --port=<your_server_tcp_port>  --enable_optimizer=1 --dialect_type='ANSI'

两个客户端参数决定了你能写哪种 SQL：--dialect_type='ANSI' 打开标准 SQL 方言（GROUP BY/ORDER BY 语义、标识符引号规则跟 ANSI 而非 ClickHouse），--enable_optimizer=1 启用新的分析优化器；不带这两个参数时默认行为跟 ClickHouse 一致，同一句 SQL 的结果列名与排序行为会有细微差异。从宿主外访问时 host/port 要填真实映射值（docker-compose port server-0 8123 可查）。

确保所有 worker 正常启动并且被识别

select * from system.workers

这张表是排查“查询为什么没下发到 worker”的第一入口：关注 state（正常应为 ACTIVE/ONLINE）与 warehouse 列是否与预期的 vw_default/vw_write 对应，worker 没注册时它会是 INACTIVE 或干脆没行。下面这段 SQL 里 CnchMergeTree 是 ByConity 对应的存储引擎（数据在 HDFS/S3，本地只是缓存），ORDER BY id 在 ClickHouse 系引擎里是必选的（它定义主键与排序键，不是查询排序）。

运行一些基本的 SQL

CREATE DATABASE test;
USE test;
CREATE TABLE events (`id` UInt64, `s` String) ENGINE = CnchMergeTree ORDER BY id;
INSERT INTO events SELECT number, toString(number) FROM numbers(10);
SELECT * FROM events ORDER BY id;

确保以上运行结果是正常的

2.6 数据导入

导入数据到指定表

bin/clickhouse client --query "INSERT INTO example FORMAT CSV" < example.dat --format_csv_delimiter "|"

原稿这条命令少了连接参数，实际跟 2.5 一样要带上 --host/--port（必要时 --password），否则它会试着连本地默认地址。几个细节：< example.dat 是宿主机侧的重定向，客户端把它当 stdin 流式上传，因此大文件不会先全部读进内存；FORMAT CSV 与 --format_csv_delimiter 必须跟文件实际分隔符一致（默认是逗号），跳表头用 --format_csv_allow_single_quote=1、--input_format_skip_unknown_fields=1；目标表不存在或列数不匹配会直接失败，先 INSERT INTO example SELECT ... LIMIT 1 验证通路。批量导入建表时记得给 example 表先建好（CREATE TABLE example (...) ENGINE = CnchMergeTree ORDER BY ...）。

2.7 停止 ByConity

停止 ByConity 容器

docker stop daemon-manager-0 server-0 tso-0 worker-default-0 worker-write-0 fdb-0 hdfs-datanode hdfs-namenode

或停止所有容器

docker stop $(docker ps -aq)

第二条命令在任何机器上都是危险操作：它会停掉这台宿主机上正在跑的全部容器，包括与 ByConity 无关的业务服务。这台机器只跑 ByConity 时可以用，否则请换成作用域明确的写法：在仓库目录里 docker compose stop（只停本项目）、docker compose down（额外删容器与网络），或 docker stop $(docker ps -q --filter "name=byconity")。要重新启动时用 docker compose up -d 而不是 docker start，因为部分服务需要完整的启动顺序；想连数据一起清掉只有 docker compose down -v，它会删除命名卷（HDFS 上的表数据就存在这里），执行前确认已备份。

2.8 配置修改及问题修复

2.8.1 配置修改

容器内部的配置文件已经挂载到物理机上，修改配置在物理机上操作即可，如设置用户密码

# /<your_directory>/byconity-simple-cluster/users.yml

users:
  default:
    networks:
      ip: ::/0
    password: "new_password"  # 修改密码为new_password
    profile: default
    quota: default

说明两件事。第一，改完配置需要让 server 重新加载：clickhouse-client --port 52145 -q "SYSTEM RELOAD CONFIG"，重启容器同样可以；只改文件不 reload 时会看到“密码改了但旧密码还能登”。第二，ip: ::/0 表示允许任意来源连接 default 用户，而 password 在文件里是明文；这套配置能直接跑是因为端口没往公网暴，真要用请改掉默认口令并按来源收窄（::/0 是 IPv6 写法，IPv4 需同时允许 0.0.0.0/0 才能从 v4 连入），并把 users.yml 纳入配置管理而不是只存在本地。

2.8.2 DB::NetException: Connection refused 问题

在 CentOS 7 上可能会遇到 clickhouse-client 连接拒绝，可尝试如下命令登录

# 进入容器内部
docker exec -it server-0 /bin/bash

# 登录 ClickHouse 客户端
clickhouse-client -m -h 127.0.0.1 --port 52145 --password

这不是 ByConity 的问题而是客户端解析地址的问题：宿主机上的 clickhouse-client 默认往 localhost 连，而 CentOS 7 的 glibc/hosts 配置下 localhost 会先解成 IPv6 的 ::1，容器里并没有监听 v6，于是 Connection refused。显式写 -h 127.0.0.1 就绕过了。-m（--multiline）只是让多行 SQL 可编辑，--password 不带值时交互式提示输入，比把密码写在命令里安全（shell 历史与 ps 都能看到）。

2.8.3 Too many open files 问题

遇到 random_device failed to open /dev/urandom: Too many open files 问题，可通过如下命令修改最大允许打开文件数量

ulimit -n 2048

注意这个值只对当前 shell 及其后续启动的进程生效，已经跑着的容器不会跟着变；而且容器内的限制由 Docker 默认 nofile 决定（2048 硬上限），改宿主 ulimit 对容器无用。正确的做法是在 docker-compose.yml 里给服务加 ulimits: { nofile: { soft: 65536, hard: 65536 } }，或在全局配 dockerd --default-ulimit nofile=65536:65536；systemd 托管的写 LimitNOFILE。2048 对一个会频繁打开 HDFS 文件句柄的数仓来说偏小，建议直接上 65536。

2.8.4 Access to file denied 问题

遇到 DB::Exception: Access to file denied: Permission denied 问题，可能是由于 hdfs 未创建 clickhouse 用户导致，尝试如下命令创建

docker exec hdfs-namenode hdfs dfs -mkdir /user
docker exec hdfs-namenode hdfs dfs -mkdir /user/clickhouse
docker exec hdfs-namenode hdfs dfs -chown clickhouse /user/clickhouse
docker exec hdfs-namenode hdfs dfs -chmod -R 775 /user/clickhouse

这四条就是 ./hdfs/create_users.sh 里的内容，手动执行适用于脚本跑失败的情况。两个补充：-chown clickhouse 只改属主不改属组，如果 namenode 开了 POSIX 权限检查（dfs.permissions.enabled=true，默认就是 true），还需要进程使用同一用户或把目录权限放到能写；排查时先 docker exec hdfs-namenode hdfs dfs -ls -R /user 看属主，再 docker compose logs worker-default-0 | grep -i hdfs 看具体路径。数据层报错时记得区分“HDFS 权限不够”与“目录不存在”（后者多因 NameNode 格式化后丢过数据）。

3 在 K8S 中部署

3.1 环境要求

3.1.1 K8S 环境

更新必要包

sudo apt-get update
sudo apt-get install -y apt-transport-https ca-certificates curl

添加 k8s signing key

curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.28/deb/Release.key | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg

添加 k8s 源

echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.28/deb/ /' | sudo tee /etc/apt/sources.list.d/kubernetes.list

安装 k8s

sudo apt-get update
sudo apt-get install -y kubectl

上面三步是 Kubernetes 官方从 v1.24 起的新仓库方案（pkgs.k8s.io），旧的 apt.kubernetes.io 已停用；URL 里的 v1.28 要与你打算装的集群版本一致，否则 kubectl 与 API server 版本差太远会报错。本小节只是“能操作集群”的准备：如果已经有现成的 K8S（公司集群、minikube、云厂商托管集群），完全不需要自己装 kubectl 以外的东西，直接从 3.2 开始。

3.1.2 Helm 环境

添加 gpg

curl https://baltocdn.com/helm/signing.asc | gpg --dearmor | sudo tee /usr/share/keyrings/helm.gpg > /dev/null

安装 apt-transport-https

sudo apt-get install apt-transport-https --yes

添加源

echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/helm.gpg] https://baltocdn.com/helm/stable/debian/ all main" | sudo tee /etc/apt/sources.list.d/helm-stable-debian.list

安装 helm

sudo apt-get update
sudo apt-get install helm

添加 helm 国内源

helm repo add stable https://kubernetes.oss-cn-hangzhou.aliyuncs.com/charts
helm repo add azure https://mirror.azure.cn/kubernetes/charts

这两个镜像源反映的是历史上的 Helm App Repository（charts 仓库）体系，而 Helm 3 已废弃 repository 里的 chart 仓库格式，主流做法是直接拉 OCI 制品或本地目录——本例的 ./chart/byconity 就是本地 chart，根本不需要 helm repo add。所以这两行在新环境里可以整段跳过；gpg --dearmor 那行也需要 sudo（写 /usr/share/keyrings），否则普通用户下会报权限错误。

3.1.3 Kind 环境

[ $(uname -m) = x86_64 ] && curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.20.0/kind-linux-amd64
chmod +x ./kind
sudo mv ./kind /usr/local/bin/kind

Kind 是“用 Docker 容器当节点”的本地 K8S 工具，只适合开发与验证：节点是容器、默认不配持久化存储类，重启机器就没了。第一行的 [ $(uname -m) = x86_64 ] && 是个条件，非 x86_64（如 ARM）机器上执行它会静默什么都不做，后面 chmod +x ./kind 就报文件不存在；ARM 下把下载地址换成 kind-linux-arm64。另外 Kind 版本与 kindest/node 镜像版本必须配套（本文的 v0.20.0 对应 v1.27.x），不配套时 kind create cluster 会在等控制平面就绪时超时。

3.1.4 Docker 环境

参考 Linux 环境下 Docker 的安装与使用（Kind 的节点就是 Docker 容器，所以这一步在 Kind 路径下是前置条件）。

3.1.5 获取 byconity-deploy 源码

git clone git@github.com:ByConity/byconity-deploy.git
cd byconity-deploy

这里用的是 SSH 地址（git@github.com:），没配 GitHub deploy key 时会报 Permission denied (publickey)；改成 HTTPS 地址 git clone https://github.com/ByConity/byconity-deploy.git 对公开仓库完全等价。后面 helm ... ./chart/byconity 用的都是这个目录里的相对路径，所有 helm 命令必须在仓库根目录执行。

3.2 Kind 配置 K8S 集群

docker 拉取 node 镜像

docker pull kindest/node:v1.27.3

创建 1 个 control-plane 和 3 个 worker 的集群

kind create cluster --config examples/kind/kind-byconity.yaml

验证

kubectl cluster-info

kind create cluster 之前先用 kind get clusters 确认没有同名集群（默认集群名 kind，而 3.4 里 docker stop byconity-cluster-* 用的节点名前缀是 byconity-cluster，说明自定义 config 里把 name 改成了它）。examples/kind/kind-byconity.yaml 里已经配了节点数、端口映射与 storage 相关设置，想改副本数或内存限制就从这个文件入手（资源不够时 Kind 节点会先把宿主 Docker 的内存吃满）。cluster-info 只能证明 API server 活着，真正该跑的是 kubectl get nodes -o wide（三个 worker 都是 Ready）与 kubectl get po -A -n kube-system（CNI 就绪后 CoreDNS 才会 Running）。

3.3 初始化 Demo

# Install with fdb CRD first
helm upgrade --install --create-namespace --namespace byconity -f ./examples/kind/values-kind.yaml byconity ./chart/byconity --set fdb.enabled=false

# Install with fdb cluster
helm upgrade --install --create-namespace --namespace byconity -f ./examples/kind/values-kind.yaml byconity ./chart/byconity

这里连跑两次 helm 是故意设计的，不是重试：FoundationDB 的 operator 与它的 CRD（foundationdbfoundationdb）必须在同一次 reconcile 里存在，而 Helm 安装 CRD 后当前 release 看不到新建的 CRD，所以先 --set fdb.enabled=false 把 operator/CRD 装下去，第二次不带这个参数时才能真正创建 FDB 集群。看到第一个命令报 kind could not be found 类错误（CRD 未生效）时，多等十几秒重试第二条即可。

等待所有 pods 准备完毕（使用如下命令查看状态）

kubectl -n byconity get po

长时间卡在 Pending/ContainerCreating 时用 kubectl -n byconity describe po <pod> 看事件（Kind 下常见的两个原因：没拉到镜像，或 PVC 没有可用存储类）；日志用 kubectl -n byconity logs -f <pod>，ByConity 侧的 byconity-server、byconity-daemon-manager、byconity-tso 与 worker 要分开看。进入客户端前确认 server 的 readiness：kubectl -n byconity get svc。

进入容器

kubectl -n byconity exec -it sts/byconity-server -- bash

进入 clickhouse 客户端

clickhouse client

sts/byconity-server 是 StatefulSet 的写法（自动选中它的 0 号副本），和直接写 pod 名相比不依赖具体副本序号。容器里 clickhouse client 连的是本容器，没开认证时能直接进；带密码时补 -p。从集群外访问需要先把端口接出来：

kubectl -n byconity port-forward svc/byconity-server 8123:8123 52145:52145
bin/clickhouse client --host 127.0.0.1 --port 52145 --dialect_type='ANSI' --enable_optimizer=1

port-forward 只适合本地调试（单连接、不能长时保活），正式对外还是用 Ingress/LB（Nginx 侧的配置参考 Linux 环境下 Nginx 的安装与使用）。

3.4 从 Kubernetes 集群中删除或停止 ByConity

删除集群

helm uninstall --namespace byconity byconity

停止 ByConity

docker stop byconity-cluster-control-plane byconity-cluster-worker byconity-cluster-worker2 byconity-cluster-worker3

两条命令的作用域完全不同，很容易误删：helm uninstall 只删 ByConity 的 K8S 资源，PersistentVolume 里的数据根据 StorageClass 的 reclaim policy 决定去留（Kind 默认用 host-path，删 release 不会清数据，下次装回来还能看到之前的表）；而 docker stop 停的是整个 Kind 集群本身（四个节点容器），K8S 层面的其他应用也一起没了。想彻底清掉就按顺序：helm uninstall → kind delete cluster --name byconity-cluster（这个命令会同时删节点容器与其中的数据）。

4 运维要点

事项做法
看健康Docker：docker compose ps + docker compose logs --tail 100 <svc>；K8S：kubectl -n byconity get po -o wide
看 workerselect * from system.workers；worker 不 ACTIVE 时先查它与 Daemon Manager、HDFS、FDB 的连通性
看存储docker exec hdfs-namenode hdfs dfs -du -h /user/clickhouse；HDFS 容器磁盘满会直接导致写入失败
看元数据FoundationDB 状态：docker exec fdb-0 fdbcli --exec status（healthy 为 true）；FDB 不可用时整个集群的写入与 DDL 都会卡住
备份数据在 HDFS/S3，元数据在 FDB：两者必须同时备份才能恢复到一致状态，只备份 HDFS 恢复不了表结构
扩容worker 本质上是无状态计算节点，Docker 拓扑下需改 compose 副本数，K8S 下 kubectl -n byconity scale sts/byconity-worker --replicas=N（按 warehouse 分组扩容，读写资源互不影响）
升级镜像 tag 与 chart 版本要同时改；本文的 0.1.0-GA 与新版本间可能存在元数据不兼容，升级前先做全量备份并在测试环境验证

5 小结

  • ByConity 把存算拆开：Server 管 SQL 与入口，Worker 管计算（按 warehouse 隔离），元数据在 FoundationDB，数据在 HDFS/S3，TSO 提供全局时间戳——排障时就按这条链路拆。
  • 三个 curl 测试是递进关系：先验 server，再用 cnch() 分别验读/写 worker；只有 system.one 返 1 不代表集群可用。
  • create_users.sh（建 HDFS 用户目录）必须在建库建表前执行，对应后面的 Access to file denied；ulimit -n 在容器里得改 compose 的 ulimits，不是改宿主 shell。
  • docker stop $(docker ps -aq) 会停掉整台机器的容器，一律换成 docker compose stop/down；down -v 与 kind delete cluster 会真删数据。
  • K8S 路径里两次 helm upgrade --install 是为了解 CRD 与 FDB 集群的创建顺序，不是重复执行；Kind 只适合本地验证，不适合当生产集群。
  • 选型提醒：本文镜像停在 0.1.0-GA，上游发布节奏已经放缓，生产使用要先确认维护风险。
