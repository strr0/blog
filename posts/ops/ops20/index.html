Linux 环境下 Canal 的安装与使用

strr0 2025-05-27

1 概述

Canal 是阿里巴巴开源的 MySQL binlog 增量订阅 & 消费组件。它的原理是伪装成 MySQL 的 slave：向 master 发送 dump 请求，接收 binlog 后解析成行级变更数据（库、表、操作类型、变更前列/变更后列），再通过 TCP（默认 11111 端口）投递给消费端。因此 MySQL 侧只需要开 binlog 并给一个 REPLICATION 权限账号，业务代码零侵入、不轮询、不丢变更细节。

常见用途：更新/失效缓存、同步 Elasticsearch、数据库备份与异地从库、实时数仓 ODS 层接入。几个角色一次对齐：

角色是什么端口
canal-server内核进程，连 MySQL 拉 binlog 并解析，按 instance（如 example）管理订阅11111
canal.clientJava SDK，自己写消费逻辑（拉取 + ack），见第 3 节—
canal.adapter把变更自动投递到 MQ（Kafka/RabbitMQ）或直接写目标库/ES，免写消费代码—
canal-adminWeb 管理端，在线管理 cluster/instance 配置8089

MySQL 端的 binlog 参数与账号权限怎么准备，见 Linux 环境下 MySQL 的安装与使用 的 3.4；本文假设库已就绪。

2 安装

2.1 准备 MySQL

  1. 对于自建 MySQL , 需要先开启 Binlog 写入功能，配置 binlog-format 为 ROW 模式，my.cnf 中配置如下
[mysqld]
log-bin=mysql-bin # 开启 binlog
binlog-format=ROW # 选择 ROW 模式
server_id=1       # 配置 MySQL replication 需要定义，不要和 canal 的 slaveId 重复

三种格式里只有 ROW 会记录每行变更前后的完整值，STATEMENT/MIXED 只记 SQL 语句，Canal 拿不到行数据，所以 ROW 是硬要求。改完 my.cnf 需重启 mysqld，用 SHOW VARIABLES LIKE 'binlog_format'; 和 SHOW MASTER STATUS; 确认生效。

注意：针对阿里云 RDS for MySQL , 默认打开了 binlog , 并且账号默认具有 binlog dump 权限 , 不需要任何权限或者 binlog 设置,可以直接跳过这一步

  1. 授权 canal 链接 MySQL 账号具有作为 MySQL slave 的权限, 如果已有账户可直接 grant
CREATE USER canal IDENTIFIED BY 'canal';  
GRANT SELECT, REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'canal'@'%';
-- GRANT ALL PRIVILEGES ON *.* TO 'canal'@'%';
FLUSH PRIVILEGES;

三条权限各管一事：REPLICATION SLAVE 是 dump binlog 的核心权限，REPLICATION CLIENT 允许执行 SHOW MASTER STATUS（定位起始位点用），SELECT 供 canal 查表结构（初始化 tsdb）。只想开放部分库时把 *.* 换成对应库名即可。建完用 canal 账号登一次验证；MySQL 8 默认 caching_sha2_password 认证可能与 Canal 内置老驱动不兼容（报 caching_sha2_password 相关错误），解决方式见第 5 节。

2.2 canal-server

2.2.1 通过二进制文件安装

  1. 下载 canal, 访问 release 页面, 选择需要的包下载, 如以 1.0.17 版本为例
wget https://github.com/alibaba/canal/releases/download/canal-1.0.17/canal.deployer-1.0.17.tar.gz

release 页同时有 canal.deployer（服务端）和 canal.adapter、client 包，订阅消费只需要 deployer。1.0.17 是老版本存档，新部署建议用 1.1.x（和下面 Docker 镜像的 v1.1.8 对齐）。

  1. 解压
mkdir /tmp/canal
tar zxvf canal.deployer-1.0.17.tar.gz  -C /tmp/canal

解压后就是 bin/conf/lib 标准布局：conf/canal.properties 是 server 级配置（端口、instance 列表），conf/example/instance.properties 是每个订阅实例的配置（连哪个库、订阅哪些表）。

  1. 配置修改

conf/example/instance.properties

## mysql serverId
canal.instance.mysql.slaveId = 1234
#position info，需要改成自己的数据库信息
canal.instance.master.address = 127.0.0.1:3306 
canal.instance.master.journal.name = 
canal.instance.master.position = 
canal.instance.master.timestamp = 
#canal.instance.standby.address = 
#canal.instance.standby.journal.name =
#canal.instance.standby.position = 
#canal.instance.standby.timestamp = 
#username/password，需要改成自己的数据库信息
canal.instance.dbUsername = canal  
canal.instance.dbPassword = canal
canal.instance.defaultDatabaseName =
canal.instance.connectionCharset = UTF-8
#table regex
canal.instance.filter.regex = .\*\\\\..\*

canal.instance.connectionCharset 代表数据库的编码方式对应到 java 中的编码类型，比如 UTF-8，GBK , ISO-8859-1

如果系统是 1 个 cpu，需要将 canal.instance.parser.parallel 设置为 false

几个关键项：slaveId 在 MySQL 看来就是一个从库 ID，必须全集群唯一且不能和 master 的 server_id 重复（重复时连接会被直接断开）；上面 127.0.0.1:3306 只适用于 Canal 和 MySQL 同机；master.journal.name/position/timestamp 三个留空是从当前位点开始订阅，想从历史某条 binlog 回放才需要指定；filter.regex 的 .*\..* 是库表正则（全库全表），生产建议收窄到业务库。

  1. 启动
sh bin/startup.sh
  1. 查看 server 日志
vi logs/canal/canal.log

正常启动应该看到 The server is running, listen on: [0.0.0.0:11111] 之类的行；报错集中在连不上 MySQL（网络/密码/权限）和位点无效两类。

  1. 查看 instance 的日志
vi logs/example/example.log

server 日志只反映进程级状态，订阅是否真的在拉 binlog、拉到了多少条，看 instance 日志更直接。

  1. 关闭
sh bin/stop.sh

2.2.2 通过 Docker 安装

  1. canal-server

拉取镜像

docker pull canal/canal-server:v1.1.8

运行容器

docker run -d \
    --name canal-server \
    -p 11111:11111 \
    -e canal.instance.master.address=127.0.0.1:3306 \
    -e canal.instance.dbUsername=canal \
    -e canal.instance.dbPassword=canal \
    -e canal.instance.connectionCharset=UTF-8 \
    -e canal.instance.tsdb.enable=true \
    -e canal.instance.gtidon=false \
    -e canal.instance.filter.regex=.*\\..* \
    canal/canal-server:v1.1.8

镜像把 instance.properties 的同名配置项都暴露成了 -e 环境变量，不需要挂配置文件就能改；canal.admin.group/canal.admin.port 两个环境变量指向 canal-admin 时，这个 server 才会被 admin 接管。两个注意：127.0.0.1 在容器里指向容器自身，连宿主机 MySQL 要写宿主 IP（或 host.docker.internal，Linux 需加 --add-host=host.docker.internal:host-gateway），连同机 MySQL 容器要用容器名——这正是第 5 节那个高频问题的根源；-v 挂上 logs/ 目录方便排错，否则日志只能 docker exec 进容器看。

  1. canal-admin

拉取镜像

docker pull canal/canal-admin:v1.1.8

运行容器

docker run -d \
    --name canal-admin \
    -p 8089:8089 \
    -e server.port=8089 \
    -e canal.adminUser=admin \
    -e canal.adminPasswd=admin \
    canal/canal-admin:v1.1.8

访问 web 界面 http://localhost:8089

admin 的默认账号密码就是 admin/admin，登录后可在「机器管理」里添加 canal-server（地址填 http://canal-server:11111，需两个容器同网络且 server 配了 canal.admin.port=11110），之后新建 instance、改 filter、启停订阅都能在页面上做，不用逐个改 properties 重启。注意 admin 自身的元数据（cluster/instance 配置）默认存在容器内嵌的 H2 里，容器重建会丢，正式使用建议通过 canal.admin.metah2.../远程数据库配置把元数据落到外部库。

3 使用

3.1 Canal Client

  1. 创建 maven 项目，并引入如下依赖
<dependency>
    <groupId>com.alibaba.otter</groupId>
    <artifactId>canal.client</artifactId>
    <version>1.1.0</version>
</dependency>

依赖版本建议和 canal-server 同线（server 用 1.1.8 就配 canal.client 1.1.8），老版 client 配新版 server 可能遇到协议兼容问题。下面示例的几个关键调用构成一套 at-least-once 语义：subscribe 用库表正则声明订阅范围（和 instance 的 filter 取交集）；getWithoutAck 拉一批但不确认，ack(batchId) 才推进位点，处理失败用 rollback(batchId) 退回重拉——所以消费逻辑要自己保证幂等。

  1. ClientSample 代码
public static void main(String args[]) {
    // 创建链接
    CanalConnector connector = CanalConnectors.newSingleConnector(new InetSocketAddress(AddressUtils.getHostIp(),
                                                                                        11111), "example", "", "");
    int batchSize = 1000;
    int emptyCount = 0;
    try {
        connector.connect();
        connector.subscribe(".*\\..*");
        connector.rollback();
        int totalEmptyCount = 120;
        while (emptyCount < totalEmptyCount) {
            Message message = connector.getWithoutAck(batchSize); // 获取指定数量的数据
            long batchId = message.getId();
            int size = message.getEntries().size();
            if (batchId == -1 || size == 0) {
                emptyCount++;
                System.out.println("empty count : " + emptyCount);
                try {
                    Thread.sleep(1000);
                } catch (InterruptedException e) {
                }
            } else {
                emptyCount = 0;
                // System.out.printf("message[batchId=%s,size=%s] \n", batchId, size);
                printEntry(message.getEntries());
            }

            connector.ack(batchId); // 提交确认
            // connector.rollback(batchId); // 处理失败, 回滚数据
        }

        System.out.println("empty too many times, exit");
    } finally {
        connector.disconnect();
    }
}

private static void printEntry(List<Entry> entrys) {
    for (Entry entry : entrys) {
        if (entry.getEntryType() == EntryType.TRANSACTIONBEGIN || entry.getEntryType() == EntryType.TRANSACTIONEND) {
            continue;
        }

        RowChange rowChage = null;
        try {
            rowChage = RowChange.parseFrom(entry.getStoreValue());
        } catch (Exception e) {
            throw new RuntimeException("ERROR ## parser of eromanga-event has an error , data:" + entry.toString(),
                                       e);
        }

        EventType eventType = rowChage.getEventType();
        System.out.println(String.format("================&gt; binlog[%s:%s] , name[%s,%s] , eventType : %s",
                                         entry.getHeader().getLogfileName(), entry.getHeader().getLogfileOffset(),
                                         entry.getHeader().getSchemaName(), entry.getHeader().getTableName(),
                                         eventType));

        for (RowData rowData : rowChage.getRowDatasList()) {
            if (eventType == EventType.DELETE) {
                printColumn(rowData.getBeforeColumnsList());
            } else if (eventType == EventType.INSERT) {
                printColumn(rowData.getAfterColumnsList());
            } else {
                System.out.println("-------&gt; before");
                printColumn(rowData.getBeforeColumnsList());
                System.out.println("-------&gt; after");
                printColumn(rowData.getAfterColumnsList());
            }
        }
    }
}

private static void printColumn(List<Column> columns) {
    for (Column column : columns) {
        System.out.println(column.getName() + " : " + column.getValue() + "    update=" + column.getUpdated());
    }
}

跑起来后在 MySQL 里随便 insert/update 一行，控制台就能打印出对应的 binlog 文件名、偏移量和变更前/变更后列。注意示例里 AddressUtils.getHostIp() 取的是本机 IP，跨机部署时换成目标地址；newSingleConnector(..., "example", "", "") 的后两个参数是 username/password，对应 canal.properties 里 canal.serverUser/canal.serverPassword 的鉴权（默认为空即不鉴权）。

3.2 不写代码：用 adapter 投递消息队列

不想维护消费代码时，canal.adapter 可以把变更直接推到 MQ 或目标存储，配置即用：

  1. 下载 canal.adapter-1.1.8.tar.gz（与 server 同版本），解压后改 conf/application.yml：server 端口 11111、canal.adapter.mode 改成目标模式（如 kafka）。
  2. 投递到 Kafka 时新增 conf/kafka/kafka.yml，指定 topic、bootstrapServers 和订阅的 instance；下游按普通 Kafka 消费即可（消息体是 JSON，含 database/table/type/data 字段），接入方式参考 Spring 整合 Kafka。
  3. 反向同步到目标库（MySQL→ES/MySQL/HBase）用 conf/userdata.yml/es 等映射配置，适合缓存失效、异构库同步类场景。

选择建议：消费逻辑简单且目标是现成存储 → adapter；需要业务加工、事务控制、重试策略 → client 自写消费。运维层面也可以只把 Canal 当 binlog 采集入口，后面接 Linux 环境下 Kafka 的安装与使用 集群做缓冲，削峰和重放都靠 Kafka 的 topic 回放能力。

4 问题与解决

4.1 使用 docker 运行 mysql 和 canal 无法监测到 binlog

可能是由于数据库连接配置问题导致的，在 docker 环境下 canal 不能直接通过 127.0.0.1 连接到 mysql，需要通过容器名访问（前提是 canal 和 mysql 已经连接到同一个 docker network），如 mysql 的容器名为 mysql-server，则通过 mysql-server:3306 访问

如果不是上述问题导致，需要根据实际 canal-server 的日志排查

tail -100f canal-server/logs/example/example.log

日志里常见的三类报错对应三个原因：Connection refused 是地址/端口不通（回到本节查网络）；Access denied for user 'canal' 是密码错或没给 REPLICATION SLAVE 权限；missing table map event/位点报错是 binlog 已被 MySQL 过期清理，删掉 instance 目录下的 meta.dat 后从当前位点重新开始。

4.2 MySQL 8 报 caching_sha2_password 相关错误

Canal 内置的 MySQL 驱动版本较老，对 MySQL 8 默认的 caching_sha2_password 认证支持不好（典型报错 Authentication plugin 'caching_sha2_password' cannot be loaded 或公钥获取失败）。两种解法选一：把 canal 账号改成旧认证 ALTER USER 'canal'@'%' IDENTIFIED WITH mysql_native_password BY 'canal';（简单直接，只影响这一个账号）；或部署时直接选带 _with_jdk11 后缀的新镜像/新版驱动。账号创建方式见 2.1，MySQL 8 认证机制的背景见 Linux 环境下 MySQL 的安装与使用。

5 小结

  • Canal 伪装 MySQL slave 拉 binlog，MySQL 侧只需 log-bin + ROW 格式 + REPLICATION 权限账号，准备过程就是 ops18 的 3.4 参数表。
  • 部署形态：二进制改 instance.properties，Docker 用同名 -e 环境变量；跨容器连接用容器名不用 127.0.0.1；需要页面管理再上 canal-admin（记得把元数据存外部库）。
  • 消费形态：client 自写逻辑（getWithoutAck/ack/rollback，at-least-once，消费端保证幂等）或 adapter 零代码投 Kafka/目标库。
  • 排错第一现场永远是 logs/<instance>/example.log：连不上、权限不够、位点丢失三类问题占绝大多数。
