Linux 环境下 Kafka 的安装与使用

strr0 2023-04-25

1 概述

Kafka 是一个以分区日志（partitioned log）为核心的分布式事件流平台：生产者把消息写进 topic 的某个分区，分区由多个 broker 上的副本（一主多从，ISR 同步）保存，消费者按 consumer group 记录 offset 顺序读取。它和传统消息队列的区别在于消息默认是追加存储、可重复消费的（而不是投递后删除），因此既能做业务解耦的队列，也能做数据管道的源。

本文用的是 kafka_2.12-3.4.0（2.12 是 Scala 版本，不是 Kafka 版本），这个版本仍然靠 ZooKeeper 保存集群元数据。需要知道的趋势：Kafka 3.3 引入了 KRaft 模式（用 broker 自带的 Raft Quorum 自己管元数据），4.0 起彻底移除 ZooKeeper，同时不再提供 Scala 2.12 的发行包并要求 JDK 17+。新集群可以直接上 KRaft 少维护一套 ZK；只是本文下面的命令都是围绕 ZK 模式写的。应用侧怎么用参考 Spring 整合 Kafka，本文只讲部署与运维。

2 安装

2.1 通过源码安装

2.1.1 Java 环境

参考 Java 环境搭建

2.1.2 Zookeeper 环境

下载 zookeeper
安装 zookeeper

tar -xzvf apache-zookeeper-3.8.1-bin.tar.gz -C /opt/software
cd /opt/software/apache-zookeeper-3.8.1-bin/conf
cp zoo_sample.cfg zoo.cfg

zk 基本配置

# /opt/software/apache-zookeeper-3.8.1-bin/conf/zoo.cfg

## zk 数据配置（可选）
dataDir=/opt/data/zookeeper

zk 启动与停止

cd /opt/software/apache-zookeeper-3.8.1-bin
bin/zkServer.sh start
bin/zkServer.sh stop

cp zoo_sample.cfg zoo.cfg 是必须要的一步：ZK 二进制包里没有 zoo.cfg，不拷就会报 Error: Could not find or load zoo.cfg。zkServer.sh start 默认已经后台运行（与下面 Kafka 的前台启动不一样），状态用 bin/zkServer.sh status 看。dataDir 名义上“可选”，实际默认值指向 /tmp/zookeeper——重启即清，所以生产必须显式配。另外 ZK 3.5+ 默认开了 AdminServer 占用 8080 端口，跟 Tomcat / Flink Web UI 冲突时可用 admin.serverPort=8085 改掉；想靠 srvr / mntr 做监控还需要 4lw.commands.whitelist=*。

2.1.3 安装

下载 kafka
安装 kafka

tar -xzvf kafka_2.12-3.4.0.tgz -C /opt/software

kafka 基本配置

# /opt/software/kafka_2.12-3.4.0/config/server.properties

## kafka 日志路径配置（可选）
log.dirs=/opt/data/kafka
## 对外地址配置
advertised.listeners=PLAINTEXT://{ip}:9092

这份配置能跑起来靠的是两个默认值：zookeeper.connect 在示例配置里已经是 localhost:2181（所以 ZK 必须同机，否则要改），broker.id 默认 0。真正必须改的是 advertised.listeners：它不是“我自己监听哪里”，而是broker 告诉客户端下次来连哪个地址，不填时会从本机 hostname 自动推导，于是出现“本地 localhost:9092 能连、另一台机器连上后拿到一个无法解析的 hostname”的经典问题。虚机、容器、多网卡、NAT 环境都必须显式写成客户端能访问到的 IP 或域名。

kafka 启动与停止

cd /opt/software/kafka_2.12-3.4.0
bin/kafka-server-start.sh config/server.properties
bin/kafka-server-stop.sh

kafka-server-start.sh 默认前台运行，关掉终端 broker 就走了；临时后台用 nohup bin/kafka-server-start.sh config/server.properties > /dev/null 2>&1 &，长期运行建议写 systemd unit（参考 ZK 与 Kafka 官方示例 unit），JVM 堆在脚本开头的 KAFKA_HEAP_OPTS 里改（默认 -Xmx1G，真实环境基本都要调）。kafka-server-stop.sh 实际是 kill -15 匹配到的 java 进程，机器上还跑着其他 Kafka 相关进程时可能误杀，用 ps -ef | grep kafka.Kafka 确认 PID 再停更安全。

2.2 通过 Docker 安装

2.2.1 拉取镜像

docker pull bitnami/zookeeper
docker pull bitnami/kafka

2.2.2 运行容器

创建网络

docker network create dev --driver bridge

运行 zookeeper 容器

docker run -d --name zookeeper-server \
    -p 2181:2181 \
    -e ALLOW_ANONYMOUS_LOGIN=yes \
    --network dev \
    bitnami/zookeeper:latest

运行 kafka 容器

docker run -d --name kafka-server \
    -p 9092:9092 \
    -e KAFKA_BROKER_ID=1 \
    -e KAFKA_CFG_LISTENERS=PLAINTEXT://:9092 \
    -e KAFKA_CFG_ADVERTISED_LISTENERS=PLAINTEXT://{ip}:9092 \
    -e KAFKA_CFG_ZOOKEEPER_CONNECT=zookeeper-server:2181 \
    -e ALLOW_PLAINTEXT_LISTENER=yes \
    --network dev \
    bitnami/kafka:latest

这段命令拿来验证能用，但直接拿到正式环境会踩四个坑：

  1. 没有挂载数据目录。ZK 的数据在 /bitnami/zookeeper，Kafka 的日志在 /bitnami/kafka（对应 KAFKA_CFG_LOG_DIRS），容器一删消息全丢。至少要加 -v /docker/kafka/data:/bitnami/kafka。
  2. {ip} 占位符在容器场景下很难填对。KAFKA_CFG_ADVERTISED_LISTENERS 写的地址必须是宿主机之外也能访问的地址；写容器名只对同一 Docker 网络里的客户端有效，写 localhost 则只能本机工具用。常见做法是配两个 listener：
-e KAFKA_CFG_LISTENERS=INTERNAL://:9092,EXTERNAL://:9093 \
-e KAFKA_CFG_ADVERTISED_LISTENERS=INTERNAL://kafka-server:9092,EXTERNAL://<宿主机 IP>:9093 \
-e KAFKA_CFG_LISTENER_SECURITY_PROTOCOL_MAP=INTERNAL:PLAINTEXT,EXTERNAL:PLAINTEXT \
-e KAFKA_CFG_INTER_BROKER_LISTENER_NAME=INTERNAL \
-p 9093:9093
  1. ALLOW_ANONYMOUS_LOGIN=yes（ZK）+ ALLOW_PLAINTEXT_LISTENER=yes（Kafka）等于全开无认证。9092 裸奔意味着任何能连上端口的客户端都能读全量消息、写脏数据、甚至删 topic，比 Redis 裸露更危险（Kafka 没有 requirepass 这种“一个密码共用的”低档保护）。内网之外一律用 SASL（SASL_PLAINTEXT / SASL_SSL，SCRAM 机制）加 TLS，KRaft 模式下用户信息直接存在集群元数据里，不用再往 ZK 写。
  2. tag 不要直接写 latest，固定到 bitnami/kafka:3.7 这类具体版本；ZooKeeper 版本与 Kafka 版本也有兼容矩阵（3.4 要求 ZK 3.6+，本文的 3.8.1 在范围内）。另外 Apache 官方也提供了 apache/kafka 镜像（KRaft 模式、自带 ZooKeeper-free 配置），不想依赖第三方镜像时可选它。

3 使用

3.1 基础操作

查看所有 topic

cd /opt/software/kafka_2.12-3.4.0
bin/kafka-topics.sh --bootstrap-server localhost:9092 --list

创建 topic

cd /opt/software/kafka_2.12-3.4.0
bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic my_topic_name \
    --partitions 20 --replication-factor 3 --config x=y

这条命令在单节点环境上会直接失败：--replication-factor 3 要求集群里至少有 3 个 broker，只有一个时报 Replication factor: 3 larger than available brokers: 1。本地验证请改成 --partitions 1 --replication-factor 1；末尾的 --config x=y 是占位，常见真实需求是 --config retention.ms=604800000（保存 7 天）或 --config cleanup.policy=compact。分区数一旦定下就不太好改（见下条），而副本数影响可用性：生产集群一般 replication-factor=3 配合 min.insync.replicas=2，两者一起决定 broker 挂掉时还能不能继续写。

修改 topic

bin/kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic my_topic_name \
    --partitions 40

分区只能增不能减，而且增加分区会破坏分区内的顺序保证：之前按 key 哈希到分区 3 的消息，扩容后可能落进新分区，同一业务实体的消息顺序就乱了。对顺序敏感（如同一条订单的状态变更）的 topic 要么一开始就把分区数留足，要么改用新 topic + 双写迁移。--alter 也可以改 --config，但 partitions 以外的配置修改不影响已有分区的消息。

删除 topic

bin/kafka-topics.sh --bootstrap-server localhost:9092 --delete --topic my_topic_name

删除是异步的（标记后由后台线程执行），且需要 delete.topic.enable=true（3.x 默认就是 true，旧版本默认 false 时命令看起来成功但 topic 仍在）。另外 --delete 不可逆，消息连同 offset 一起消失，先把命令里的 localhost:9092 确认一遍再回车。想先观察可以用 --describe，它会列出 Leader、Replicas、ISR 与各分区起始 offset。

生产者

bin/kafka-console-producer.sh --topic quickstart-events --bootstrap-server localhost:9092

> This is my first event
> This is my second event

消费者

bin/kafka-console-consumer.sh --topic quickstart-events --from-beginning --bootstrap-server localhost:9092

This is my first event
This is my second event

注意两个块里的 > 是 producer 的输入提示符（不敲 >），而 consumer 输出不带 >，直接粘回终端会把提示符一并当消息内容。console 工具只适合联调：它默认一条一行、无批量、无重试，且 --from-beginning 会从最早的消息开始打（大 topic 上能把磁盘带宽刷满）。想验证分区与 key 行为可以用 --property print.key=true,print.partition=true,print.offset=true --property print.timestamp=true；生产者侧 kafka-console-producer.sh --parse-key --delimiter : 可以按 key:value 格式发送，用来观察同一 key 是否总进同一分区。

3.2 消费堆积与消费者组排查

运维中最常回答的问题是“积压了多少、谁在消费、为什么没消费”，靠的是 consumer group 工具：

bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --list
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group my-group
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --delete-offsets --group my-group --topic my_topic_name

--describe 输出里重点看三列：CURRENT-OFFSET（已消费到哪）、LOG-END-OFFSET（写到哪）和两者的差 LAG（积压量）。LAG 持续增长说明消费能力不够，稳定不变且不为 0 可能是卡死（消费者活着但不推进，常见于单条处理超时后重试或死循环）；--describe 不输出成员信息时再加 --members，能看到各分区被哪个消费者实例抢到、rebalance 是否反复发生。分区数大于消费者实例数时会有实例闲着，分区数小于实例数时多余实例不干活——扩容消费者之前先确认 kafka-topics.sh --describe 里的分区数。

4 上线检查清单

项说明
advertised.listeners必须是客户端可达地址，否则“连得上却发不了消息”
认证对外端口上 SASL（SCRAM）+ TLS；ZK 不开匿名访问；ALLOW_PLAINTEXT_LISTENER 只用于本地
数据目录源码部署的 log.dirs / Docker 的 /bitnami/kafka 挂载与备份，dataDir 不能指 /tmp
副本与落盘replication.factor>=3、min.insync.replicas=2、acks=all；刷盘间隔默认依赖 OS page cache，一般不需要调 log.flush.interval.messages
retention默认 7 天，按磁盘容量与回放需求设 retention.ms / retention.bytes，并区分 compact 类 topic
JVM 与系统参数堆大小（默认 1G）、ulimit -n（文件句柄少会直接报 Too many open files）、关闭 swap（vm.swappiness=1）
监控LAG、ISR 收缩率、UnderReplicatedPartitions、磁盘使用率、RequestHandler 线程忙比
升级预案ZK 模式与 KRaft 不能长期共存，规划好 Kafka 4.0 之前的迁移窗口

5 小结

  • Kafka 靠 ZooKeeper 存元数据的旧架构已经到尾声，新集群直接上 KRaft 可以少维护一套 ZK；本文的 3.4 命令仍然需要先起 ZK。
  • listeners 是自己监听哪里，advertised.listeners 是告诉客户端来连哪里，两者的区分解决了绝大多数“本地能用、远程连不上”的问题。
  • Docker 那两条 docker run 不带数据卷、不带认证，只适合验证；正式部署需要挂卷、固定版本 tag，并把 PLAINTEXT 换成 SASL/TLS。
  • --replication-factor 不能超过 broker 数；分区只增不减，而 LAG（kafka-consumer-groups.sh --describe）是判断消费问题的第一入口。
