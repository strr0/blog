Jenkins 自动化部署

strr0 2024-07-12

1 概述

Jenkins 是基于 Java 的开源持续集成/持续部署（CI/CD）工具，生态成熟、插件丰富，适合"没有 GitLab 自带 CI、但要自动化发布"的场景。本文走的是最轻量的路线：直接 java -jar jenkins.war 跑单机 + Freestyle 任务 + Execute shell 后置脚本；团队长期使用建议尽早转向 Pipeline（Jenkinsfile 把流程写进仓库，可审查可回放），本文的步骤在两种形态下都适用。

与 GitLab CI/CD 自动化部署 的对比：GitLab CI 的执行器（Runner）概念在 Jenkins 里对应 Agent/节点；Jenkins 单机部署时"Master 就是执行机"，本文章节里的后置脚本默认就落在同一台机器上。另外出于安全考虑，Jenkins 官方不建议在 Master 上直接跑构建，正式环境应挂 Agent 节点；本文的单机形态适合个人与小团队，上生产前请评估这一点。

2 部署

2.1 环境要求

  • 机器要求：

256 MB 内存，建议大于 512 MB

10 GB 的硬盘空间（用于 Jenkins 和 Docker 镜像）

  • 需要安装以下软件：

Java 8 （JRE 或者 JDK 都可以）

Docker （导航到网站顶部的 Get Docker 链接以访问适合您平台的 Docker 下载）

这段是 Jenkins 早期教程的要求，现在的水位已经变了：Jenkins 2.426 起不再支持 Java 8，最低要求 Java 11，官方推荐 Java 17；老镜像里 256 MB 内存也只是能启动，真跑 Maven 构建建议 2 GB 起。Java/Docker 的安装参考 基础环境配置 与 Docker 安装。

2.2 安装及初始化

2.2.1 下载

下载 Jenkins

war-stable 是 LTS 稳定线；另有 war/latest（weekly）功能新但插件兼容风险高，生产用 LTS。内网下载可走国内镜像 https://mirrors.tuna.tsinghua.edu.cn/jenkins/war-stable/latest/jenkins.war。

2.2.2 运行

打开终端进入到下载目录，运行命令

java -jar jenkins.war --httpPort=8080

打开浏览器进入链接 http://localhost:8080 按照说明完成安装

初始化页面会要求解锁管理员密码，位置在提示的路径（默认工作目录 .jenkins/secrets/initialAdminPassword，也可以看启动日志输出）；接着选 Install suggested plugins 或自定义插件列表，并创建首个管理员账号。两个安全点：首次安装页可以点 Skip 跳过向导，但跳过后任何人访问 8080 都能直接进后台建账号，只在完全内网的临时验证时可以这么做；另外 Jenkins 默认允许匿名读，装完第一时间在 Manage Jenkins > Security 里把权限收紧到 Logged-in users。

2.2.3 配置国内镜像

官方插件源在国内访问不稳定，下载插件超时/校验失败时把更新中心换成清华镜像。进入 jenkins 工作目录（如 /home/centos/.jenkins）

cd /home/centos/.jenkins

修改 hudson.model.UpdateCenter.xml

<?xml version='1.1' encoding='UTF-8'?>
<sites>
  <site>
    <id>default</id>
    <url>https://mirrors.tuna.tsinghua.edu.cn/jenkins/updates/update-center.json</url>
  </site>
</sites>

修改 updates/default.json，全文替换地址

:%s/www.google.com/www.baidu.com/g
:%s/https:\/\/updates.jenkins.io\/download/https:\/\/mirrors.tuna.tsinghua.edu.cn\/jenkins/g

这两行其实是 vim 命令模式的替换命令（不是 bash）：用 vim updates/default.json 打开文件后逐行输入。把 www.google.com 换成 www.baidu.com 是因为 Jenkins 用"访问某站点是否成功"做网络可达性探测，Google 在国内探测必失败，插件页会显示离线。改完两个文件后重启 Jenkins 并在 Manage Jenkins > Plugins 点 Check now 重新拉取索引。

2.2.4 重启

nohup java -jar jenkins.war --httpPort=8080 > jenkins.log &

war 直跑形态没有进程守护，换端口、改 JVM 内存都要先杀旧进程再起新的（ps -ef | grep jenkins.war 找 PID）。长期运行建议用 systemd 单元托管（ExecStart 指向同样的 java 命令，配 Restart=always），顺手把 JAVA_OPTS 的堆大小显式固定下来；正式部署更推荐官方 Docker 镜像或 war 放 Tomcat，本文后续步骤不受影响。

2.3 问题与修复

无法访问 jenkins，检查端口是否开放

firewall-cmd --list-ports

如果端口未开放，运行如下命令开放

firewall-cmd --permanent --zone=public --add-port=8080/tcp
systemctl reload firewalld

--permanent 只写持久配置，必须配合后面的 reload 才生效（两套配置的关系详见 基础环境配置 的第 5 节）；云服务器还要叠加安全组放行。排障顺序建议：先在本机 curl -v http://127.0.0.1:8080 确认 Jenkins 活着，再查防火墙、最后查安全组。

3 使用

3.1 基础

3.1.1 插件安装

Manage Jenkins > Plugins > Available plugins

  • Maven Integration plugin
  • Git plugin

搜索安装 Maven Integration 和 Git 两个插件（Git 通常在 suggested 列表里已装）；插件安装走的就是 2.2.3 配的更新中心，国内不换镜像很容易卡在依赖解析。

3.1.2 全局配置

Manage Jenkins > Tools

配置 jdk、maven、git 等。注意 JDK 条目与构建用 JDK 是两回事：Jenkins 自身跑在哪个 Java 与 Maven 任务用哪个 JDK 可以在 Tools 里分开指（比如 Jenkins 跑 Java 17、任务用 Java 8 的老 JDK），路径按 基础环境配置 装好的 /usr/local/java/... 填；Git 那行默认会自动探测，报 Not Found 时手工指定 /usr/bin/git 或源码安装的 /usr/local/git/bin/git。

3.1.3 凭证配置

Manage Jenkins > Credentials

在 Stores scoped to Jenkins 列表的 Domains 下面 (global) 点击 Add credentials

私有仓库常用两种：Username with password（HTTPS 拉代码，GitLab 可填 Personal Access Token 代替密码，比真实密码好吊销）和 SSH Username with private key（SSH 拉代码）。凭证只在此处配置一次，任务里按 ID 引用；泄露风险面比把 token 写进脚本小得多。

3.2 Maven 项目配置

3.2.1 构建一个 maven 项目

新建任务选 Maven 项目（依赖 Maven Integration plugin），如 springboot-demo

3.2.2 配置源代码

在 Source Code Management 选择 Git

配置仓库地址和凭证及分支等信息。仓库地址用 HTTPS 时确认以 .git 结尾（见 3.3）；首次构建报 NoSuchMethodError/凭证类错误先回 3.1.3 检查凭证类型。

3.2.3 配置 maven options

如 clean package -U -Dmaven.test.skip=true

Maven 项目类型的 Root POM 默认 pom.xml，Goals 里不写 mvn 只写参数。-U 强制更新 SNAPSHOT（依赖经常被刷新时好用，代价是每次都慢一截）；-Dmaven.test.skip=true 与 -D 之间不能有空格，写法细节与两种跳测试的区别见 RuoYi-Vue-Plus 框架 3.1。

3.2.4 配置后置脚本

在 Post Steps 底下点击 Add post-build step 选择 Execute shell

#!/bin/bash
BUILD_ID=springboot-demo

JVM_OPTION="-Xms256m -Xmx1024m"
FILE_PATH="/home/centos/workspace/springboot-demo/springboot-demo.jar"
LOG_PATH="/home/centos/workspace/springboot-demo/springboot-demo.out"
PROFILES="prod"

PID=`ps -ef | grep springboot-demo | grep java | awk '{print $2}'`
if [ ! -z "$PID" ]
then
   kill -9 $PID
fi

rm -rf $FILE_PATH

cp /home/centos/.jenkins/workspace/springboot-demo/target/springboot-demo.jar $FILE_PATH

nohup java -jar -Dspring.profiles.active=$PROFILES $JVM_OPTION $FILE_PATH >> $LOG_PATH 2>&1 &

脚本做的事：kill 旧进程 → 删旧 jar → 从构建工作区拷新 jar → nohup 拉起。几个要改自己项目时的注意点：

  • ps -ef | grep springboot-demo | grep java 是子串匹配，同机部署了名字相近的服务（如 springboot-demo-admin）会一并 kill；名字有包含关系时把 grep 收紧成 -jar.*springboot-demo\.jar，或改用 pidfile 记录 PID。
  • kill -9 不给应用 graceful shutdown 的机会（正在处理的请求直接断），先 kill $PID（SIGTERM）等待几秒再兜底 kill -9 更稳。
  • Spring Boot 3 的优雅停机需要 server.shutdown=graceful 配合才有意义。
  • 路径全部硬编码 /home/centos/...，换用户/换机器时逐处改；更好的做法是提成 Jenkins 全局变量。
  • 拉起后没有任何健康检查，构建成功不等于服务启动成功；收尾加一句 sleep 5 && curl -sf http://127.0.0.1:8080/actuator/health || exit 1，让启动失败直接反映在构建结果上。

3.2.5 配置后置脚本（docker）

在 Post Steps 底下点击 Add post-build step 选择 Execute shell

#!/bin/bash
BUILD_ID=springboot-demo

containerId=`docker ps -aq -f name=^${BUILD_ID}$`
if [ ! -z "$containerId" ]
then
   docker stop $containerId
   docker rm $containerId
fi
imageId=`docker images -q ${BUILD_ID}:1.0`
if [ ! -z "$imageId" ]
then
   docker rmi $imageId
fi

docker build -t "springboot-demo:1.0" springboot-demo

docker run -d --name springboot-demo -p 8081:8080 -v /home/centos/workspace/springboot-demo/config:/config springboot-demo:1.0

Docker 形态的要点：

  • 原稿里两处 ID 获取用的是 docker ps -a | grep xxx | awk '{print $1}' 和 docker images | grep xxx | awk '{print $3}'：grep 子串匹配会误伤名字相近的容器，awk 取列在输出格式变化时不稳定，已改成官方推荐的 -f name=^...$ / docker images -q 写法（同 Docker 安装 4.7）。
  • docker build 的上下文目录 springboot-demo 是相对任务工作区的路径：如果 Dockerfile 在仓库根目录，这里应该写 .；而且必须先跑完 3.2.3 的 mvn package（Dockerfile COPY ./target/*.jar 时否则报 COPY failed，机理见 RuoYi-Vue-Plus 框架 3.2）。
  • 镜像 tag 写死 1.0 意味着每次都要先删旧镜像才能重建；用 1.0-$BUILD_NUMBER 并保留回滚能力更稳，删镜像那步也可以省掉（新 tag 不冲突，旧镜像交给定期清理）。
  • -v .../config:/config 挂载外部配置是对的；容器里连宿主机服务时同样不能写 localhost（指容器自己），参考 Docker 安装 的 bridge/host 网络部分。
  • Jenkins 跑 docker 命令同样需要 jenkins 用户在 docker 组（机理同 GitLab CI/CD 4.2，记得重启生效并评估 docker 组≈root 的风险）。

3.3 问题与修复

3.3.1 Jenkins 拉取代码报 hudson.plugins.git.GitException: Failed to fetch from xxx

配置 git 仓库地址加上 .git 后缀。GitLab/Gitee 对不带 .git 的 smart-http 端点处理有差异，Jenkins（JGit 实现）容易在协商阶段就失败；加上后缀是最便宜的修法。如果改了仍失败，依次检查：凭证类型与权限（3.1.3）、仓库路径里有无多余空格/尾斜杠、服务器到 Git 仓库的网络与代理。

3.3.2 构建成功但服务没起来

后置脚本里 nohup 拉起失败不会反映到构建结果（见 3.2.4 最后一条）；排查顺序：看 $LOG_PATH 尾部异常 → ps -ef | grep java 确认进程 → 确认端口没被旧进程占着。另外 nohup 方式启动的进程归属于执行用户，Jenkins 被重启不会带走它，容易出现"旧进程一直在、新 jar 从没生效"的假象。

4 部署检查清单

项说明
Java 版本新版 Jenkins 最低 Java 11（推荐 17）；任务用 JDK 在 Tools 里单独指
安全不改初始管理员密码/跳过向导 = 裸奔；匿名读要收紧；8080 不暴露公网
更新中心国内换清华镜像后记得改 default.json 的探测地址并 Check now
凭证用 PAT/SSH key，不要把密码写进后置脚本
Maven-Dmaven.test.skip=true 不能有空格；SNAPSHOT 依赖才加 -U
重启脚本grep 子串误杀风险；kill -9 → SIGTERM；加健康检查步骤
Docker 形态先 package 再 build；容器名精确匹配；tag 用 BUILD_NUMBER；jenkins 用户在 docker 组
防火墙8080 --permanent + reload；叠加安全检查组

5 小结

  • war 直跑的 Jenkins 适合个人/小团队快速自动化发布；正式环境考虑 Agent 分离与 Pipeline 化。
  • 两条发布路线共用同一套骨架：Git 拉代码 + Maven 打包 + 后置脚本切旧进程、上新产物；区别只在产物落在宿主机 jar 还是 Docker 镜像。
  • 后置脚本的三个共性风险：子串匹配误杀、kill -9 硬切、构建绿灯不等于服务启动成功——加健康检查是唯一不把运气留给线上的手段。
