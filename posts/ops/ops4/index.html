Linux 环境下 RabbitMQ 的安装与使用

strr0 2023-05-01

1 概述

RabbitMQ 是一个实现了 AMQP 0-9-1 协议的消息代理，模型上是“路由”而不是“存储”：生产者把消息发给 exchange，exchange 根据类型与 binding 规则把消息投递到一个或多个 queue，消费者确认（ack）后消息就从队列删除。这一点和 Kafka 的追加日志根本不同——RabbitMQ 不能“回到上周重新消费”，堆积超过阈值要么压内存要么落盘，所以它适合任务分发、异步解耦、延迟/重试队列，不适合做事件溯源与回放。

四个常见 exchange 类型：direct（routing key 精确匹配）、fanout（广播给所有绑定队列，不看 key）、topic（order.*.paid、order.# 这种通配匹配）、headers（按消息属性匹配，实际用得少）。另外还有一个名字为空串的 default exchange，此时 routing key 直接当队列名用——很多新手代码“没声明 exchange 也能发”就是靠它。

本文用官方镜像 rabbitmq:3-management（tag 里的 management 表示预装了管理插件）。RabbitMQ 4.x 已经发布，要求较新的 Erlang/OTP，并把 Streams 纳入主线，不过本文用到的这些命令在 3.13 与 4.x 上基本一致。应用侧的写法参考 Spring 整合 RabbitMQ，本文只讲部署与运维。

2 安装

2.1 通过 Docker 安装

2.1.1 拉取镜像

docker pull rabbitmq:3-management

不带 management 的镜像需要自己 rabbitmq-plugins enable rabbitmq_management 才有 15672 页面。建议把版本固定到具体小版本（如 rabbitmq:3.13-management-alpine）而不是 3，否则上游推新 tag 时你的部署会跟着漂。alpine 版体积小，但调试工具少，需要时在管理页面与容器内命令行之间做取舍。

2.1.2 运行容器

docker run -d --hostname my-rabbit \
    --name rabbitmq-server \
    -p 5673:5672 \
    -p 15673:15672 \
    -e RABBITMQ_DEFAULT_USER=user \
    -e RABBITMQ_DEFAULT_PASS=password \
    rabbitmq:3-management

端口：15673 还是 15672？ 这条命令把宿主机端口做了偏移：AMQP 在宿主机是 5673，管理端是 http://localhost:15673（而不是很多教程里写的 15672）。如果本机还跑着另一个 RabbitMQ、或你希望跟 Spring 整合 RabbitMQ 里的 localhost:5672 直接对上，把映射改成 -p 5672:5672 -p 15672:15672 即可，容器内端口不用动。其他相关端口：5671（TLS AMQP）、15671（TLS 管理端）、15692（Prometheus 指标，rabbitmq_prometheus 插件默认开）、4369（epmd，仅集群需要）、25672（节点间通信）。

剩下三个更容易踩的坑：

  • 没有挂载数据目录。队列、交换机、用户、vhost 等元数据（Mnesia）与持久化消息都在 /var/lib/rabbitmq，不挂卷的话容器一删全部消失，连 durable 队列的定义也留不住。至少加 -v /docker/rabbitmq/data:/var/lib/rabbitmq，日志可选 -v .../log:/var/log/rabbitmq。
  • --hostname 决定节点名。RabbitMQ 节点名是 rabbit@<hostname>，Mnesia 数据与节点名绑定。改了 hostname 等于换了一个节点，旧数据卷里的元数据不会被识别（表现为“队列都不见了”），集群与持久化部署中这个值不能随便变。
  • RABBITMQ_DEFAULT_USER / PASS 只在首次初始化生效。数据目录已有元数据时这两个环境变量会被忽略，改了重启密码也不会变；改密码用 rabbitmqctl change_password <user> <newpass> 或管理页面。另外镜像默认创建的用户不再受 guest 只能本机连接的限制。

3 使用

3.1 管理端

http://localhost:15672（账号密码 user/password）

按 2.1.2 的端口映射，这里实际应该访 http://localhost:15673。管理页面上能看 vhost 切换、Connections / Channels / Consumers、Exchanges 与 Queues（可在页面直接 declare、绑定、发布/获取消息）、以及 Policy 定义。三个实用细节：Overview 页面的 Message rates 是判断消费快慢最直接的入口；队列页的 Get messages 默认 Ack mode = Acknowledgment，拉下去的消息会被确认并删除，想“看看不删”要改成 Nack requeue；Ports and admin 里设了 RABBITMQ_DEFAULT_PASS 的用户密码在页面上是可见的，管理端口暴露到公网等于泄露凭证。

3.2 基础操作

下面的命令默认在容器里执行：docker exec -it rabbitmq-server rabbitmqctl ...，宿主机没装 RabbitMQ 时直接调 rabbitmqctl 会报命令不存在，或因为连不到 epmd/节点而报错。

启动

rabbitmqctl start_app

停止

rabbitmqctl stop_app

停止并关闭节点

rabbitmqctl stop

获取所有队列

rabbitmqctl list_queues

获取消息数量

rabbitmqctl list_queues name messages_ready messages_unacknowledged

messages_ready 是已入队等待投递的消息，messages_unacknowledged 是已发出但还没收到 ack 的消息，两者相加才是通常说的“堆积”。list_queues 不带参数时只查当前 vhost，多 vhost 环境用 rabbitmqctl list_queues -p <vhost> ...；想定位“谁在消费”用 rabbitmqctl list_queues name consumers，或直接看 list_consumers。

创建队列

rabbitmqadmin declare queue name=<myqueue> durable=true

从这一条开始换工具了：rabbitmqadmin 不是 Erlang 节点上的控制命令，而是管理 HTTP API 的封装，所以它走的是 15672（本例映射后是 15673）而不是 5672，需要 -H localhost -P 15673 -u user -p password -V <vhost> 把地址、端口、账号和 vhost 都给对；缺省它会试 15672 的 /api。官方镜像里没有自带 rabbitmqadmin，需要从仓库下载放到能执行的目录，或者干脆用管理页面/声明式配置完成同样的事。另外 durable=true 只保证队列定义重启不丢，消息真的落盘还需要消息本身也用 persistent 标志（delivery_mode=2），否则队列在但消息空。

创建交换机

rabbitmqadmin declare exchange name=<myexchange> type=<direct,fanout,topic,header>

type=<direct,fanout,topic,header> 是枚举占位，直接复制执行会报参数非法，实际只能选一个（且 headers 类型的名字是 headers 不是 header）。交换机创建后类型不可改，要换只能新建后迁移；内置的 amq.topic、amq.direct、amq.fanout 可以直接用，不必新建。

绑定队列到交换机

rabbitmqadmin declare binding source=<myexchange> destination=<myqueue>

direct/topic 类型的交换机不写 destination_key（即 routing key / pattern）的绑定等于白绑：source=ex destination=q destination_key=order.paid（topic 类型可用 order.*、order.#）。只有 fanout 和 headers 不依赖 routing key。另外 destination_type=queue 与交换机到交换机的绑定（destination_type=exchange，做层级路由用）也需要明确。

发布消息

rabbitmqadmin publish exchange=<myexchange> routing_key=<myroutingkey> payload=<mymessage>

想发到队列名的默认路由，写 exchange=amq.default routing_key=<myqueue>（default exchange 在 API 里的名字就是 amq.default）。payload 不带引号时含空格的文本会被拆成多个参数，命令行里最好写成 payload="<mymessage>"。

获取消息

rabbitmqadmin get queue=<myqueue> requeue=false

requeue=false 意味着取出来的消息会被 ack 删除，用它“看看队列里有什么”直接把消息消费掉了，测试环境能接受、生产队列上就是丢数据。只想看内容就配合 count=1 ackrequeue=true（新版参数名，旧版写 requeue=true），并且先确认这些消息不是业务唯一副本。

删除队列

rabbitmqctl delete_queue <myqueue>

删除不可逆：队列里未消费的消息会直接丢弃。队列名含特殊字符时需要加引号，而带参数（如 x-queue-type=quorum）的队列重建后参数必须一致，否则声明会因属性不匹配报错（PRECONDITION_FAILED）。实际项目中很少手动建队，一般由应用启动时声明，手动建只是用来提前配好 TTL/DLX 等参数。

获取所有消费者

rabbitmqctl list_consumers

输出是 queue_name / channel_pid / consumer_tag / ack_required / prefetch_count 等列，排查“消息分给了谁”时配合 list_channels 看。prefetch_count（QoS）是个很关键的参数：不设（=0）时 broker 会无限制地往消费者里推，容易造成内存倒灌，Spring Boot 侧对应的配置是 listener.simple.prefetch，具体参见 Spring 整合 RabbitMQ。

3.3 高可用与常见队列参数

集群方向：经典镜像队列（ha-mode 策略）已在 3.10 中移除，现在官方推荐 Quorum 队列，声明时加 x-queue-type=quorum（需要奇数个节点、走 Raft，不支持优先级队列）。Docker 环境下的集群要求三个条件同时满足：各节点 --hostname 固定且能相互解析、共享同一个 Erlang cookie（RABBITMQ_ERLANG_COOKIE 或挂载同一份 cookie 文件）、开通 4369 与 25672。之后用 rabbitmqctl join_cluster rabbit@<node>（需在目标节点 stop_app 状态下执行）把节点加进去，rabbitmqctl cluster_status 验证。

业务上最常用的三类参数（建议用 policy 统一管，而不是每个队列手动声明）：

# TTL + 死信：超时未消费的消息转进死信队列
rabbitmqctl set_policy --apply-to queues ttl-dlx "^order\\." '{"message-ttl":60000,"dead-letter-exchange":"dlx"}' --priority 1
  • TTL：message-ttl（队列级）或发布时 expiration（消息级）；队列上不同 TTL 的消息只看队头，会出现“后面的先过期”。
  • 死信（DLX）：dead-letter-exchange / dead-letter-routing-key，被 reject（且 requeue=false）、过期、或因 max-length 被顶出的消息会转到这里——这是重试队列与死信队列的实现基础，消费失败时不要无条件 requeue=true，否则会在原地死循环。
  • 长度上限：max-length 配合 overflow=drop-head|reject-publish，防止堆积把内存吃光；更大的堆积可以用 Lazy Queue / Streams 把消息主要放磁盘。

内存告警方面，RabbitMQ 默认在内存用到宿主总量 40% 时开始阻塞生产者（vm_memory_high_watermark.ratio），而容器里它看到的常常是宿主内存而非限额，所以建议同时设 --memory=1g（Docker 限额）与 RABBITMQ_VM_MEMORY_HIGH_WATERMARK=0.6 这类绝对值，否则会出现“容器被 OOM kill 而不是背压”的现象。磁盘水位（disk_free_limit，默认 50MB 太低）也建议按机器磁盘的 50% 调高。

4 上线检查清单

项说明
端口对应宿主机映射（5673/15673）与应用配置里的地址、rabbitmqadmin -P 三者一致
数据卷挂 /var/lib/rabbitmq，否则队列定义与消息随容器消失
hostname / 节点名固定 --hostname，变更等于丢数据
账号与权限不用 guest 远程登录；按 vhost 授权 rabbitmqctl add_user + set_permissions -p <vhost> <user> ".*" ".*" ".*"；管理端口不暴露公网
vhost多业务共用实例时按环境/业务分 vhost，相当于命名空间隔离
prefetch 与 ack消费者必须设 prefetch_count，手动 ack，失败走重试/死信而不是无限 requeue
持久化队列 durable + 消息 delivery_mode=2，两者缺一都会重启丢消息
高可用关键队列用 Quorum 类型；集群节点奇数、cookie 一致、磁盘水位已调
监控管理 API /api/queues、Prometheus 插件（15692）：堆积量、ack 率、内存/磁盘水位、阻塞连接

5 小结

  • RabbitMQ 是路由模型（exchange → binding → queue，ack 即删），Kafka 是日志模型（追加 + offset 回放）；需要重试/延迟/路由选 RabbitMQ，需要回放/大吞吐选 Kafka。
  • Docker 命令里只改了两行就能差一个端口：映射到 5673/15673 后，管理端与 rabbitmqadmin -P 都要跟着变，应用配置也不能再默认 5672。
  • 不挂数据卷、改 --hostname、事后改 RABBITMQ_DEFAULT_PASS 是三个最容易丢数据或丢配置的动作。
  • rabbitmqctl（节点控制）与 rabbitmqadmin（HTTP API）不是一套东西，后者需要 management 插件且默认只走 15672；用 rabbitmqadmin get 看消息会真删除消息。
  • 堆积排查先看 messages_ready / messages_unacknowledged，消费失败靠 TTL+DLX 做重试与死信，高可用靠 Quorum 队列。
