Linux 环境下 Nginx 的安装与使用

strr0 2024-11-12

1 概述

Nginx（engine x）是一个高性能的 HTTP 与反向代理服务器，也提供 IMAP/POP3/SMTP 代理。它用 epoll/kqueue 事件驱动 + 多进程模型（一个 master 管 N 个 worker，每个 worker 单线程处理海量连接），所以内存占用小、并发高，常见角色是：静态资源服务器、反向代理与负载均衡、TLS 终结点、前端项目的统一入口。

版本上 Nginx 分主线（mainline）与稳定（stable）两条线，生产选 stable 分支、需要新特性才用主线（文中的 1.25.1 属于当时的主线）。下面都是源码编译路径，目的主要是能自己选模块（HTTPS、stream、状态页）；如果只需要标准能力，包管理器安装会省事得多，但目录结构与本文不同（配置在 /etc/nginx、站点在 /usr/share/nginx）。

2 安装

2.1 编译环境依赖

Debian 系

apt install gcc zlib1g zlib1g-dev libpcre3-dev libssl-dev

Redhat 系

yum install gcc zlib zlib-devel pcre pcre-devel openssl openssl-devel

2.2 获取源码

Nginx 依赖几样东西：GCC（编译）、PCRE（rewrite 与 location ~ 的正则）、zlib（gzip）、OpenSSL（HTTPS）。发行版把 PCRE1 拆成了 libpcre3-dev，而 PCRE1 早已停止维护、新系统上逐步换成 PCRE2（包名 libpcre2-dev）；configure 报 the HTTP rewrite module requires the PCRE library 时两个包都试一下。如果不想处理这些依赖关系，apt install nginx / yum install nginx 就能拿到可用的预编译版本。

wget https://nginx.org/download/nginx-1.25.1.tar.gz

下载链接原稿用的是 http://，改成 https:// 可以避免镜像劫持与签名无法验证的问题；Nginx 官网同时提供 .asc 验签文件，正式环境建议验一次。

2.3 编译

tar -xzvf nginx-1.25.1.tar.gz
cd nginx-1.25.1
./configure
make

./configure 不带参数时用的是保守默认值：没有 HTTPS（http_ssl_module 默认不编）、没有 gzip 静态模块、没有状态页。正式部署几乎一定要显式给选项：

./configure --prefix=/usr/local/nginx \
            --with-http_ssl_module \
            --with-http_gzip_static_module \
            --with-http_stub_status_module \
            --with-stream \
            --with-pcre-jit
make -j"$(nproc)"

--prefix 决定后面所有路径（配置、日志、pid、html）的根；改了这个值，2.4 里的 /usr/local/nginx/... 都要跟着改。--with-stream 是四层代理（TCP/UDP，代理 MySQL、Redis 时用得上），不带它写 stream {} 会报未知指令。另外 ./configure 会生成 objs/Makefile，中途装了依赖就要重跑 configure，直接 make 会报模块缺失。

2.4 安装

安装到默认前缀（--prefix，即 /usr/local/nginx，不是 /usr/local/bin）

make install

产物布局是固定的：/usr/local/nginx/sbin/nginx（可执行文件）、/usr/local/nginx/conf/（配置）、/usr/local/nginx/logs/（access.log、error.log、nginx.pid）、/usr/local/nginx/html/（默认站点）。注意 make install 会直接把 conf/nginx.conf 写进去，升级时它会覆盖你改过的配置（只覆盖同名文件，带 --oldconf-path 可以自己控制），因此线上一般把业务配置拆成 conf.d/*.conf 再用 include 引入。想 systemctl start nginx 得自己写 unit（ExecStart=/usr/local/nginx/sbin/nginx，配 Type=forking 与 PIDFile=/usr/local/nginx/logs/nginx.pid），或干脆用包管理器安装。

3 使用

3.1 复制配置（可选）

cp /usr/local/nginx/conf/nginx.conf /usr/local/nginx/conf/nginx-web.conf

这份拷贝配合 3.4 的 -c 参数使用，作“用一份独立配置跑一个实例”的场景（比如同一个机器上先用默认配置验证安装、再用 nginx-web.conf 跑业务）。但要注意：两个实例各自拥有不同的 pid 文件时会同时在跑，端口会冲突（bind() to 0.0.0.0:8080 failed (98: Address already in use)）；而且后面所有命令（-t、-s reload、-s stop）都必须带同一个 -c，不带就操作到了默认配置那个实例。日常更推荐的做法是只维护一份 nginx.conf + include conf.d/*.conf，用 nginx -T 把最终生效的全部配置打出来确认。

3.2 配置模板

http {
  upstream backend {
    ip_hash;
    server 127.0.0.1:8081;
  }

  server {
    listen 8080;
    server_name localhost;

    location / {
      root       /usr/share/nginx/html/dist;
      try_files  $uri $uri/ /index.html;
      index      index.html index.htm;
    }

    location /prod-api/ {
      proxy_set_header Host $http_host;
      proxy_set_header X-Real-IP $remote_addr;
      proxy_set_header REMOTE-HOST $remote_addr;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      proxy_pass http://backend/;
    }
  }
}

这段是片段而不是完整的 nginx.conf：外层还需要 worker_processes auto; 与 events { worker_connections 1024; }，而 http {} 里的内容才能直接贴进来（注意不要与默认配置里已有的 http {} 嵌套）。几个与路径相关的点：root /usr/share/nginx/html/dist 是包管理器安装的目录，源码安装的默认站点目录是 /usr/local/nginx/html，混用会得到 404 或 open() ... failed (13: Permission denied)（Nginx 以 www-data / nginx 用户跑，要确保该用户对静态目录有读权限）。upstream 只有一台 127.0.0.1:8081 时，ip_hash 没有意义（它用于多后端时把同一客户端 IP 固定到同一台，需要后端有会话状态才用）；要负载均衡就多写几行 server，并用 max_fails/fail_timeout 控制摘除。listen 8080 在源码安装下不带 default_server 会与默认配置的 listen 80 共存，注意默认那个 server {} 没删时，访问 80 端口走的是默认页。

头部四个 proxy_set_header 是把真实客户端信息传给后端：X-Real-IP 与 X-Forwarded-For 用于日志与风控（$proxy_add_x_forwarded_for 会把经手的每一跳都拼上），Host $http_host 保留原始 Host 头（包括端口），影响后端生成的重定向地址与虚拟主机匹配；$host 则不带端口，两者不要弄混。

3.3 配置模板（多项目）

3.3.1 修改前端配置

vite.config.ts 配置添加前缀

export default defineConfig(({ mode, command }: ConfigEnv): UserConfig => {
  const env = loadEnv(mode, process.cwd());
  return {
    // 前缀配置，如 /web1 /web2 /web3
    base: env.VITE_APP_CONTEXT_PATH
  }
})

router/index.js 配置添加前缀

const router = createRouter({
  // 前缀配置，如 /web1 /web2 /web3
  history: createWebHistory(import.meta.env.VITE_APP_CONTEXT_PATH),
});

axios 请求添加前缀

const service = axios.create({
  // 前缀配置，如 /web1/prod-api /web2/prod-api
  baseURL: import.meta.env.VITE_APP_BASE_API,
  timeout: 50000
});

3.3.2 Nginx 配置

http {
  upstream backend {
    ip_hash;
    server 127.0.0.1:8081;
  }

  server {
    listen 8080;
    server_name localhost;

    location / {
      root       /usr/share/nginx/html/dist;
      try_files  $uri $uri/ /index.html;
      index      index.html index.htm;
    }

    location /prod-api/ {
      #...
    }

    location /web1 {
      alias      /usr/share/nginx/html/web1/dist;
      try_files  $uri $uri/ /web1/index.html;
      index      index.html index.htm;

      location /web1/prod-api/ {
        proxy_set_header Host $http_host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header REMOTE-HOST $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_pass http://backend/;
      }
    }

    location /web2 {
      #...
    }

    location /web3 {
      #...
    }
  }
}

嵌套在 location /web1 里的 location /web1/prod-api/ 匹配的是完整 URI（不是剩余部分），所以 proxy_pass http://backend/; 依然会剔掉 /web1/prod-api/ 这段，转到后端的是 /xxx，与单项目模板的行为一致——这也是为什么多个前端项目共用一个后端时，后端接口路径不能再带项目前缀。另一个常见误解：alias 只影响静态文件目录，对 proxy_pass 无效。两个项目都部署到 /web1、/web2 时，location / 里那份 try_files ... /index.html 仍会先匹配非 /webN 开头的请求，如果不需要根路径项目可以把 location / 删掉或改成 location = / { return 302 /web1/; }。

3.4 启动与停止

启动

/usr/local/nginx/sbin/nginx -c /usr/local/nginx/conf/nginx-web.conf

刷新配置

/usr/local/nginx/sbin/nginx -s reload -c /usr/local/nginx/conf/nginx-web.conf

停止

/usr/local/nginx/sbin/nginx -s stop

三条命令都有细节：-s stop 是立即终止（当前连接会被直接断掉，正在传的大文件、长轮询会报错），平滑退出用 -s quit，且带 -c 的那两个实例要同样带上。改配置前永远先 nginx -t（语法与文件路径检查），-t 同带 -c 才是真的在验你要用的那份配置；-s reload 是开新 worker、旧 worker 处理完现有连接后退出，因此改 listen 端口、改 upstream 里的 keepalive 这类不一定能靠 reload 生效，必要时 quit 后重启。日志里 nginx: [emerg] open() ... failed (2: No such file or directory) 通常是 logs/ 目录或 pid 文件不存在。

4 常见问题与修复

4.1 proxy_pass 尾斜杠决定路径怎么拼

原稿只留了一句“proxy_pass 地址后缀的 / 会将拦截的 location 替换成转发后的地址”，实际规则比这复杂一层，而它恰好是前端 404 的第一大原因：

locationproxy_pass请求 /prod-api/user/list 转发结果
/prod-api/http://backend//user/list（把匹配到的 location 部分剔掉）
/prod-api/http://backend/prod-api/user/list（不写 URI 时原样透传）
^~ /prod-api/http://backend/api//api/user/list
~ ^/prod-api/(.*)$http://backend/$1/user/list（正则 location 必须自己捕获并引用）

记忆方式：proxy_pass 中写了路径部分（哪怕是单独的 /）就会做前缀替换；只写到端口/host 就原样透传。还有一点很容易忽略：带变量的 upstream 名字不能用普通前缀替换（proxy_pass http://$var 需要 resolver）。另外替换只剔 location 匹配到的那一段，剩下的部分直接拼到 proxy_pass 的路径后面，所以两边斜杠要配好，否则会出现 //user 这种双斜杠路径。

后端到底该选哪一行，取决于服务本身的 context-path：Spring Boot 设了 server.servlet.context-path=/prod-api 时就不能剔前缀（用不带 / 的写法）；context-path 为空而靠网关/Nginx 做映射时才剔。与 RuoYi-Vue-Plus 框架 配套的默认约定是 VITE_APP_BASE_API=/prod-api 且后端不带 context-path，所以模板里的 proxy_pass http://backend/; 是配套正确的。

4.2 alias 与 location 的斜杠

多项目模板里 location /web1 { alias /usr/share/nginx/html/web1/dist; } 两个值都不以 / 结尾，这在 location /web1 前缀匹配下会把 /web100/index.html 也当命中，然后拼出 /usr/share/nginx/html/web1dist/index.html 这种根本不存在的文件。官方建议两边对称：

location /web1/ {
  alias /usr/share/nginx/html/web1/dist/;
  try_files $uri $uri/ /web1/index.html;
}

还有两个关联问题：alias 与 try_files 一起用时，回退项必须写能被再次匹配的 URI（/web1/index.html）而不是文件路径；而 history 路由模式下回退到 index.html 后，页面里资源的绝对路径又依赖前端的 base，所以 3.3.1 里 VITE_APP_CONTEXT_PATH 必须同时满位两个条件：以 / 开头、以 / 结尾（写成 web1 或 /web1 都会导致刷新后资源 404），且 createWebHistory(import.meta.env.VITE_APP_CONTEXT_PATH) 与 base 用同一个值，否则路由能进但刷新会白屏。

4.3 其他高频问题

# WebSocket：需要 HTTP/1.1 与 Upgrade 头传递
map $http_upgrade $connection_upgrade {
  default upgrade;
  ''      close;
}

location /ws/ {
  proxy_pass http://backend/;
  proxy_http_version 1.1;
  proxy_set_header Upgrade $http_upgrade;
  proxy_set_header Connection $connection_upgrade;
  proxy_read_timeout 3600s;      # 空闲连接被 Nginx 默认 60s 切断
}

location /prod-api/ {
  client_max_body_size 50m;      # 默认 1m，否则大文件上传直接 413
  proxy_connect_timeout 5s;
  proxy_send_timeout 60s;
  proxy_read_timeout 60s;        # 后端慢接口超时报 504
}

location ~* \.(js|css|png|jpg|woff2)$ {
  expires 7d;
  add_header Cache-Control "public, max-age=604800";
}

server_tokens off;                # 不对外泄露 Nginx 版本
client_body_timeout 30s;
keepalive_timeout 65s;
worker_connections 10240;         # 单个 worker 最大连接数，配合系统 ulimit -n

几个口头供快速定位：502 通常是后端没起/端口错/权限不够（SELinux 下反代会被拦）；504 是后端超时，调 proxy_read_timeout 前先确认接口真的需要这么久；413 是 client_max_body_size；404 先查 root/alias 拼出的真实路径（用 nginx -T 配合 error_log 的 [$uri] 看）；前端刷新白屏看 base 与 history 回退；HTTPS 循环重定向看 SLB/Nginx 之间没传 X-Forwarded-Proto，后端生成的跳转地址仍是 http。

5 上线检查清单

项说明
编译模块需要 HTTPS 就必须 --with-http_ssl_module，没编进去后期只能重新编译（不能动态加载）
配置校验改完必跑 nginx -t -c <同一份配置>，再 nginx -T 确认 include 到了预期文件
实例唯一多份 -c 配置容易跑出多个 master 进程，用 `ps -ef
转发路径proxy_pass 尾斜杠与后端 context-path 一致；正则 location 必须自己处理 $1
alias 路径location /web1/ 与 alias .../dist/ 两边斜杠对称；前端 base 以 / 开头结尾
超时与体积client_max_body_size、proxy_read_timeout、proxy_send_timeout 按业务调，不用默认值
WebSocketproxy_http_version 1.1 + Upgrade/Connection，并放宽 proxy_read_timeout
TLSlisten 443 ssl http2、ssl_protocols TLSv1.2 TLSv1.3、ssl_session_cache shared:SSL:10m、证书链完整与到期监控、HTTP→HTTPS 301
日志access log 格式里带上 $request_time 与 $upstream_response_time，排查慢请求靠这两个字段
系统限制worker_rlimit_nofile 与 ulimit -n、net.core.somaxconn，否则高并发下 worker_connections 达不到配置值

6 小结

  • 源码安装的代价是 everything 自己管：模块靠 ./configure（HTTPS 默认不开），升级靠 make 后换二进制 + kill -USR2 平滑升级或 quit+重启，make install 还会覆盖同名配置。
  • proxy_pass 写不写路径部分（包括单独的 /）决定了前缀会不会被剔掉，必须跟后端的 context-path 配合着看。
  • alias 部署多项目时，location 与 alias 两边斜杠要对称，前端 base 要同时以 / 开头结尾，三者一致才能“进入正常 + 刷新不白屏”。
  • -s stop 与 -s quit、-t/-s reload 时带不带 -c，是操作错实例的常见原因。
