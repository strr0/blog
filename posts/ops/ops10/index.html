GitLab CI/CD 自动化部署

strr0 2023-10-25

1 概述

GitLab CI/CD 是 GitLab 自带的持续集成服务，核心由两部分组成：GitLab Runner（执行器，负责真正执行作业）和 .gitlab-ci.yml（作业配置，声明每个阶段做什么）。整条链路可以理解为三段：提交代码触发流水线 → Runner 按 yml 执行作业 → 产物部署到目标机器。

把 .gitlab-ci.yml 添加到仓库根目录，并让 GitLab 项目绑定一个可用的 Runner 后，每次提交或推送都会触发 CI 管道，执行自动化构建与部署。

关于部署位置的两个常识：

  • Runner 不建议装在 GitLab 服务器本身——作业是 CPU/IO 密集型的，会和 GitLab 自身服务抢资源，GitLab 官方也建议分离部署。
  • Runner 装在哪台机器，作业就在这台机器上执行。如果最终要让 docker run 把服务起在目标机上，最简单的方式是把 Runner 直接注册到那台部署机上（用 shell 执行器），这也是本文示例的做法。

两种常用执行器的取舍：

执行器环境隔离适用场景典型坑
shell无，直接用宿主机环境部署机上的简单发布（本文示例）机器上要先装齐 mvn/docker 等工具，PATH 与权限问题多见
docker每个作业一个临时容器构建环境标准化、多语言项目产物随容器销毁，需要 artifacts 传出；操作宿主机 docker 需挂 socket

2 GitLab Runner 部署

2.1 环境需求

  • Linux 主机一台（Runner 与 GitLab 的主版本建议对齐，如 GitLab 15.x 配 Runner 15.x）
  • Docker 环境（仅 docker 类型 runner 需要，安装参考 Docker 安装）

2.2 安装 Runner

2.2.1 添加官方源

curl -L "https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.rpm.sh" | sudo bash

脚本会往 /etc/yum.repos.d/ 写入 GitLab 官方仓库（curl | bash 属于"直接信任上游脚本"的做法，介意的话先下载脚本审查再执行）。Debian/Ubuntu 系把 URL 里的 script.rpm.sh 换成 script.deb.sh。

2.2.2 安装最新版本

yum install gitlab-runner

非 root 用户记得加 sudo。除非有特殊需要，建议保持 Runner 与 GitLab 主版本一致（GitLab 15.x 用 Runner 15.x），跨大版本可能出现 API 不兼容。

2.2.3 安装指定版本

先在浏览器访问 https://<你的gitlab地址>/api/v4/version 查看 GitLab 版本（未登录时该接口可能被禁用，需带管理员 token 访问）。

查看可用 runner 版本

yum list gitlab-runner --showduplicates | sort -r

安装

yum install gitlab-runner-15.11.0-1

2.3 注册 Runner

安装完成的 Runner 只是"装好了软件"，还没和 GitLab 建立关系；注册动作会把连接信息写入 /etc/gitlab-runner/config.toml。注册完可以用 gitlab-runner list 和 gitlab-runner verify 检查状态。

2.3.1 交互模式

运行命令注册

gitlab-runner register

如需代理，运行如下命令注册

export HTTP_PROXY=http://yourproxyurl:3128
export HTTPS_PROXY=http://yourproxyurl:3128

sudo -E gitlab-runner register

-E 不能省：sudo 默认会丢弃当前环境变量，不加 -E 时前面 export 的代理对注册命令不生效。注册过程按提示依次输入：

  • GitLab URL，如 https://gitlab.com（自建实例填自己的域名，注意末尾不要多加 /）
  • 验证 token（项目/组/实例三种级别决定了这个 runner 能被谁使用，入口见本节末尾）
  • Runner 描述名称（后续按 tag 调度、按名称注销时会用到）
  • 执行器类型，如 docker（选 docker 时还会追问默认镜像）

2.3.2 非交互模式

Shell 类型执行器（推荐）

gitlab-runner register \
    --non-interactive \
    --url "https://gitlab.com/" \
    --registration-token "$PROJECT_REGISTRATION_TOKEN" \
    --executor "shell" \
    --shell "bash" \
    --description "shell-executor-runner" \
    --tag-list "shell" \
    --run-untagged="true" \
    --locked="false"

Docker 类型执行器（GitLab 15.10 及以上，注册参数从 --registration-token 换成了 --token）

gitlab-runner register \
    --non-interactive \
    --url "https://gitlab.com/" \
    --token "$RUNNER_TOKEN" \
    --executor "docker" \
    --docker-image alpine:latest \
    --description "docker-runner"

Docker 类型执行器（GitLab 15.10 以下，仍用 --registration-token）。两种 token 的分工：--registration-token 是"项目注册令牌"（一个令牌可注册多个 runner），--token 是在 UI 建好 runner 后生成的专属令牌。这个机制在 16.x 之后仍在持续调整（项目级注册令牌正在被下线），以你的 GitLab 版本注册页面的提示为准——页面会连 token 一起生成完整的 gitlab-runner register 命令，复制执行即可（token 属于敏感信息，注意不要外泄）。

gitlab-runner register \
    --non-interactive \
    --url "https://gitlab.com/" \
    --registration-token "$PROJECT_REGISTRATION_TOKEN" \
    --executor "docker" \
    --docker-image alpine:latest \
    --description "docker-runner" \
    --tag-list "docker,aws" \
    --run-untagged="true" \
    --locked="false"

注册成功后可在 GitLab 项目的 Runner 页面看到新注册的 runner（未配置 tag 时状态显示 unknown，跑过一次作业后变 green）。

token 的位置：Project -> Settings -> CI / CD -> Runners（组与实例级别的入口在各自的 Settings -> CI/CD -> Runners）。

使用 docker 类型执行器时，作业命令都在临时容器里执行，构建结果（如 target/*.jar）默认随容器销毁而消失，需要通过 artifacts 传出，所以"只需要构建产物"的场景适合用它。反过来，如果部署动作就是要在宿主机上 docker run/systemctl，docker 执行器还得把 /var/run/docker.sock 挂进容器（等于把宿主机 root 级权限交给 runner，安全上要评估，参见 Docker 安装 的 5.1 docker 组一节），此时 shell 执行器往往更直接。

2.4 移除 Runner

gitlab-runner unregister --name shell-executor-runner

--name 对应注册时的描述名；如果有多个同名 runner，可改用 --url + --token 精确指定。注意这条命令只清理本地 config.toml，GitLab 服务端页面上的 runner 记录（尤其是 UI 创建 + --token 方式注册的）还要在 UI 里删除才算真正下线。

3 GitLab CI/CD 配置

3.1 环境变量设置

在 Settings -> CI / CD -> Variables 页设置所需要的环境变量，如 APP_NAME（项目名称）、APP_PORT（端口号）、IMAGE_NAME（镜像名称）、IMAGE_VERSION（镜像版本）。

三点建议：

  • 密码、token 这类变量务必勾选 Masked（日志中出现该值时会被打码）与 Protected（仅保护分支可用）；Masked 对值的字符集有要求，生成时避免特殊符号。
  • 类型选 Variable 即可；File 类型会把变量内容写成临时文件、变量名是文件路径，适合传 kubeconfig、私有 settings.xml 这类"文件"。
  • UI 变量与 yml 里的 variables: 同名时，以 UI 配置的优先。

3.2 作业配置

在项目根目录创建 .gitlab-ci.yml

stages:
  - build
  - deploy

variables:
  MAVEN_CLI_OPTS: >-
    -DskipTests

build-job:
  stage: build
  script:
    - mvn $MAVEN_CLI_OPTS package
    - |
      if docker ps -a | grep -q "$APP_NAME"; then
        docker stop "$APP_NAME"
        docker rm "$APP_NAME"
      fi
    - |
      if docker images | grep -q "$IMAGE_NAME"; then
        docker rmi "$IMAGE_NAME:$IMAGE_VERSION"
      fi
    - docker build -t "$IMAGE_NAME:$IMAGE_VERSION" ruoyi-admin
  only:
    refs:
      - master
  except:
    changes:
      - xxx/*

deploy-job:
  stage: deploy
  script:
    - docker run -d --name "$APP_NAME" -p "$APP_PORT:8080" "$IMAGE_NAME:$IMAGE_VERSION"
  only:
    refs:
      - master
  except:
    changes:
      - xxx/*

逐段解释这份配置：

  • stages 定义阶段顺序，先 build 后 deploy；同一阶段内的作业并行。
  • only/except 是老写法：refs: master 表示只有 master 分支触发；except: changes: xxx/* 表示只改了 xxx/ 目录时不触发（xxx/* 是占位符，按项目实际目录改，比如 docs/*）。新语法用 rules:，两者不要混用（同时存在时以 rules 为准）。
  • build-job 里 mvn package 必须在 docker build 之前——示例的 Dockerfile 是 COPY ./target/*.jar 风格，只 build 不 package 会报 COPY failed（同 RuoYi-Vue-Plus 框架 3.1 的坑）。
  • docker ps -a | grep -q "$APP_NAME" 是子串匹配，容器名有包含关系时会误杀（比如 app 会匹配到 app-admin），更稳的写法是 docker ps -aq -f name=^${APP_NAME}$（参考 Docker 安装 的 4.7）。
  • build 和 deploy 两个作业能接力，前提是它们被调度到同一个 Runner、镜像存在同一台机器上；Runner 池里有多台机器时用 tags: 把两个作业锁定到同一个 runner，否则 deploy 会报"镜像不存在"。

3.3 自动化部署

当代码被 push 到 GitLab 时触发流水线，可在项目左侧 CI / CD -> Pipelines 页看到执行结果；点进单个作业能查看每一步脚本的实时输出，排查失败基本都从这里开始。

4 常见问题与修复

4.1 mvn: 未找到命令

shell 执行器的作业由 gitlab-runner 用户以非登录 shell 执行，root 配在 /etc/profile、~/.bashrc 里的 PATH 对它不一定生效；mvn 如果装在别的用户目录下，还会叠加"其他用户无权进入 home"的问题。原稿的处理是把安装目录权限放开：

chmod -R 755 $M2_HOME

更推荐的做法是不依赖 PATH：在 /etc/gitlab-runner/config.toml 对应 [[runners]] 段里加 environment = ["PATH=/opt/maven/bin:/usr/local/bin:/usr/bin:/bin", "JAVA_HOME=..."]，或在 yml 里用绝对路径调用 mvn。如果是 docker 执行器报这个错，原因不同——容器里根本没装 mvn，应改用 image: maven:3.9-eclipse-temurin-17 这类自带构建工具的镜像，放权限没用。

4.2 docker 权限问题

shell 执行器下 gitlab-runner 用户默认无权访问 docker daemon，作业里执行 docker 命令会报连接 /var/run/docker.sock 被拒：

sudo gpasswd -a gitlab-runner docker
newgrp docker

两个容易踩的点：newgrp 只作用于当前这个手工开的 shell，已经在跑的 runner 服务感知不到组变化，必须 sudo systemctl restart gitlab-runner 后才会真正生效（可在作业脚本里加一句 id 验证输出是否包含 docker 组）；而把 runner 加入 docker 组等于给了它宿主机 root 级别的权限（见 Docker 安装 的 5.1），共享实例上要慎重。

4.3 413 Request Entity Too Large

当构建作业失败并出现以下错误时，说明上传的产物超过了 Admin Area 配置的最大产物大小：

Uploading artifacts as "archive" to coordinator... too large archive ...

处理顺序建议是先缩小产物而不是先抬限制：artifacts:paths: 只声明真正需要的文件（比如只要 target/*.jar，不要把整个 target/ 含依赖下载缓存全传了）；确实需要大文件中转时，优先考虑对象存储（如 Linux 环境下 MinIO 的安装与使用）而不是改 GitLab 全局配置。

4.4 artifacts 问题

每个作业都在独立的工作目录里执行，上一个作业产生的文件默认不会带给下一个作业。需要在作业之间传递文件时，用 artifacts 显式声明：

build-job:
  stage: build
  script:
    - mvn $MAVEN_CLI_OPTS package
  artifacts:
    paths:
      - ruoyi-admin/target/*.jar
    expire_in: 1 hr

下游作业执行前，GitLab 会把声明的 artifacts 下载回它自己的工作目录，因此跨 runner 也能传文件（但镜像这种"机器本地资源"传不了，见 3.2 的最后一条）。expire_in 控制保留时长——artifacts 占 GitLab 服务端存储，别留太久。

artifacts 问题的另一个解决思路是尽量不跨作业使用产物，后续作业如需使用上一个作业的产物时，可以选择将两个作业合并，如 mvn 打包项目和 docker 打包镜像整合为一个作业。像本文这种"构建 + 部署在同一台机器"的场景，拆两个作业只是让 stages 语义更清晰，合并也完全没问题。

6 小结

  • GitLab CI/CD = Runner（执行环境）+ .gitlab-ci.yml（作业编排），注册动作把两者连起来，配置落在 /etc/gitlab-runner/config.toml。
  • shell 执行器最直接（部署动作就是宿主机命令），docker 执行器环境干净但产物传出、宿主机访问都要额外处理。
  • “找不到命令/没有权限"类问题的本质，是 runner 用户的执行环境与运维同学的 root shell 不同：PATH、组权限、服务重启三者最容易漏。
  • 作业之间默认互相看不到工作目录，跨作业传文件靠 artifacts，能不跨就不跨。
