树结构工具类封装

strr0 2024-10-01

1 概述

菜单、部门、评论这类树形数据，数据库里通常按邻接表存成扁平结构（每行带一个 parent_id），查询一次就能全部取出，但前端需要的是嵌套 children 的树。于是「扁平列表 → 树」就成了高频工具方法。

本文记录一个泛型工具类的封装方式：先用接口约定「什么对象可以树化」，再给两种建树实现并对比差异。SQL 侧如何取出子树见 MySQL 树形查询。

2 可树化接口

/**
 * 可树化
 */
public interface Treeable<T, K> {
    /**
     * 获取 id
     */
    K getId();

    /**
     * 获取父级 id
     */
    K getParentId();

    /**
     * 获取子节点
     */
    List<T> getChildren();

    /**
     * 设置子节点
     */
    void setChildren(List<T> children);
}

两个泛型参数的含义：T 是节点自身类型（保证 children 元素类型正确），K 是主键类型。实体只要实现这四个方法就能被工具类处理，工具类本身不需要为每种业务实体重写一遍。

3 两种建树实现

3.1 递归查找

public static <T extends Treeable<T, K>, K> List<T> build(List<T> list, K pid) {
    if (list == null || list.isEmpty()) {
        return null;
    }
    List<T> tree = new ArrayList<>();
    list.forEach(item -> {
        if (pid.equals(item.getParentId())) {
            item.setChildren(build(list, item.getId()));
            tree.add(item);
        }
    });
    return tree;
}

思路直白：从虚拟根 pid 出发，每层全表扫一遍找出「父亲是它」的节点，再对每个子节点递归。

代价是每一层递归都要完整遍历一次列表，整体复杂度约 O(n²)（准确说是 O(n × 节点数被扫描的层数)），数据量上千、层级一深就会明显变慢。

3.2 直接建树（推荐）

public static <T extends Treeable<T, K>, K> List<T> build(List<T> list) {
    Map<K, T> itemMap = new HashMap<>();
    List<T> tree = new ArrayList<>();
    list.forEach(item -> {
        T parent = itemMap.get(item.getParentId());
        if (parent != null) {
            List<T> children = parent.getChildren();
            if (children == null) {
                children = new ArrayList<>();
                parent.setChildren(children);
            }
            children.add(item);
        } else {
            tree.add(item);
        }
        itemMap.put(item.getId(), item);
    });
    return tree;
}

用 itemMap 缓存「已经遍历过的节点」，每个节点只处理一次：能找到父亲就挂到父亲的 children 上，找不到就当根节点。整体 O(n)，且不递归，没有栈深度问题。

3.3 对比

维度递归查找直接建树
时间复杂度约 O(n²)O(n)
是否递归是，层级过深有栈溢出风险否
对数据顺序的要求无要求父节点先于子节点出现
根节点判定显式传入的 pid隐式：在已遍历集合中找不到父亲
数据有环时无限递归直至栈溢出成环节点被当作根节点，不崩

3.2 的顺序约束很容易被忽略：如果 SQL 没有 order by parent_id, id（或按层级排序），子节点先于父节点出现时会被误判为根节点，导致树「碎成一排」。稳妥做法是查询时排序，或先做一次全量 put 建索引、第二次遍历再挂载。

4 使用方式

4.1 实体类实现 Treeable 接口

public class SysResourceVo extends SysResource implements Treeable<SysResourceVo, Integer> {
    private List<SysResourceVo> children;

    @Override
    public List<SysResourceVo> getChildren() {
        return children;
    }

    @Override
    public void setChildren(List<SysResourceVo> children) {
        this.children = children;
    }
}

id 与 parentId 已由父类 SysResource 提供 getter，正好满足接口要求，所以只需补 children 字段及其访问方法。

4.2 构建树结构

/**
  * 菜单树
  */
public static List<SysResourceVo> buildMenuTree(List<SysResourceVo> resources) {
    return TreeUtil.build(resources);
}

5 边界问题与改进建议

  • 空列表返回 null：3.1 在入参为空时返回 null，调用方容易 NPE。工具方法建议统一返回空集合（Collections.emptyList()）。
  • pid 为 null 时抛 NPE：3.1 用 pid.equals(...)，根节点 parent_id 为 NULL 时会炸；可改用 Objects.equals(pid, item.getParentId()) 并约定根哨兵值（如 0 / -1）。
  • 原地修改输入：两种实现都会 setChildren 改写传入对象，因此不能对同一批数据重复调用（会重复挂载），也不能在未复制的情况下并发复用。若需保持输入不变，应先深拷贝。
  • 脏数据：parent_id 指向不存在的节点时，3.2 会把它当根输出，表现为「树上少了一层但没报错」，排查时可直接检查孤儿节点。
  • 序列化体积：树结构返回给前端时 children 为空最好置 null 或 []，避免 JSON 中出现大量 "children": null。

6 小结

  • 用 Treeable<T, K> 约定树化能力，工具类只依赖接口，一套代码适配所有实体。
  • 优先使用哈希索引的单遍实现（O(n)），但要保证「父先于子」的顺序，否则退回递归实现或先建索引再挂载。
  • 工具方法应避免返回 null、避免原地改写输入、并对孤儿与环状数据有明确行为。
