Spring 整合 Nacos

strr0 2024-01-11

1 概述

Nacos 是构建云原生应用的动态服务发现、配置管理和服务管理平台，一个进程同时充当三种角色：

  • 注册中心：服务实例上线时注册、下线时摘除，消费方按服务名拿到实例列表；
  • 配置中心：把配置从 jar 里搬到服务端，支持按 namespace / group / dataId 分层与动态刷新；
  • 元数据与治理入口：控制台可查看拓扑、做权重与灰度。

本文覆盖两条链路：Spring Cloud（配置中心 + 服务发现 + RestTemplate 负载均衡）和 Dubbo（以 Nacos 为注册中心）。Dubbo 服务被发现后如何被调用，属于 Spring Cloud 实战 的范畴。

2 快速开始

2.1 MySQL 环境

参考 MySQL 安装。

导入 nacos 数据。Nacos 默认用内嵌 Derby 存储，单机试用可以，多节点集群必须换成 MySQL，否则各节点配置与服务数据不一致。

2.2 Nacos 环境

参考 Nacos 安装。

启动后确认三件事：控制台能登录、命名空间里已建好 dev（注意命名空间 ID 也要填 dev，理由见 3.2）、集群模式下 MySQL 配置已生效。

3 Spring Cloud 接入

3.1 配置中心

引入依赖：

<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-config</artifactId>
</dependency>

application 配置：

spring:
  application:
    # 应用名称
    name: provider-service
  profiles:
    # 环境配置
    active: dev
  cloud:
    nacos:
      # nacos 服务地址
      server-addr: localhost:8848
      config:
        # 配置组
        group: DEFAULT_GROUP
        namespace: ${spring.profiles.active}
  config:
    import:
      - optional:nacos:${spring.application.name}.yml

四个要点：

  • spring.config.import 是新写法：Spring Cloud 2020+ 废弃了 bootstrap.yml 引导机制，改用 import 显式声明外部配置来源，不需要再引 spring-cloud-starter-bootstrap。
  • optional: 前缀是双刃剑：Nacos 不可达时应用仍能启动，但配置会静默缺失。生产环境建议保留 optional:（保证应用能起来），同时给关键配置写默认值并在启动日志里核对。
  • dataId 由 import 决定：这里解析为 provider-service.yml，配合 group=DEFAULT_GROUP、namespace=dev 定位。三者任一不匹配，表现都是「配置读不到但没有任何报错」。
  • namespace 填的是命名空间 ID，不是控制台里显示的名字。ID 与 profile 名不一致时，配置会落到 public 命名空间。

3.2 注册中心及服务发现

3.2.1 服务提供方配置

引入依赖：

<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId>
</dependency>

application 配置：

spring:
  application:
    # 应用名称
    name: provider-service
  profiles:
    # 环境配置
    active: dev
  cloud:
    nacos:
      # nacos 服务地址
      server-addr: localhost:8848
      discovery:
        # 注册组
        group: DEFAULT_GROUP
        namespace: ${spring.profiles.active}

定义服务接口：

@RestController
public class HelloController {
    @GetMapping("/hello")
    public String hello() {
        return "provider:hello!";
    }
}

spring.application.name 就是注册到 Nacos 的服务名，消费方要用它拼 URL，因此不能随意改动。启动成功后应能在控制台服务列表看到实例，看不到就先检查 namespace ID 与 server-addr。

3.2.2 服务消费者配置

引入依赖：

<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId>
</dependency>

<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-loadbalancer</artifactId>
</dependency>

这里需要的是 discovery 而不是 config：消费者要按服务名解析实例地址，靠的是服务发现；同时 Spring Cloud 已用 spring-cloud-starter-loadbalancer 取代了停止维护的 Ribbon。

application 配置：

spring:
  application:
    # 应用名称
    name: consumer-service
  profiles:
    # 环境配置
    active: dev
  cloud:
    nacos:
      # nacos 服务地址
      server-addr: localhost:8848
      discovery:
        # 注册组
        group: DEFAULT_GROUP
        namespace: ${spring.profiles.active}

RestTemplate 配置：

@Configuration
@EnableDiscoveryClient
public class RestTemplateConfig {
    @Bean
    @LoadBalanced
    public RestTemplate restTemplate() {
        return new RestTemplate();
    }
}

@EnableDiscoveryClient 在当前的自动配置体系下已非必需（引入 starter 即完成注册），保留它主要用于显式表达意图。

定义服务客户端：

@Component
public class ProviderClient {
    private final RestTemplate restTemplate;

    public ProviderClient(RestTemplate restTemplate) {
        this.restTemplate = restTemplate;
    }

    public String hello() {
        ResponseEntity<String> exchange = restTemplate.exchange("http://provider-service/hello", HttpMethod.GET, null, String.class);
        return exchange.getBody();
    }
}

URL 的 host 位置写的是服务名而不是域名，这是负载均衡的关键约定：http://服务名/路径。协议头 http:// 不能省，否则会被当作相对地址解析失败。

@LoadBalanced 注解的作用是使 RestTemplate 开启负载均衡功能，在 RestTemplate 的 bean 上添加 @LoadBalanced 注解后，Spring 会为 RestTemplate bean 注册一个 loadBalancedInterceptor 拦截器，这个拦截器可以替换请求地址中的服务逻辑名（即上文中的 provider-service），将其转换为具体的服务地址，实现负载均衡。

需要实例级元数据（如按机房路由）时，除了 @LoadBalanced 还可以注入 LoadBalancerClient 手工选择实例；spring.cloud.loadbalancer.configurations: zone 等开关可以切换内置策略。

4 Dubbo 注册中心及服务发现

4.1 定义基础服务

创建 dubbo 公共服务模块，并定义服务接口：

public interface HelloService {
    String hello();
}

提供方与消费方必须引用同一个接口全限定名，这是 RPC 的隐式契约，把它单独抽成 common 模块可以避免两边各自定义导致不一致。

4.2 服务提供方配置

引入依赖：

<dependency>
    <groupId>org.apache.dubbo</groupId>
    <artifactId>dubbo-spring-boot-starter</artifactId>
    <version>${dubbo-spring-boot.version}</version>
</dependency>

application 配置：

spring:
  application:
    # 应用名称
    name: dubbo-provider-service
  profiles:
    # 环境配置
    active: dev

dubbo:
  application:
    logger: slf4j
    # 关闭qos端口避免单机多生产者端口冲突 如需使用自行开启
    qos-enable: false
    # 元数据中心 local 本地 remote 远程 这里使用远程便于其他服务获取
    metadataType: remote
    # 可选值 interface、instance、all，默认是 all，即接口级地址、应用级地址都注册
    register-mode: instance
    service-discovery:
      # FORCE_INTERFACE，只消费接口级地址，如无地址则报错，单订阅 2.x 地址
      # APPLICATION_FIRST，智能决策接口级/应用级地址，双订阅
      # FORCE_APPLICATION，只消费应用级地址，如无地址则报错，单订阅 3.x 地址
      migration: FORCE_APPLICATION
  protocol:
    # 使用 dubbo 协议通信
    name: dubbo
    # dubbo 协议端口(-1表示自增端口,从20880开始)
    port: -1
  # 注册中心配置
  registry:
    address: nacos://${spring.cloud.nacos.server-addr}
    group: DUBBO_GROUP
    parameters:
      namespace: ${spring.profiles.active}
  scan:
    # 接口实现类扫描
    base-packages: com.strr.provider.dubbo

定义 Dubbo 服务：

@DubboService
public class HelloServiceImpl implements HelloService {
    @Override
    public String hello() {
        return "dubbo-provider:hello!";
    }
}

关键配置逐条说明：

配置作用取值理由
qos-enable: false关闭 QoS 运维端口（默认 22222）单机跑多个 provider 时端口会冲突
metadataType: remote元数据上报到远程元数据中心应用级服务发现下，消费方需要从远端拿到「服务名 → 接口」映射
register-mode: instance只注册应用级实例接口级注册在大规模服务下会造成注册数据爆炸
migration: FORCE_APPLICATION只消费应用级地址与 register-mode: instance 配套；混用 2.x/3.x 时应先用 APPLICATION_FIRST 过渡
protocol.name: dubbo / port: -1走 Dubbo 私有协议，端口从 20880 自增多实例同机部署时避免端口占用
registry.group: DUBBO_GROUPDubbo 在 Nacos 里使用的分组与 Spring Cloud 的 DEFAULT_GROUP 隔离，两类服务互不干扰
scan.base-packages扫描 @DubboService 实现的包不配置则注解不会被暴露

注意 address: nacos://${spring.cloud.nacos.server-addr} 引用的是 Spring Cloud 侧的属性，因此该服务必须同时具备 Nacos 配置（本地写在 application.yml 或由配置中心下发）。若配置来源缺失，占位符无法解析，启动阶段就会报 Could not resolve placeholder。

4.3 服务消费者配置

引入依赖：

<dependency>
    <groupId>org.apache.dubbo</groupId>
    <artifactId>dubbo-spring-boot-starter</artifactId>
    <version>${dubbo-spring-boot.version}</version>
</dependency>

application 配置：

spring:
  application:
    # 应用名称
    name: dubbo-consumer-service
  profiles:
    # 环境配置
    active: dev

dubbo:
  application:
    logger: slf4j
    # 关闭qos端口避免单机多生产者端口冲突 如需使用自行开启
    qos-enable: false
    # 元数据中心 local 本地 remote 远程 这里使用远程便于其他服务获取
    metadataType: remote
    # 可选值 interface、instance、all，默认是 all，即接口级地址、应用级地址都注册
    register-mode: instance
    service-discovery:
      # FORCE_INTERFACE，只消费接口级地址，如无地址则报错，单订阅 2.x 地址
      # APPLICATION_FIRST，智能决策接口级/应用级地址，双订阅
      # FORCE_APPLICATION，只消费应用级地址，如无地址则报错，单订阅 3.x 地址
      migration: FORCE_APPLICATION
  protocol:
    # 使用 dubbo 协议通信
    name: dubbo
    # dubbo 协议端口(-1表示自增端口,从20880开始)
    port: -1
  # 注册中心配置
  registry:
    address: nacos://${spring.cloud.nacos.server-addr}
    group: DUBBO_GROUP
    parameters:
      namespace: ${spring.profiles.active}
  # 消费者相关配置
  consumer:
    # 结果缓存(LRU算法)
    # 会有数据不一致问题 建议在注解局部开启
    cache: false
    # 支持校验注解
    # validation: jvalidationNew
    # 调用重试 不包括第一次 0为不需要重试
    retries: 0
    # 初始化检查
    check: false
    # 超时时间
    timeout: 3000

消费端与提供端必须保持一致的三项是 registry.address、registry.group、parameters.namespace，任一不同都会表现为「看得见服务但没有 provider」。retries: 0 对写接口是必须的——Dubbo 默认重试会让非幂等操作重复执行；check: false 让消费方启动时不强依赖提供方在线，适合本地开发。

定义服务消费者：

@RestController
public class HelloController {
    private static final Logger logger = LoggerFactory.getLogger(HelloController.class);
    @DubboReference
    private HelloService helloService;

    @GetMapping("/hello")
    public String hello() {
        logger.info(helloService.hello());
        return "dubbo-consumer:hello!";
    }
}

@DubboReference 会生成代理注入到字段，调用时走注册中心拿到的地址列表。需要指定版本、分组、超时或负载均衡策略时，都在该注解上按方法粒度覆盖。

4.4 No provider available 排查

服务消费者 No provider available 问题：

  1. 确认服务是否真的注册成功：服务提供方的 application 配置中需指定扫描服务的包路径（dubbo.scan.base-packages），否则 @DubboService 不会被暴露。控制台按 DUBBO_GROUP + namespace 过滤后应能看到对应服务。
  2. 确认接口契约一致：提供方与消费者定义的 HelloService 名称必须一致（类名和包名都一致，可将其定义为一个公共的接口模块）。
  3. 确认 group / namespace / version 三项对齐：Dubbo 在 Nacos 中使用独立分组 DUBBO_GROUP，若消费方用了默认 DEFAULT_GROUP，或命名空间 ID 不一致，就查不到 provider。
  4. 确认服务发现模式兼容：两侧都设成 FORCE_APPLICATION 时，若提供方是 2.x 只注册接口级地址，消费方会拿不到应用级实例，此时应临时改回 APPLICATION_FIRST 双订阅过渡。
  5. 确认 provider 已启动且端口可达：protocol.port: -1 自增出的实际端口要在网络层放行，Dubbo 是长连接直连，注册成功但连不上同样会失败。
  6. 确认序列化白名单：Dubbo 3.2 起默认开启序列化安全检查，自定义 DTO 不在白名单内会被拒绝，报错信息里通常包含 Serialization security 关键字。

5 小结

  • 配置中心用 spring.config.import 显式引入，dataId / group / namespace 三者任一不匹配都是静默失败。
  • namespace 填命名空间 ID，这一条能解决相当一部分「配置不生效」和「No provider」。
  • Spring Cloud 与 Dubbo 共用一个 Nacos，靠 group 隔离（DEFAULT_GROUP 与 DUBBO_GROUP）。
  • Dubbo 3.x 推荐应用级服务发现（register-mode: instance + migration: FORCE_APPLICATION），但混部期要用 APPLICATION_FIRST 平滑过渡。
  • 消费端 retries 与 check 的默认值对业务不友好，应显式声明。
