Spring 整合 RabbitMQ

strr0 2023-09-19

1 概述

RabbitMQ 遵循 AMQP 模型：生产者把消息发给交换机（Exchange），交换机依据绑定关系把消息投递到一个或多个队列，消费者从队列取走并确认。中间多出来的这一层「交换机 + 绑定」，正是它与 Kafka「生产者直接写分区」最大的结构差异——RabbitMQ 的路由规则由交换机类型决定，消息被确认后即从队列删除，不能重放。

四种常用交换模式：

交换机类型路由依据典型用途
Directrouting key 精确相等按业务类型分队列
Fanout忽略 routing key，广播给所有绑定队列缓存失效、事件通知
Topicrouting key 与 # / * 通配模式匹配按层级维度订阅（订单.创建.*）
Headers按消息头键值匹配，忽略 routing key多条件组合过滤

2 环境配置

服务端部署参考 消息队列安装，本文假设 localhost:5672 已可用，账号 user。

3 依赖与应用配置

3.1 引入依赖

<dependency>
    <groupId>org.springframework.amqp</groupId>
    <artifactId>spring-rabbit</artifactId>
    <version>${amqp.version}</version>
</dependency>

<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-messaging</artifactId>
</dependency>

spring-messaging 由 spring-rabbit 传递引入，@RabbitListener 的消息抽象依赖它；单独声明是为了固定版本，不需要额外写 <version> 时应交给 BOM 管理。

3.2 application 配置

spring:
  rabbitmq:
    host: localhost
    port: 5672
    username: user
    password: password

5672 是 AMQP 协议端口，管理控制台用的是 15672，两者不要混用。

4 四种交换模式

下文四个小节里的 ProducerService 是同名的不同版本，只是为了让每种模式都能独立完整地复制运行。实际落到同一个工程时应合并成一个类，否则会出现 Bean 名称冲突。

4.1 直连模式（Direct）

队列及交换机配置：

@Configuration
public class RabbitDirectConfig {
    public final static String DIRECTNAME = "strr-direct";

    @Bean
    protected Queue queue() {
        return new Queue("hello-queue");
    }

    @Bean
    protected DirectExchange directExchange() {
        return new DirectExchange(DIRECTNAME, true, false);
    }

    @Bean
    protected Binding binding() {
        return BindingBuilder.bind(queue()).to(directExchange()).with("direct");
    }
}
  • new Queue("hello-queue") 使用的是默认构造：持久化、非独占、不自动删除。交换机与队列只有在声明时才会真正建立，光在配置文件里写名字无效。
  • new DirectExchange(DIRECTNAME, true, false) 两个布尔值是 durable 与 autoDelete。
  • Binding 把队列绑到交换机上，绑定时用的 routing key 是 "direct"。

生产者配置：

@Service
public class ProducerService {
    @Autowired
    private RabbitTemplate rabbitTemplate;

    public void sendDirect(String key, String what) {
        rabbitTemplate.convertAndSend(key, new Foo(what));
    }
}

消费者配置：

@Service
public class DirectConsumerService {
    @RabbitListener(queues = "hello-queue")
    public void listen(Foo foo) {
        // TODO
    }
}

测试：

@SpringBootTest
class ApplicationTests {
    @Autowired
    private ProducerService producerService;

    @Test
    void sendDirectTest() {
        producerService.sendDirect("hello-queue", "hello world!");
    }
}

这里的路由并没有经过上面声明的 strr-direct 交换机。 convertAndSend(routingKey, object) 这个两参重载等价于「交换机名传空字符串」，而空字符串指的是 broker 内置的默认交换机，它按「routing key 等于队列名」直接投递，所以传的是 "hello-queue"。要验证自建 Direct 交换机，必须用三参版本并传绑定时的 key：

rabbitTemplate.convertAndSend(RabbitDirectConfig.DIRECTNAME, "direct", new Foo(what));

两种写法都能收到消息，但排障思路完全不同——前者只看队列名，后者要看交换机与绑定是否匹配。

4.2 广播模式（Fanout）

队列及交换机配置：

@Configuration
public class RabbitFanoutConfig {
    public final static String FANOUTNAME = "strr-fanout";

    @Bean
    protected FanoutExchange fanoutExchange() {
        return new FanoutExchange(FANOUTNAME, true, false);
    }

    @Bean
    protected Queue queueOne() {
        return new Queue("queue-one");
    }

    @Bean
    protected Queue queueTwo() {
        return new Queue("queue-two");
    }

    @Bean
    protected Binding bindingOne() {
        return BindingBuilder.bind(queueOne()).to(fanoutExchange());
    }

    @Bean
    protected Binding bindingTwo() {
        return BindingBuilder.bind(queueTwo()).to(fanoutExchange());
    }
}

Fanout 的绑定不带 routing key，消息到达即复制给所有绑定队列。性能上也通常是四种模式里最快的，因为无需匹配规则。

生产者配置：

@Service
public class ProducerService {
    @Autowired
    private RabbitTemplate rabbitTemplate;

    public void sendFanout(String what) {
        rabbitTemplate.convertAndSend(RabbitFanoutConfig.FANOUTNAME, null, new Foo(what));
    }
}

消费者配置：

@Service
public class FanoutConsumerService {
    @RabbitListener(queues = "queue-one")
    public void listen1(Foo foo) {
        // TODO
    }

    @RabbitListener(queues = "queue-two")
    public void listen2(Foo foo) {
        // TODO
    }
}

测试：

@SpringBootTest
class ApplicationTests {
    @Autowired
    private ProducerService producerService;

    @Test
    void sendFanoutTest() {
        producerService.sendFanout("hello fanout!");
    }
}

两个队列都会各收到一份。这带来一个隐含约定：同一个队列的多个消费者是竞争消费（分流），不同队列之间才是广播（各得一份）。想让两个服务都收到通知，就必须各自拥有独立队列并都绑到同一个 Fanout 交换机上。

4.3 Topic 模式（根据路由 key 模糊匹配）

队列及交换机配置：

@Configuration
public class RabbitTopicConfig {
    public final static String TOPICNAME = "strr-topic";

    @Bean
    protected TopicExchange topicExchange() {
        return new TopicExchange(TOPICNAME, true, false);
    }

    @Bean
    protected Queue queue1() {
        return new Queue("topic1-queue");
    }

    @Bean
    protected Queue queue2() {
        return new Queue("topic2-queue");
    }

    @Bean
    protected Queue queue3() {
        return new Queue("topic3-queue");
    }

    @Bean
    protected Binding queue1Binding() {
        return BindingBuilder.bind(queue1()).to(topicExchange())
                .with("topic1.#");
    }

    @Bean
    protected Binding queue2Binding() {
        return BindingBuilder.bind(queue2()).to(topicExchange())
                .with("topic2.#");
    }

    @Bean
    protected Binding queue3Binding() {
        return BindingBuilder.bind(queue3()).to(topicExchange())
                .with("topic3.#");
    }
}

routing key 以 . 分段，两个通配符的差别是：* 匹配恰好一段，# 匹配零或多段。所以 topic1.# 既能收 topic1.aa，也能收 topic1 和 topic1.aa.bb；若写成 topic1.* 则只匹配 topic1.aa 这一段的情况。

生产者配置：

@Service
public class ProducerService {
    @Autowired
    private RabbitTemplate rabbitTemplate;

    public void sendTopic(String key, String what) {
        rabbitTemplate.convertAndSend(RabbitTopicConfig.TOPICNAME, key, new Foo(what));
    }
}

消费者配置：

@Service
public class TopicConsumerService {
    @RabbitListener(queues = "topic1-queue")
    public void listen1(Foo foo) {
        // TODO
    }

    @RabbitListener(queues = "topic2-queue")
    public void listen2(Foo foo) {
        // TODO
    }

    @RabbitListener(queues = "topic3-queue")
    public void listen3(Foo foo) {
        // TODO
    }
}

测试：

@SpringBootTest
class ApplicationTests {
    @Autowired
    private ProducerService producerService;

    @Test
    void sendTopicTest() {
        producerService.sendTopic("topic1.aa", "hello topic1!");
        producerService.sendTopic("topic2.bb", "hello topic2!");
        producerService.sendTopic("topic3.cc", "hello topic3!");
    }
}

三个 key 各自命中同前缀的队列。如果传一个 topic4.dd，消息会因为无队列匹配而被静默丢弃——这是 Topic 模式最隐蔽的问题，解决办法见 6.3 的备用交换机。

4.4 Header 模式（根据 header 匹配）

队列及交换机配置：

@Configuration
public class RabbitHeaderConfig {
    public final static String HEADERNAME = "strr-header";

    @Bean
    protected HeadersExchange headersExchange() {
        return new HeadersExchange(HEADERNAME, true, false);
    }

    @Bean
    protected Queue queueName() {
        return new Queue("name-queue");
    }

    @Bean
    protected Queue queueAge() {
        return new Queue("age-queue");
    }

    @Bean
    protected Binding bindingName() {
        Map<String, Object> map = new HashMap<>();
        map.put("name", "strr");
        return BindingBuilder.bind(queueName())
                .to(headersExchange()).whereAny(map).match();
    }

    @Bean
    protected Binding bindingAge() {
        return BindingBuilder.bind(queueAge())
                .to(headersExchange()).where("age").exists();
    }
}

三种匹配语义要分清：whereAny(map) 是「任一键值命中即可」，whereAll(map) 是「全部键值都要命中」，where("age").exists() 只要求该头存在、不校验取值。

生产者配置：

@Service
public class ProducerService {
    @Autowired
    private RabbitTemplate rabbitTemplate;

    public void sendHeader(Message message) {
        rabbitTemplate.convertAndSend(RabbitHeaderConfig.HEADERNAME, null, message);
    }
}

消费者配置：

@Service
public class HeaderConsumerService {
    @RabbitListener(queues = "name-queue")
    public void handler1(byte[] msg) {
        // TODO
    }

    @RabbitListener(queues = "age-queue")
    public void handler2(byte[] msg) {
        // TODO
    }
}

入参是 byte[] 而不是 Foo：这一节的发送端直接把手工构造的 Message 交出去，body 是原始字节，没有 JSON 转换器参与，所以消费端也只能按字节接收。

测试：

@SpringBootTest
class ApplicationTests {
    @Autowired
    private ProducerService producerService;

    @Test
    void sendHeaderTest() {
        Message nameMsg = MessageBuilder.withBody("hello header! name-queue".getBytes())
                .setHeader("name", "strr").build();
        Message ageMsg = MessageBuilder.withBody("hello header! age-queue".getBytes())
                .setHeader("age", "99").build();
        producerService.sendHeader(nameMsg);
        producerService.sendHeader(ageMsg);
    }
}

name 与 age 两个头分别命中两条队列。注意 routing key 传 null 是有意为之，Headers 交换机会完全忽略它。

5 序列化与反序列化白名单

5.1 问题与修复

java.lang.SecurityException: Attempt to deserialize unauthorized class xxx

Spring AMQP 从 2.4.8 / 2.5 起默认拒绝按消息头 __TypeId__ 反序列化任意类（历史上这里出过远程代码执行漏洞），因此当生产端用 Jackson2JsonMessageConverter 发送对象、消费端要还原成自定义类时，必须显式声明可信包。

在生产者定义转换器：

@Configuration
public class RabbitmqConfig {
    @Bean
    public MessageConverter messageConverter() {
        DefaultClassMapper classMapper = new DefaultClassMapper();
        classMapper.setTrustedPackages("com.example");    // 替换为 xxx 实际包名
        Jackson2JsonMessageConverter jsonConverter = new Jackson2JsonMessageConverter();
        jsonConverter.setClassMapper(classMapper);
        return jsonConverter;
    }
}

在消费者定义转换器：

@Configuration
public class RabbitmqConfig {
    @Bean
    public MessageConverter messageConverter() {
        return new Jackson2JsonMessageConverter();
    }
}

两端配置不同的原因在于职责不同：生产端要把「对象 → JSON + 类型头」写出去，需要控制写入哪个类型头以及是否允许；消费端只要有 Jackson2JsonMessageConverter，就能依据 @RabbitListener 方法的参数类型完成反序列化，不再依赖类型头，因此天然规避了白名单限制——这也是 Spring 整合 Kafka 里用 ByteArrayDeserializer 的同一个思路。

如果 @Bean 返回类型直接写成 MessageConverter，容器里同时存在多个候选时可能注入歧义，建议保留具体类型 Jackson2JsonMessageConverter 或使用 @Primary。

6 可靠性配置

6.1 持久化要三处齐备

队列声明为 durable（本文所有交换机与队列都是 true, false）只保证元数据在重启后存在。消息不丢还需要：

  • 消息投递模式为持久（Spring AMQP 默认 deliveryMode=PERSISTENT）；
  • 发送端确认（spring.rabbitmq.publisher-confirm-type: correlated + publisher-returns: true），否则「broker 收到」和「消息进队」这两步都是黑盒；
  • 消费端手动确认（见 6.2）。

三者缺一，重启或异常时就会丢。

6.2 手动 ack 与预取

spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: manual
        prefetch: 10

默认是 auto：监听方法正常返回即自动确认，抛异常则重新入队（可能造成死循环重试）。改成 manual 后需要在方法里拿 Channel 显式 basicAck / basicNack，并务必处理「确认动作本身失败」的情况。prefetch 控制单消费者一次预取多少条未确认消息，不设限会让消息全堆在某个慢消费者本地。

6.3 重试与死信

重试只该用于「有希望成功」的异常（网络抖动、下游超时）；反序列化失败、参数非法这类确定性错误重试一万次也没用，应直接进死信队列。

@Bean
public Queue helloQueue() {
    return QueueBuilder.durable("hello-queue")
            .deadLetterExchange("strr-dlx")
            .deadLetterRoutingKey("dead.hello")
            .build();
}

配合 spring.rabbitmq.listener.simple.retry.max-attempts 控制次数，超过后由 RepublishMessageRecoverer 或 broker 侧 DLX 投递到死信队列，再由独立的告警消费者处理。另外无匹配队列而丢失的消息，可以给交换机配 alternate 备用交换机兜住。

6.4 幂等

RabbitMQ 提供的是 at-least-once，重复投递是常态。消费端必须有幂等保障：唯一业务键去重、状态机校验（只接受合法迁移），或先写去重表再执行业务。

7 小结

  • 四种交换机的差别只在路由依据，队列才是消息的归宿；竞争消费发生在同一队列内部，跨队列才是广播。
  • 两参的 convertAndSend 走默认交换机，测试自建交换机时要用三参版本，否则结果一样但验证的不是同一条链路。
  • 反序列化白名单是安全默认值，不是 bug；消费端靠方法参数类型反序列化可以同时绕开类型头依赖。
  • 「消息不丢」是队列持久化 + 消息持久 + confirm + 手动 ack 四件事的合称，缺一即不可靠。
