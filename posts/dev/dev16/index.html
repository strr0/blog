Spring 整合 OAuth 2.0

strr0 2024-12-21

1 概述

OAuth 2.0 是一个开放授权标准：资源拥有者不必把账号密码交给第三方应用，而是由授权服务器签发一枚权限有限、时效有限的访问令牌（access token），第三方拿令牌去访问资源服务器。「不接触凭据、权限可收敛、时效可控」三点合起来，就是它相比「把你的密码抄给我」的本质改进。

本文按「协议本身 → 两代 Spring 实现」组织：

章节内容现状
第 2 节角色、授权模式与流程图与实现无关，来自 RFC 6749
3.1spring-security-oauth2（@EnableAuthorizationServer）已停止维护，仅作存量项目参考
3.2Spring Authorization Server（spring-security-oauth2-authorization-server）官方推荐，并自行扩展出密码模式
第 4 节上线检查清单—

2 基础知识

2.1 四种角色

  • Resource Owner —— 资源拥有者，通常就是终端用户
  • Resource Server —— 资源服务器，持有受保护数据，只认令牌
  • Client —— 客户端，想访问资源的第三方应用
  • Authorization Server —— 授权服务器，负责认证用户、签发与校验令牌

落到一个具体场景（「某网站用 GitHub 账号登录」）：

角色对应到实际系统
Resource Owner你（GitHub 用户）
Client那个第三方网站
Authorization ServerGitHub 的 OAuth 授权服务
Resource ServerGitHub API（api.github.com）

分工的关键在于资源服务器只与授权服务器约定「怎么验令牌」，完全不参与用户认证。所以业务系统只需回答三个问题：这张令牌是不是我信任的授权服务器签发的、有没有过期、scope 够不够。

2.2 四种授权模式

四种模式的差别只在「用户如何把授权意愿传达给授权服务器」以及「客户端如何换到令牌」，拿到 access token 之后的访问方式完全一致：

模式客户端是否接触密码令牌怎么到手适用
授权码否后端用 code 换取有服务端的 Web 应用，首选
隐式否直接出现在 URL 片段早期纯前端 SPA，已不推荐
密码是直接提交用户名密码自家应用 / 遗留系统过渡
客户端无关用自己的凭据无用户参与的机器对机器调用

2.2.1 授权码模式（Authorization Code）

授权流程如下（图中 User-Agent 即浏览器）

     +----------+
     | Resource |
     |   Owner  |
     |          |
     +----------+
          ^
          |
         (B)
     +----|-----+          Client Identifier      +---------------+
     |         -+----(A)-- & Redirection URI ---->|               |
     |  User-   |                                 | Authorization |
     |  Agent  -+----(B)-- User authenticates --->|     Server    |
     |          |                                 |               |
     |         -+----(C)-- Authorization Code ---<|               |
     +-|----|---+                                 +---------------+
       |    |                                         ^      v
      (A)  (C)                                        |      |
       |    |                                         |      |
       ^    v                                         |      |
     +---------+                                      |      |
     |         |>---(D)-- Authorization Code ---------'      |
     |  Client |          & Redirection URI                  |
     |         |                                             |
     |         |<---(E)----- Access Token -------------------'
     +---------+       (w/ Optional Refresh Token)

(A) 客户端通过资源拥有者的用户代理将客户端标识和重定向地址发送到授权服务器

(B) 授权服务器认证资源拥有者（用户代理）和是否同意授权

(C) 获得资源拥有者同意后，授权服务器重定向用户代理到目标地址，并带上 code

(D) 客户端将 code 及重定向地址发送到授权服务器请求 access_token

(E) 授权服务器返回 access_token 到客户端

授权码是唯一把「前端通道」和「后端通道」切开的模式：code 走浏览器（暴露在地址栏，但生命周期只有几分钟且一次性），token 走客户端后端直连授权服务器（不经过浏览器）。即便 code 泄露，没有客户端凭据也换不到 token，这就是它安全性最高的原因。

两个必须同时启用的参数：

  • PKCE（S256）：授权码可能被恶意 App 截获（自定义 URL Scheme 回调），客户端在 (A) 附带 code_challenge，在 (D) 附带 code_verifier，截获到 code 也换不到 token。OAuth 2.1 草案把它列为必选，移动端与 SPA 应当默认启用。
  • state：(A) 生成随机值，(C) 回来时比对，用于防 CSRF；redirect_uri 必须在授权服务器上精确匹配白名单，不能做前缀匹配。

2.2.2 隐式模式（Implicit）

授权流程如下

     +----------+
     | Resource |
     |  Owner   |
     |          |
     +----------+
          ^
          |
         (B)
     +----|-----+          Client Identifier     +---------------+
     |         -+----(A)-- & Redirection URI --->|               |
     |  User-   |                                | Authorization |
     |  Agent  -|----(B)-- User authenticates -->|     Server    |
     |          |                                |               |
     |          |<---(C)--- Redirection URI ----<|               |
     |          |          with Access Token     +---------------+
     |          |            in Fragment
     |          |                                +---------------+
     |          |----(D)--- Redirection URI ---->|   Web-Hosted  |
     |          |          without Fragment      |     Client    |
     |          |                                |    Resource   |
     |     (F)  |<---(E)------- Script ---------<|               |
     |          |                                +---------------+
     +-|--------+
       |    |
      (A)  (G) Access Token
       |    |
       ^    v
     +---------+
     |         |
     |  Client |
     |         |
     +---------+

(A) 客户端通过资源拥有者的用户代理将客户端标识和重定向地址发送到授权服务器

(B) 授权服务器认证资源拥有者（用户代理）和是否同意授权

(C) 获得资源拥有者同意后，授权服务器重定向用户代理到目标地址（url 片段附带 access_token）

(D) 用户代理发送请求到资源服务器（不包含上述片段）

(E) 资源服务器返回一个带嵌入式脚本的页面（脚本能提取片段中的 access_token）

(F) 用户代理执行脚本提取 access_token

(G) 用户代理返回 access_token 到客户端

隐式模式存在的原因是「纯浏览器应用没有后端，藏不住 client_secret，也无法完成 (D)(E) 这次后端换票」。代价是 access_token 直接出现在 URL 片段里：它会留在浏览器历史中、被页面内任意脚本读取，而且没有 refresh token，过期只能让用户重新走一遍授权。今天的替代方案是 SPA 也走授权码 + PKCE（公开客户端把客户端认证方法设为 ClientAuthenticationMethod.NONE），隐式模式在 OAuth 2.1 草案中已被删除。

2.2.3 密码模式（Resource Owner Password Credentials）

授权流程如下

     +----------+
     | Resource |
     |  Owner   |
     |          |
     +----------+
          v
          |    Resource Owner
         (A) Password Credentials
          |
          v
     +---------+                                  +---------------+
     |         |>--(B)---- Resource Owner ------->|               |
     |         |         Password Credentials     | Authorization |
     | Client  |                                  |     Server    |
     |         |<--(C)---- Access Token ---------<|               |
     |         |    (w/ Optional Refresh Token)   |               |
     +---------+                                  +---------------+

(A) 资源拥有者向客户端提供用户名密码

(B) 客户端将从资源拥有者得到的认证信息发送到授权服务器请求 access_token

(C) 授权服务器校验认证信息，校验通过返回 access_token

密码模式只省去了一次浏览器跳转，并没有省掉风险：用户把明文密码交给了客户端，客户端因此可以冒充用户做任何 scope 允许的事，也无法启用 MFA、验证码与第三方 consent 页面。它只在两种情况下可接受——客户端与授权服务器同属一家（自家 App），或从旧的 Basic 认证迁移过来时作为过渡。OAuth 2.1 草案已经移除它，Spring Authorization Server 也从一开始就不提供内置实现，这正是 3.2.2 要自己写三件套的原因。

2.2.4 客户端模式（Client Credentials）

授权流程如下

     +---------+                                  +---------------+
     |         |                                  |               |
     |         |>--(A)- Client Authentication --->| Authorization |
     | Client  |                                  |     Server    |
     |         |<--(B)---- Access Token ---------<|               |
     |         |                                  |               |
     +---------+                                  +---------------+

(A) 客户端将客户端的认证信息发送到授权服务器请求 access_token

(B) 授权服务器校验认证信息，校验通过返回 access_token

客户端模式没有资源拥有者参与，客户端以自己的身份取令牌，拿到的权限是「这个应用能看到的范围」而不是「某个用户授权的范围」。定时任务、服务间调用、对接开放平台属于它的典型场景。由于凭据在每次换票时都要用，client_secret 必须只存在于服务端配置或密钥系统中，绝不能打包进前端或客户端安装包。

2.3 令牌的两种形态

上面四种模式解决的是「怎么拿到令牌」，而「令牌长什么样」是一个独立的维度，它直接决定了后面的验签、注销与扩容方案：

形态内容资源端怎么验能否主动失效
JWT（自包含）header.payload.signature，权限与用户信息写在 payload 里本地用公钥验签，无需回源默认不能，需额外黑名单
Opaque（引用令牌）一串无意义随机字符，服务端存着它的元数据必须调 introspection 接口或查共享存储能，删记录即失效

本文两个实现都选 JWT，所以第 3 节里反复出现的「无法主动注销」「重启后验签失败」等问题，根源都在这张表里。

3.1.2 配置

四个配置类各司其职：WebSecurityConfig 管「谁能登录」，AuthorizationServerConfig 管「允许哪些客户端、用哪几种模式、怎么换票」，JwtConfig 管「令牌长什么样、怎么签发与解析」，ResourceServerConfig 管「哪些接口需要什么角色」。

Security 配置

@Configuration
public class WebSecurityConfig extends WebSecurityConfigurerAdapter {
    @Bean
    @Override
    public AuthenticationManager authenticationManagerBean() throws Exception {
        return super.authenticationManagerBean();
    }

    @Override
    protected void configure(AuthenticationManagerBuilder auth) throws Exception {
        auth.inMemoryAuthentication()
            .withUser("user").password("password").roles("USER")
            .and()
            .withUser("admin").password("password").roles("USER", "ADMIN");
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return NoOpPasswordEncoder.getInstance();
    }
}

这段里 passwordEncoder() Bean 与 auth.inMemoryAuthentication().password("password") 并不作用在同一条链上：configure(AuthenticationManagerBuilder auth) 显式构建的构建器默认用 PasswordEncoderFactories 产生的 DelegatingPasswordEncoder，它按 {id}rawPassword 前缀分派，遇到裸明文会报 There is no PasswordEncoder mapped for the id "null"。两种改法任选其一：.password("{noop}password")，或 auth.inMemoryAuthentication().passwordEncoder(NoOpPasswordEncoder.getInstance())。下面 withClient("client").secret("secret") 走的是授权服务器另一套编码器，同理需要 {noop} 前缀或显式配置 AuthorizationServerSecurityConfigurer#passwordEncoder。明文只适合演示，生产必须换 BCryptPasswordEncoder。

授权服务器配置

@Configuration
@EnableAuthorizationServer
public class AuthorizationServerConfig extends AuthorizationServerConfigurerAdapter {
    //...

    @Override
    public void configure(ClientDetailsServiceConfigurer clients) throws Exception {
        clients.inMemory()
            .withClient("client")
            .secret("secret")
            .authorizedGrantTypes("password", "refresh_token")
            .scopes("read", "write");
    }

    @Override
    public void configure(AuthorizationServerEndpointsConfigurer endpoints) throws Exception {
        TokenEnhancerChain tokenEnhancerChain = new TokenEnhancerChain();
        tokenEnhancerChain.setTokenEnhancers(Arrays.asList(jwtTokenEnhancer, jwtAccessTokenConverter));
        endpoints.tokenStore(tokenStore)
                .accessTokenConverter(jwtAccessTokenConverter)
                .tokenEnhancer(tokenEnhancerChain)
                .authenticationManager(authenticationManager);
    }
}

三个容易看漏的点：

  • authorizedGrantTypes("password", "refresh_token") 里两个值都要写。声明 password 只允许走密码换票；refresh_token 是一项独立的授权类型，不写它，即使 DefaultTokenServices 打开了 setSupportRefreshToken(true)，刷新请求仍会被拒。
  • authenticationManager(authenticationManager) 是密码模式专属。授权码模式靠浏览器里的登录态，不需要程序化校验用户名密码；只有密码模式要拿上面 WebSecurityConfig 暴露的 AuthenticationManager 去验账号。
  • TokenEnhancerChain 的顺序不可颠倒：jwtTokenEnhancer 往令牌里塞附加 claim，jwtAccessTokenConverter 负责把整个令牌序列化成 JWT 并签名。converter 必须放最后，否则增强器写入的字段不会被编进最终的 JWT，接口返回的 payload 里就少了 username。

令牌配置

@Configuration
public class JwtConfig {
    // jwt 令牌转换
    @Bean
    public JwtAccessTokenConverter getJwtAccessTokenConverter() {
        JwtAccessTokenConverter converter = new JwtAccessTokenConverter();
        converter.setSigningKey("secret");
        return converter;
    }

    // jwt 令牌增强
    @Bean
    public TokenEnhancer getJwtTokenEnhancer() {
        return (token, authentication) -> {
            Map<String, Object> additionalInfo = new HashMap<>();
            additionalInfo.put("username", authentication.getPrincipal());
            ((DefaultOAuth2AccessToken) token).setAdditionalInformation(additionalInfo);
            return token;
        };
    }

    @Bean
    public TokenStore getTokenStore(JwtAccessTokenConverter converter) {
        return new JwtTokenStore(converter);
    }

    @Bean
    public DefaultTokenServices getTokenService(TokenStore tokenStore) {
        DefaultTokenServices tokenServices = new DefaultTokenServices();
        tokenServices.setTokenStore(tokenStore);
        tokenServices.setSupportRefreshToken(true);
        return tokenServices;
    }
}

JwtTokenStore 名字里有 Store，实际什么都不存——它只做「把 OAuth2AccessToken 转成 JWT 字符串」和「把 JWT 解回来」两件事，令牌的全部状态都编码在签名过的 payload 里。这带来两个直接后果：

  • 授权服务器重启、扩容都不用共享会话存储，天然水平扩展；
  • 但服务端无法主动让一张未过期的令牌失效，退出登录、封号、改密码都不能立即切断访问。

想保留 JWT 又要有撤销能力，常见做法是把有效期压短（几分钟到半小时）并配合 refresh token 轮换，或者加一张以 jti 为键的 Redis 黑名单；也可以把 JwtTokenStore 换成 RedisTokenStore，代价是每次请求多一次 Redis 查询。另外，签名密钥写死为 "secret" 意味着任何拿到这个字符串的人都能自行签发令牌，且对称密钥必须分发给每一个需要验签的服务；多节点部署应改用 RSA（KeyPair），并把公钥通过 /oauth/token_key 暴露给资源端。

资源服务器配置

@Configuration
@EnableResourceServer
public class ResourceServerConfig extends ResourceServerConfigurerAdapter {
    @Override
    public void configure(HttpSecurity http) throws Exception {
        http.authorizeRequests()
            .antMatchers("/hello").hasAnyRole("USER")
            .anyRequest().authenticated();
    }
}

hasAnyRole("USER") 比对时会自动补 ROLE_ 前缀，对应 WebSecurityConfig 里 roles("USER") 生成的 ROLE_USER；若想直接写全权限名，要用 hasAnyAuthority()。authorizeRequests() 与 antMatchers() 在 Security 5.8 起被 authorizeHttpRequests() / requestMatchers() 取代，新版写法见 3.2.3。资源端与授权端拆成两个服务时，这里还需要额外提供 ResourceServerTokenServices（共享 TokenStore Bean，或用 RestTemplate 调 /oauth/check_token），共部一个进程则直接复用上面的 Bean。

3.2 Spring Authorization Server 版本（新，官方推荐）

Spring Authorization Server 是按 OAuth 2.1 / OIDC 1.0 最终规范重写的实现，不再提供 @EnableAuthorizationServer 这种一锅端注解，而是把每个端点、每种授权类型、每个扩展点都拆成显式 Bean。代价是配置代码量大很多，好处是所有行为都能在代码里检索到。

与旧版的概念对照：

旧版（spring-security-oauth2）新版（Authorization Server）说明
@EnableAuthorizationServerOAuth2AuthorizationServerConfigurer由注解开关改为 DSL 配置
ClientDetails / ClientDetailsServiceRegisteredClient / RegisteredClientRepository客户端注册信息
AuthorizationServerTokenServices / DefaultTokenServicesOAuth2AuthorizationService授权记录（含 code、各类型 token）的存取
TokenStore + JwtAccessTokenConverterOAuth2TokenGenerator + JwtEncoder + JWKSource签发与编解码拆成三个组件
TokenEnhancerOAuth2TokenCustomizer<JwtEncodingContext>往 payload 里加自定义 claim
/oauth/token/oauth2/token端点路径默认不兼容

它内置支持的只有授权码（含 PKCE）、客户端凭据与刷新令牌，后续版本又补上了设备码与 token exchange，没有密码模式与隐式模式。所以下面先自己实现一遍密码模式。

3.2.1 依赖

<dependency>
    <groupId>org.springframework.security</groupId>
    <artifactId>spring-security-oauth2-authorization-server</artifactId>
    <version>1.0.0</version>
</dependency>

3.2.2 扩展密码模式

密码模式在新版里要自己接三件套，顺序是「解析请求 → 构造认证对象 → 校验并签发令牌」：

组件实现的接口职责注册位置
OAuth2ResourceOwnerAuthenticationToken继承 AbstractAuthenticationToken承载 username / password / scope 的中间认证对象无需注册
OAuth2ResourceOwnerAuthenticationConverterAuthenticationConverter从 token 请求里读参数，grant_type 不是 password 就返回 null 放行给下一个tokenEndpoint.accessTokenRequestConverters(...)
OAuth2ResourceOwnerAuthenticationProviderAuthenticationProvider校验客户端许可、验账号、校 scope，签发 access/refresh/id token 并落库tokenEndpoint.authenticationProviders(...)

三处缺一处的报错症状完全不同，可以直接据此定位：converter 没注册 → unsupported_grant_type；provider 没注册 → 同样报 unsupported_grant_type（没有任何 provider 支持这个认证类型）；RegisteredClient 里没加 AuthorizationGrantType.PASSWORD → 命中 provider 里的授权类型检查，报 unauthorized_client。

两个必须提前知道的坑：一是 AuthorizationGrantType 是个普通类而不是枚举，官方只提供 AUTHORIZATION_CODE、REFRESH_TOKEN、CLIENT_CREDENTIALS 等常量，没有 PASSWORD，需要自行 new AuthorizationGrantType("password") 定义一个常量（上面三件套引用的都是它）。二是代码里的 OAuth2EndpointUtils、OAuth2AuthenticationProviderUtils、SpringAuthorizationServerVersion 属于框架内部类，不在公开 API 里，升级随时可能改签名——从官方源码复制到自己的包里并锁死版本是常见做法，社区也有现成的密码模式扩展实现可参考。

密码认证 token 信息

public class OAuth2ResourceOwnerAuthenticationToken extends AbstractAuthenticationToken {
    private static final long serialVersionUID = SpringAuthorizationServerVersion.SERIAL_VERSION_UID;

    private final AuthorizationGrantType authorizationGrantType;
    private final Authentication clientPrincipal;
    private final String username;
    private final String password;
    private final Set<String> scopes;

    public OAuth2ResourceOwnerAuthenticationToken(AuthorizationGrantType authorizationGrantType, Authentication clientPrincipal,
                                                  @Nullable String username, @Nullable String password, @Nullable Set<String> scopes) {
        super(Collections.emptyList());
        Assert.notNull(authorizationGrantType, "authorizationGrantType cannot be null");
        Assert.notNull(clientPrincipal, "clientPrincipal cannot be null");
        this.authorizationGrantType = authorizationGrantType;
        this.clientPrincipal = clientPrincipal;
        this.username = username;
        this.password = password;
        this.scopes = Collections.unmodifiableSet((scopes != null) ? new HashSet<>(scopes) : Collections.emptySet());
    }

    //...
}

这个认证对象只是数据载体：super(Collections.emptyList()) 传入空权限集合，真正的权限要到 provider 验完账号之后才由 access token 的 scope 决定。

密码认证转换器

public class OAuth2ResourceOwnerAuthenticationConverter implements AuthenticationConverter {
    @Override
    public Authentication convert(HttpServletRequest request) {
        // grant_type (REQUIRED)
        String grantType = request.getParameter(OAuth2ParameterNames.GRANT_TYPE);
        if (!AuthorizationGrantType.PASSWORD.getValue().equals(grantType)) {
            return null;
        }

        MultiValueMap<String, String> parameters = OAuth2EndpointUtils.getParameters(request);

        // username (REQUIRED)
        String username = parameters.getFirst(OAuth2ParameterNames.USERNAME);
        if (!StringUtils.hasText(username) || parameters.get(OAuth2ParameterNames.USERNAME).size() != 1) {
            OAuth2EndpointUtils.throwError(OAuth2ErrorCodes.INVALID_REQUEST, OAuth2ParameterNames.USERNAME, OAuth2EndpointUtils.ACCESS_TOKEN_REQUEST_ERROR_URI);
        }

        // password (REQUIRED)
        String password = parameters.getFirst(OAuth2ParameterNames.PASSWORD);
        if (!StringUtils.hasText(password) || parameters.get(OAuth2ParameterNames.PASSWORD).size() != 1) {
            OAuth2EndpointUtils.throwError(OAuth2ErrorCodes.INVALID_REQUEST, OAuth2ParameterNames.PASSWORD, OAuth2EndpointUtils.ACCESS_TOKEN_REQUEST_ERROR_URI);
        }

        // scope (OPTIONAL)
        String scope = parameters.getFirst(OAuth2ParameterNames.SCOPE);
        if (StringUtils.hasText(scope) && parameters.get(OAuth2ParameterNames.SCOPE).size() != 1) {
            OAuth2EndpointUtils.throwError(OAuth2ErrorCodes.INVALID_REQUEST, OAuth2ParameterNames.SCOPE,
                    OAuth2EndpointUtils.ACCESS_TOKEN_REQUEST_ERROR_URI);
        }
        Set<String> scopes = null;
        if (StringUtils.hasText(scope)) {
            scopes = new HashSet<>(Arrays.asList(StringUtils.delimitedListToStringArray(scope, " ")));
        }

        // 用于获取 client
        Authentication clientPrincipal = SecurityContextHolder.getContext().getAuthentication();
        if (clientPrincipal == null) {
            OAuth2EndpointUtils.throwError(OAuth2ErrorCodes.INVALID_REQUEST, OAuth2ErrorCodes.INVALID_CLIENT,
                    OAuth2EndpointUtils.ACCESS_TOKEN_REQUEST_ERROR_URI);
        }

        return new OAuth2ResourceOwnerAuthenticationToken(AuthorizationGrantType.PASSWORD, clientPrincipal, username, password, scopes);
    }
}

convert() 返回 null 而不是抛异常，是这套 SPI 的约定：转换器链会依次询问，不匹配就交给下一个。这里能从 SecurityContextHolder 里拿到 client 主体，是因为客户端认证（Basic 或 POST）在进入 token 端点前已经由 clientAuthentication 链完成。每个参数都校验 parameters.get(...).size() != 1，目的是拒绝重复参数（RFC 6749 要求每个参数只能出现一次）。

密码认证处理

public class OAuth2ResourceOwnerAuthenticationProvider implements AuthenticationProvider {
    private static final Log LOGGER = LogFactory.getLog(OAuth2ResourceOwnerAuthenticationProvider.class);
    private static final String ERROR_URI = "https://datatracker.ietf.org/doc/html/rfc6749#section-5.2";
    private static final OAuth2TokenType ID_TOKEN_TOKEN_TYPE = new OAuth2TokenType(OidcParameterNames.ID_TOKEN);

    private final AuthenticationManager authenticationManager;
    private final OAuth2AuthorizationService authorizationService;
    private final OAuth2TokenGenerator<? extends OAuth2Token> tokenGenerator;

    public OAuth2ResourceOwnerAuthenticationProvider(AuthenticationManager authenticationManager, OAuth2AuthorizationService authorizationService,
                                                     OAuth2TokenGenerator<? extends OAuth2Token> tokenGenerator) {
        Assert.notNull(authorizationService, "authorizationService cannot be null");
        Assert.notNull(tokenGenerator, "tokenGenerator cannot be null");
        this.authenticationManager = authenticationManager;
        this.authorizationService = authorizationService;
        this.tokenGenerator = tokenGenerator;
    }

    @Override
    public Authentication authenticate(Authentication authentication) throws AuthenticationException {
        OAuth2ResourceOwnerAuthenticationToken resourceOwnerAuthentication = (OAuth2ResourceOwnerAuthenticationToken) authentication;

        OAuth2ClientAuthenticationToken clientPrincipal = OAuth2AuthenticationProviderUtils
                .getAuthenticatedClientElseThrowInvalidClient(resourceOwnerAuthentication);
        RegisteredClient registeredClient = clientPrincipal.getRegisteredClient();

        if (LOGGER.isTraceEnabled()) {
            LOGGER.trace("Retrieved registered client");
        }

        if (!registeredClient.getAuthorizationGrantTypes().contains(AuthorizationGrantType.PASSWORD)) {
            throw new OAuth2AuthenticationException(OAuth2ErrorCodes.UNAUTHORIZED_CLIENT);
        }

        Authentication usernamePasswordAuthentication = null;
        try {
            usernamePasswordAuthentication = authenticationManager.authenticate(new UsernamePasswordAuthenticationToken(resourceOwnerAuthentication.getUsername(), resourceOwnerAuthentication.getPassword()));
        } catch (AuthenticationException e) {
            throw new OAuth2AuthenticationException(OAuth2ErrorCodes.ACCESS_DENIED);
        }

        Set<String> authorizedScopes = registeredClient.getScopes();
        Set<String> requestedScopes = resourceOwnerAuthentication.getScopes();
        if (!CollectionUtils.isEmpty(requestedScopes)) {
            Set<String> unauthorizedScopes = requestedScopes.stream().filter(scope -> !authorizedScopes.contains(scope)).collect(Collectors.toSet());
            if (!CollectionUtils.isEmpty(unauthorizedScopes)) {
                throw new OAuth2AuthenticationException(OAuth2ErrorCodes.INVALID_SCOPE);
            }
        }

        if (LOGGER.isTraceEnabled()) {
            LOGGER.trace("Validated token request parameters");
        }

        // @formatter:off
        DefaultOAuth2TokenContext.Builder tokenContextBuilder = DefaultOAuth2TokenContext.builder()
                .registeredClient(registeredClient)
                .principal(usernamePasswordAuthentication)
                .authorizationServerContext(AuthorizationServerContextHolder.getContext())
                .authorizedScopes(requestedScopes)
                .authorizationGrantType(AuthorizationGrantType.PASSWORD)
                .authorizationGrant(resourceOwnerAuthentication);
        // @formatter:on

        // ----- Access token -----
        OAuth2TokenContext tokenContext = tokenContextBuilder.tokenType(OAuth2TokenType.ACCESS_TOKEN).build();
        OAuth2Token generatedAccessToken = this.tokenGenerator.generate(tokenContext);
        if (generatedAccessToken == null) {
            OAuth2Error error = new OAuth2Error(OAuth2ErrorCodes.SERVER_ERROR,
                    "The token generator failed to generate the access token.", ERROR_URI);
            throw new OAuth2AuthenticationException(error);
        }

        if (LOGGER.isTraceEnabled()) {
            LOGGER.trace("Generated access token");
        }

        OAuth2AccessToken accessToken = new OAuth2AccessToken(OAuth2AccessToken.TokenType.BEARER,
                generatedAccessToken.getTokenValue(), generatedAccessToken.getIssuedAt(),
                generatedAccessToken.getExpiresAt(), tokenContext.getAuthorizedScopes());

        // @formatter:off
        OAuth2Authorization.Builder authorizationBuilder = OAuth2Authorization.withRegisteredClient(registeredClient)
                .principalName(usernamePasswordAuthentication.getName())
                .authorizationGrantType(AuthorizationGrantType.PASSWORD)
                .authorizedScopes(authorizedScopes)
                .attribute(Principal.class.getName(), usernamePasswordAuthentication);
        // @formatter:on

        if (generatedAccessToken instanceof ClaimAccessor claimAccessor) {
            authorizationBuilder.token(accessToken, metadata -> metadata.put(OAuth2Authorization.Token.CLAIMS_METADATA_NAME, claimAccessor.getClaims()));
        } else {
            authorizationBuilder.accessToken(accessToken);
        }

        // ----- Refresh token -----
        OAuth2RefreshToken refreshToken = null;
        // Do not issue refresh token to public client
        if (registeredClient.getAuthorizationGrantTypes().contains(AuthorizationGrantType.REFRESH_TOKEN) &&
                !clientPrincipal.getClientAuthenticationMethod().equals(ClientAuthenticationMethod.NONE)) {
            tokenContext = tokenContextBuilder.tokenType(OAuth2TokenType.REFRESH_TOKEN).build();
            OAuth2Token generatedRefreshToken = this.tokenGenerator.generate(tokenContext);
            if (generatedRefreshToken != null) {
                if (!(generatedRefreshToken instanceof OAuth2RefreshToken)) {
                    OAuth2Error error = new OAuth2Error(OAuth2ErrorCodes.SERVER_ERROR,
                            "The token generator failed to generate a valid refresh token.", ERROR_URI);
                    throw new OAuth2AuthenticationException(error);
                }

                if (LOGGER.isTraceEnabled()) {
                    LOGGER.trace("Generated refresh token");
                }

                refreshToken = (OAuth2RefreshToken) generatedRefreshToken;
                authorizationBuilder.refreshToken(refreshToken);
            }
        }

        // ----- ID token -----
        OidcIdToken idToken;
        if (requestedScopes.contains(OidcScopes.OPENID)) {
            // @formatter:off
            tokenContext = tokenContextBuilder
                    .tokenType(ID_TOKEN_TOKEN_TYPE)
                    .authorization(authorizationBuilder.build())    // ID token customizer may need access to the access token and/or refresh token
                    .build();
            // @formatter:on
            OAuth2Token generatedIdToken = this.tokenGenerator.generate(tokenContext);
            if (!(generatedIdToken instanceof Jwt)) {
                OAuth2Error error = new OAuth2Error(OAuth2ErrorCodes.SERVER_ERROR,
                        "The token generator failed to generate the ID token.", ERROR_URI);
                throw new OAuth2AuthenticationException(error);
            }

            if (LOGGER.isTraceEnabled()) {
                LOGGER.trace("Generated id token");
            }

            idToken = new OidcIdToken(generatedIdToken.getTokenValue(), generatedIdToken.getIssuedAt(),
                    generatedIdToken.getExpiresAt(), ((Jwt) generatedIdToken).getClaims());
            authorizationBuilder.token(idToken, metadata -> metadata.put(OAuth2Authorization.Token.CLAIMS_METADATA_NAME, idToken.getClaims()));
        }
        else {
            idToken = null;
        }

        OAuth2Authorization authorization = authorizationBuilder.build();

        this.authorizationService.save(authorization);

        if (LOGGER.isTraceEnabled()) {
            LOGGER.trace("Saved authorization");
        }

        Map<String, Object> additionalParameters = Collections.emptyMap();
        if (idToken != null) {
            additionalParameters = new HashMap<>();
            additionalParameters.put(OidcParameterNames.ID_TOKEN, idToken.getTokenValue());
        }

        if (LOGGER.isTraceEnabled()) {
            LOGGER.trace("Authenticated token request");
        }

        return new OAuth2AccessTokenAuthenticationToken(registeredClient, clientPrincipal, accessToken, refreshToken, additionalParameters);
    }

    @Override
    public boolean supports(Class<?> authentication) {
        return OAuth2ResourceOwnerAuthenticationToken.class.isAssignableFrom(authentication);
    }
}

provider 的骨架就是五步：① 取 RegisteredClient 并确认它允许 PASSWORD；② 用 authenticationManager 验账号密码（这一步才是真正校验用户身份）；③ 校验请求 scope 是否全部在注册范围内；④ 依次生成 access / refresh / id token；⑤ authorizationService.save(authorization) 落库并返回 OAuth2AccessTokenAuthenticationToken。几个细节：

  • 账号验错时抛的是 OAuth2ErrorCodes.ACCESS_DENIED（映射为 access_denied），而不是常见的 invalid_grant；前端要把它归入统一的「账号或密码错误」提示。
  • refresh token 的签发条件是「客户端注册了 REFRESH_TOKEN 授权类型」且「客户端认证方式不是 NONE」——公开客户端拿不到 refresh token，这是 OAuth 2.1 的硬性要求。
  • 只有 requestedScopes 里含 openid 才会生成 id token，走的是 OIDC 那套流程。
  • authorizedScopes 与 requestedScopes 用混了：构建 tokenContext 时传的是 requestedScopes，而 authorizationBuilder.authorizedScopes(...) 存的是 registeredClient.getScopes()。请求不带 scope 时 requestedScopes 为 null，签出的 JWT 里 scope claim 为空，而授权记录里存的却是客户端的全部 scope。生产上应以「请求 scope 与注册 scope 的交集」为准，两处保持统一。

3.2.3 配置

新版没有“一个注解开启授权服务器”，而是把安全链拆成两条：一条负责协议端点（/oauth2/authorize、/oauth2/token、/oauth2/jwks 等），一条负责普通业务接口。两条链靠 securityMatcher 区分，匹配优先级由 @Order 或 Bean 顺序决定。

链之外的几个 Bean 更值得逐条看：

  • registeredClientRepository()：InMemoryRegisteredClientRepository 重启即丢，生产要换 JdbcRegisteredClientRepository。redirectUri 必须精确匹配才会被接受；本文只注册了 web 一个 scope，测试时传别的 scope 会被拒。
  • authorizationService()：InMemoryOAuth2AuthorizationService 存的是「已发放的授权记录」（code、access、refresh、id token 的元数据），换 JdbcOAuth2AuthorizationService 之前要先建好 oauth2_authorization 表。
  • authorizationServerSettings()：全默认值意味着端点路径是 /oauth2/authorize、/oauth2/token、/oauth2/jwks，而 issuer 由请求推导。放在网关或多节点后面时必须显式 .issuer("https://auth.example.com") 并正确处理 X-Forwarded-*，否则 JWT 里的 iss 与 JWKS 地址会漂移，资源端验签直接失败。
  • jwkSource()：Jwks.generateRsa() 每次启动都新生成一把密钥。后果是重启后所有已签发的 JWT 全部验签失败，多节点之间也互不认账。生产要把密钥对固化（keystore 或 JWK Set 文件），并支持新旧 kid 并存的轮换。
  • oAuth2TokenCustomizer()：instanceof SysUserDetails 这个判断在本文配置下永远不会命中——上面的 userDetailsService() 返回的是 InMemoryUserDetailsManager，principal 是 org.springframework.security.core.userdetails.User。要看到 userId / nickname 这些自定义 claim，得先接入真实的 UserDetailsService。它就是旧版 TokenEnhancer 在新版里的对应位置。
  • tokenGenerator()：DelegatingOAuth2TokenGenerator 按「谁能处理这个 tokenType」依次询问，JWT 场景下 JwtGenerator 会先命中，OAuth2AccessTokenGenerator（签发不透明令牌）其实用不到，只保留 JwtGenerator + OAuth2RefreshTokenGenerator 更清晰。

资源服务器配置

@Configuration
public class ResourceServerConfig {
    @Bean
    public SecurityFilterChain resourceServerSecurityFilterChain(HttpSecurity http) throws Exception {
        // @formatter:off
        http
            .securityMatcher("/**")
            .authorizeHttpRequests(authorize -> authorize
                .anyRequest().authenticated()
            )
            .oauth2ResourceServer(oauth2ResourceServer -> oauth2ResourceServer
                .jwt(Customizer.withDefaults())
            );
        // @formatter:on

        return http.build();
    }
}

资源端只需要知道「怎么验 JWT」：.jwt(Customizer.withDefaults()) 会拾取容器里的 JwtDecoder Bean，而那个 decoder 是从 jwkSource 建出来的。授权端与资源端同进程时共享密钥没问题；拆成两个服务后，资源端应改成 NimbusJwtDecoder.withJwkSetUri("http://auth-server/oauth2/jwks") 或按 issuer 自动发现——资源端不应该持有签名私钥，这是两服务分离的核心意义。

权限判断上有个常被忽略的映射：JWT 里的 scope claim 会被 JwtAuthenticationConverter 转成带 SCOPE_ 前缀的权限，所以按 scope 鉴权要写 hasAuthority("SCOPE_web")；而 roles("USER") 对应的是 hasRole("USER")（比对时补 ROLE_ 前缀）。两者混用会导致 403 却看不出原因。

3.3 测试

获取 token（Authorization Server 版本的接口为 /oauth2/token）

POST http://localhost:8080/oauth/token?username=user&password=password&grant_type=password&scope=read
Accept: application/json
Authorization: Basic Y2xpZW50OnNlY3JldA==    # btoa('client:secret')

上面这条请求只对 3.1（旧版）成立，换成新版要同时改三样东西：

  • 端点：旧版默认 /oauth/token，新版默认 /oauth2/token。
  • 凭据：Y2xpZW50OnNlY3JldA== 是 client:secret 的 Base64，对应旧版的 withClient("client").secret("secret")；新版的客户端是 WEB_CLIENT / WEB_SECRET，不换请求头会在客户端认证阶段就报 invalid_client。
  • scope：旧版注册了 read / write，scope=read 合法；新版只注册了 web，传 read 会被 3.2.2 provider 的 scope 校验拦下，返回 invalid_scope。

新版的等价写法（参数放表单而不是 URL）：

POST http://localhost:8080/oauth2/token
Accept: application/json
Authorization: Basic V0VCX0NMSUVOVDpXRUJfU0VDUkVU    # btoa('WEB_CLIENT:WEB_SECRET')
Content-Type: application/x-www-form-urlencoded

username=user&password=password&grant_type=password&scope=web

顺带说一句参数位置：示例把参数拼在 query string 上也能跑通，因为 request.getParameter() 对 query 和表单一视同仁；但 RFC 6749 要求用 application/x-www-form-urlencoded 请求体，拼在 URL 上会被访问日志与反向代理原样记录，密码类参数尤其不该出现在那里。

请求受保护的资源

GET http://localhost:8080/hello
Accept: application/json
Authorization: Bearer <access_token>

这一步与版本无关：拿到 access token 后，新旧两版的资源端行为完全一致——解 JWT、验签、看 exp、比权限。这正是 2.1 里那句「资源服务器只与授权服务器约定怎么验令牌」的具体体现。

4 上线检查清单

文中的代码为了可重复运行，把依赖全部换成了内存实现、把凭据写成了明文。对照下表逐项收口：

项文中演示生产必须改成
用户 / 客户端存储InMemory* 三个 BeanJdbcRegisteredClientRepository + JdbcOAuth2AuthorizationService，带建表脚本
密码与 secret明文 + NoOpPasswordEncoderBCryptPasswordEncoder；secret 从环境变量 / 配置中心 / KMS 注入，不进代码库
签名密钥启动随机 RSA，旧版硬编码 "secret"固化密钥库 + kid 轮换；资源端只拿公钥 / JWKS
令牌失效无任何撤销机制短 TTL + refresh 轮换；需要立即断流时加 jti 黑名单或直接换 Opaque 令牌
授权类型以密码模式为主线优先授权码 + PKCE；密码模式仅限自家应用且记录开启原因
传输与回调http://localhost:8080全链路 HTTPS；redirect_uri 精确匹配，禁用通配与前缀匹配
错误处理多处 //... 留空的 handler统一包装且不外泄堆栈；登录失败不区分「用户不存在」与「密码错误」
时效access 1 小时 / refresh 7 天access 5–30 分钟；refresh 轮换 + 复用检测（旧 refresh 一用即全链回收）
审计与端点未开启记录换票与授权日志（不落令牌原文）；按需暴露 /oauth2/revoke、/oauth2/introspect 与 JWKS

5 小结

  • OAuth 2.0 只解决授权，不解决认证；要拿它做登录必须叠加 OIDC（id token），否则应使用 Sa-Token / Spring Security Session 这类应用层方案。
  • 四种模式的差异全在「用户怎么把意愿交给授权服务器」，其中只有授权码把前端通道与后端通道切开，所以它是默认选择；隐式与密码已被 OAuth 2.1 移除。
  • 令牌形态（JWT / Opaque）是一个与授权模式正交的决策，它决定了能不能主动注销、能不能水平扩容、资源端要不要回源。先选形态，再写配置。
  • 旧版靠注解堆功能，新版靠 Bean 显式接线：两条 SecurityFilterChain、三个 InMemory* 存储、一个 OAuth2TokenGenerator。新版看着繁琐，但每一环都可单独测试与替换。
  • 密码模式在新版要自己写「Token + Converter + Provider」三件套并在 tokenEndpoint 里注册两处，缺任何一环的报错信息都不同——排障时先对照 3.2.2 的那张表。
