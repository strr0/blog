Spring 事件驱动

strr0 2023-11-08

1 概述

事件驱动是一种把「发生了什么」与「因此要做什么」解耦的策略：主流程只负责发布事实，副作用由监听器各自认领，从而避免业务方法里堆叠一串下游调用。

Spring 提供的是应用内事件机制（观察者模式），特点是零外部依赖、调用链清晰；但它不跨进程、不保证投递，需要可靠异步时应该换消息队列。

三个角色：

  • 事件（Event）：承载事实的数据对象；
  • 发布者（Publisher）：发布事件，不关心谁处理；
  • 监听器（Listener）：订阅并处理事件，彼此互不感知。

2 快速上手

2.1 定义事件

事件类继承 ApplicationEvent（非必须）：

public class MyEvent extends ApplicationEvent {
    public MyEvent(Object source) {
        super(source);
    }
}

「非必须」是指：从 Spring 4.2 起，可以发布任意对象作为事件，监听端用 @EventListener(MyEvent.class) 直接匹配类型即可，省掉样板构造器。继承 ApplicationEvent 的好处是语义显式，且能拿到 timestamp、source 等字段。

2.2 定义事件监听器

2.2.1 通过实现接口方式

public class MyListener implements ApplicationListener<MyEvent> {
    @Override
    public void onApplicationEvent(MyEvent event) {
        // TODO
    }
}

该类必须被 Spring 管理（注册为 Bean）才会收到事件，仅写类不生效。

2.2.2 通过注解方式

@Component
public class MyListener {
    @EventListener
    public void onReceiveEvent(MyEvent event) {
        // TODO
    }
}

注解方式更常用：一个类里可以放多个监听方法，方法参数可以有多个（按类型依次匹配），还能通过 condition 写 SpEL 做条件过滤。

2.3 发布事件

@SpringBootTest
public class ApplicationTests {
    @Autowired
    private ApplicationContext applicationContext;

    @Autowired
    private ApplicationEventPublisher applicationEventPublisher;

    @Test
    void test1() {
        applicationContext.publishEvent(new MyEvent("my-event"));
    }

    @Test
    void test2() {
        applicationEventPublisher.publishEvent(new MyEvent("my-event"));
    }
}

两个用例效果相同：ApplicationContext 本身就实现了 ApplicationEventPublisher。业务代码中建议注入 ApplicationEventPublisher，它只暴露发布能力，比直接依赖容器更干净。

3 执行模型

3.1 默认是同步的

事件发布后，容器在发布者所在线程里依次调用所有监听器，全部执行完才从 publishEvent 返回。因此：

  • 监听器耗时会计入发布方的响应时间；
  • 监听器抛出的异常会向上传播，可能回滚发布者的事务或中断主流程。

3.2 异步执行

可通过 @Async 注解把监听改为异步：

@Component
public class MyListener {
    @Async
    @EventListener
    public void onReceiveEvent(MyEvent event) {
        // TODO
    }
}

两个前提与两个副作用必须心里有数：

  • 需要开启 @EnableAsync，否则 @Async 不生效；
  • 建议显式提供线程池（实现 AsyncConfigurer 或指定 @Async("xxxExecutor")），默认执行器可能不复用线程；
  • 异步之后主流程与监听器不再同事务、不再同时刻，事件对象若携带可变对象，可能被主流程继续修改；
  • 监听器抛出的异常默认不会回到发布者，需要 AsyncUncaughtExceptionHandler 兜住。

3.3 与事务绑定

「数据落库成功后再发通知」是典型诉求。事件在事务方法内部发布时，监听器其实先于提交执行，一旦回滚就产生脏副作用。这种场景应改用 @TransactionalEventListener：

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onReceiveEvent(MyEvent event) {
    // 仅在事务提交成功后执行
}

phase 可选 AFTER_COMMIT（默认）、AFTER_ROLLBACK、AFTER_COMPLETION、BEFORE_COMMIT。注意它默认只在存在事务时触发，事务外发布的事件会被忽略，需要时设置 fallbackExecution = true。

3.4 多个监听器的顺序

同一事件的多个监听器按 @Order 值从小到大执行；无序时依赖 Bean 的注册顺序，不应依赖该行为。

4 小结

  • 应用内事件用于解耦同进程的副作用，不能替代消息队列。
  • 事件类可以不继承 ApplicationEvent，监听器必须被容器管理。
  • 默认同步执行，异常与耗时都会影响发布者；异步要配合 @EnableAsync 与显式线程池。
  • 涉及事务的副作用用 @TransactionalEventListener，而不是在业务方法末尾手写「提交后再处理」。
