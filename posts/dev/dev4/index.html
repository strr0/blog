Spring 整合 Kafka

strr0 2023-09-17

1 概述

Kafka 是分区日志型消息系统，适合高吞吐、需要重放或做流式处理链路（日志采集、事件溯源、埋点）的场景。与 RabbitMQ 的「队列 + 路由」模型不同，Kafka 的消费进度由消费者组的 offset 决定，同一条消息可以被多个组各自重复消费。

本文记录 Spring 侧的最小可用链路：Topic 自动创建 → 生产者发对象 → 消费者收对象。

2 环境配置

Broker 的部署参考 消息队列安装，本文假设 localhost:9092 已可用。

3 Spring 配置

3.1 引入依赖

<dependency>
    <groupId>org.springframework.kafka</groupId>
    <artifactId>spring-kafka</artifactId>
    <version>${spring-boot.version}</version>
</dependency>

<!-- kafka 序列化 -->
<dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>${jackson.version}</version>
</dependency>

JsonMessageConverter 依赖 jackson-databind，需要显式引入。另外注意 spring-kafka 有独立的版本线（如 3.x 对应 Spring Boot 3.x），复用 ${spring-boot.version} 只在两者恰好同号时才不会出问题，更稳妥的做法是由 spring-boot-dependencies BOM 或 spring-boot-starter 统一管理版本。

3.2 application 配置

spring:
  kafka:
    bootstrap-servers: localhost:9092
    producer:
      value-serializer: org.springframework.kafka.support.serializer.JsonSerializer
    consumer:
      value-deserializer: org.apache.kafka.common.serialization.ByteArrayDeserializer
  • bootstrap-servers：连接入口，生产环境应写多个节点。
  • 生产端 value-serializer 用 JsonSerializer，把对象直接序列化成 JSON 字节。
  • 消费端 value-deserializer 故意用 ByteArrayDeserializer，先拿到原始字节，再由消息转换器负责反序列化，原因见第 5 节。
  • key 未配置时使用 Kafka 客户端默认的 StringSerializer / StringDeserializer，两端保持一致即可。

3.3 Topic 和消息转换器配置

@Configuration
@EnableKafka
public class KafkaConfig {
    @Bean
    public NewTopic topic() {
        return new NewTopic("topic1", 1, (short) 1);
    }

    // 消息转换
    @Bean
    public RecordMessageConverter converter() {
        return new JsonMessageConverter();
    }
}
  • @EnableKafka 开启 @KafkaListener 的注册能力，监听容器工厂由它导入。
  • new NewTopic("topic1", 1, (short) 1) 表示 1 个分区、副本因子 1。该 Bean 由 KafkaAdmin 在启动时创建 Topic；若使用纯 spring-kafka（非 Boot），需要自行声明 KafkaAdmin，否则 Topic 不会自动出现。
  • JsonMessageConverter 负责「对象 ↔ JSON 字节」的转换，使监听方法可以直接声明业务类型入参。

3.4 生产者

@Service
public class KafkaProducerService {
    @Autowired
    private KafkaTemplate<String, Object> kafkaTemplate;

    // 发送消息
    public void sendFoo(String what) {
        kafkaTemplate.send("topic1", new Foo1(what));
    }
}

send 是异步的，返回 ListenableFuture / CompletableFuture。需要确认落盘结果时应注册回调或 get() 等待，并注意 acks 配置（默认 all 需服务端配合）。

3.5 消费者

@Service
public class KafkaConsumerService {
    // 接收消息
    @KafkaListener(id = "fooGroup", topics = "topic1")
    public void listen(Foo2 foo) {
        // TODO
    }
}

id 即消费者组名。这里入参是 Foo2，而发送方发的是 Foo1，两者字段一致即可正常映射——反序列化目标由监听方法签名决定，这正是第 5 节方案的意义。

4 测试

@SpringBootTest
class ApplicationTests {
    @Autowired
    private KafkaProducerService kafkaProducerService;

    @Test
    void sendMessageTest() {
        String what = "hello world!";
        kafkaProducerService.sendFoo(what);
    }
}

运行后若消费者没有打印，优先按顺序排查：Topic 是否被创建 → 消费者组是否真的启动（id 冲突会导致只跑一个实例）→ offset 是否已越过该消息（首次消费需配 auto-offset-reset: earliest）。

5 为什么消费端用 ByteArrayDeserializer

Kafka 自带的 JsonDeserializer 依赖消息头里的 __TypeId__ 反推目标类，这带来两个问题：

  1. 生产方与消费方必须共享同一个类的全限定名，跨语言、跨服务演进时极易失配；
  2. 按消息头实例化类存在反序列化安全风险，需要显式配置 trusted.packages。

本项目的做法是绕开这条链路：

  • Kafka 层用 ByteArrayDeserializer，只负责把字节原样交给 Spring；
  • Spring 层的 JsonMessageConverter 依据监听方法的参数类型（Foo2）决定反序列化成什么。

好处是消费端完全自主决定目标类型，生产端不需要暴露类名，两端只靠 JSON 字段契约耦合。

6 注意事项

  • 重复消费不可避免：Kafka 提供 at-least-once，业务侧必须做幂等（唯一键、状态机、去重表）。
  • 分区决定并发：同一分区只会被组内一个消费者处理，想提高并发需要增加分区数与消费者实例。
  • 顺序只在分区内成立：需要严格有序的业务要用 key 把相关消息路由到同一分区。
  • 异常处理：监听方法抛异常默认会重试并可能阻塞该分区，应配置 DefaultErrorHandler + DeadLetterPublishingRecoverer 做重试上限与死信投递。
  • 首次消费位置：auto-offset-reset 默认 latest，测试环境经常「收不到消息」就是这个原因。

7 小结

  • 链路四步：NewTopic 建主题、KafkaTemplate 发、@KafkaListener 收、JsonMessageConverter 负责对象转换。
  • 消费端用 ByteArrayDeserializer + 参数类型反序列化，比 JsonDeserializer 的 __TypeId__ 方案更解耦、更安全。
  • 幂等、分区并发、死信处理是上生产前必须补的三块。
