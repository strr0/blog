概述

单体应用长到一定程度，一次发布影响全部功能、一个慢接口拖垮整个进程，此时才需要把服务按业务能力拆开。微服务不是一套框架，而是一组必须由基础设施兜住的能力：配置怎么下发、服务怎么互相找到、下游挂了怎么办、请求从哪里进入、一次调用跨了哪些服务。

本文按这五个问题依次落地，涉及的角色如下：

能力本文组件当前版本线的替代品
配置中心Spring Cloud ConfigNacos、Apollo
注册与发现Netflix EurekaNacos、Consul
服务调用RestTemplate / FeignOpenFeign（不变）
容错Netflix HystrixResilience4j、Sentinel
网关Netflix Zuul 1Spring Cloud Gateway
事件驱动Spring Cloud Stream + Kafka同（编程模型改为函数式）
链路跟踪Spring Sleuth + ZipkinMicrometer Tracing + Zipkin

阅读时需要留意一个前提：文中依赖版本是 Spring Boot 2.4.0 / Spring Cloud 2020.0.0，Hystrix、Zuul 1、Sleuth 在 Netflix 停止维护后已被移出官方支持列表，因此第 4、5、8 节保留了当年的写法，并在每节末尾给出迁移方向。概念层面（断路器、舱壁、前置/后置过滤器、traceId 透传）至今仍然适用。

客户端三行的含义：register-with-eureka 把自己注册到中心，fetch-registry 拉一份服务列表到本地（Feign / LoadBalancer 靠这份本地缓存寻址，所以即使只当服务方也要开），prefer-ip-address: true 让注册的是 IP 而不是主机名——容器与跨网段环境下主机名经常解不了。

服务端配置里的两个 false 表示既不注册也不拉取，这是单机 Eureka 的标准写法；集群部署时它们要改成 true，并在 defaultZone 里互相指向对方。

3.2 服务发现

3.2.1 DiscoveryClient 方式

通过 DiscoveryClient 获取服务实例进行访问（需要在启动类上添加 @EnableDiscoveryClient 注解开启服务发现）

该注解在当前的自动配置体系下已非必需，引入 Eureka Client 依赖就会开启服务发现；注解本身可用于显式声明意图，或在多注册中心场景下控制开关。

@Component
public class OrganizationDiscoveryClient {
    private final DiscoveryClient discoveryClient;

    @Autowired
    public OrganizationDiscoveryClient(DiscoveryClient discoveryClient) {
        this.discoveryClient = discoveryClient;
    }

    public Organization getOrganization(String organizationId) {
        RestTemplate restTemplate = new RestTemplate();
        List<ServiceInstance> instances = discoveryClient.getInstances("organizationservice");    // organizationservice 为服务名称
        if (instances.isEmpty()) {
            return null;
        }
        String serviceUri = String.format("%s/v1/organizations/%s", instances.get(0).getUri().toString(), organizationId);
        ResponseEntity<Organization> exchange = restTemplate.exchange(serviceUri, HttpMethod.GET, null, Organization.class);
        return exchange.getBody();
    }
}

3.2.2 RestTemplate 方式

通过 RestTemplate 访问（需要在 RestTemplate Bean 上添加 @LoadBalanced 告诉 Spring 创建一个支持 Ribbon 的 Bean）

注意措辞修正：Spring Cloud 2019 之后 Ribbon 已进入维护模式，@LoadBalanced 背后默认换成 spring-cloud-starter-loadbalancer。行为一致（把服务名换成实例地址），但配置前缀从 ribbon.* 变成 spring.cloud.loadbalancer.*，自定义策略也不再是实现 IRule，而是用 @LoadBalancerClient 指定自定义的 ReactorLoadBalancer 或替换 ServiceInstanceListSupplier。

@Component
public class OrganizationRestTemplateClient {
    private final RestTemplate restTemplate;

    @Autowired
    public OrganizationRestTemplateClient(RestTemplate restTemplate) {
        this.restTemplate = restTemplate;
    }

    public Organization getOrganization(String organizationId) {
        // organizationservice 为服务名称
        ResponseEntity<Organization> exchange = restTemplate.exchange("http://organizationservice/v1/organizations/{organizationId}",
                HttpMethod.GET,
                null,
                Organization.class,
                organizationId);
        return exchange.getBody();
    }
}

3.2.3 FeignClient 方式

通过 Feign 访问（需要在启动类上添加 @EnableFeignClients 注解开启 Feign）

@FeignClient("organizationservice")    // organizationservice 为服务名称
public interface OrganizationFeignClient {
    @RequestMapping(
            method = RequestMethod.GET,
            value = "/v1/organizations/{organizationId}",
            consumes = "application/json"
    )
    Organization getOrganization(@PathVariable("organizationId") String organizationId);
}

三种方式的定位并不相同：

方式谁选实例是否负载均衡适用
DiscoveryClient开发者自己需自己实现需要按元数据（区域、权重）定制寻址时
RestTemplate + @LoadBalancedLoadBalancer是已有的 HTTP 代码改造成本最低
FeignLoadBalancer是声明式接口，配合容错与拦截器最省事

前两种还有两个具体缺陷：DiscoveryClient 写法里 new RestTemplate() 每次调用都新建（应作为 Bean 复用，否则连接池不生效），instances.get(0) 永远取第一个实例（不是负载均衡，且实例列表顺序不保证）。

4 断路器

4.1 断路器配置

由于 Spring Cloud 2020 已移除 Hystrix，更换如下版本

依赖版本
Spring Boot2.3.0.RELEASE
Spring CloudHoxton.SR5

添加依赖

<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-netflix-hystrix</artifactId>
</dependency>

启动类添加 @EnableCircuitBreaker 注解开启断路器模式

两个补充：一是 randomlyRunLong() 是书中用于模拟偶发慢响应的辅助方法（随机 sleep 超过阈值），实际业务中不存在；二是 Netflix 在 2018 年就把 Hystrix 列入维护模式，Spring Cloud Circuit Breaker 现在以 Resilience4j 为默认实现。本节保留 Hystrix 写法是因为三种弹性模式的概念与它高度对应：@HystrixCommand → @CircuitBreaker + @Retry，fallbackMethod → fallbackMethod（同名同义），threadPoolKey → @Bulkhead。从 Hystrix 迁过去时不必重新理解模型，只需重新对应参数名。

4.2 三种弹性模式

4.2.1 断路器模式

杀死运行缓慢和退化的系统调用，调用快速失败，防止资源枯竭

@HystrixCommand(
        commandProperties = {
                // 设置超时
                @HystrixProperty(name = "execution.isolation.thread.timeoutInMilliseconds", value = "12000")
        }
)
public List<License> getLicensesByOrg(String organizationId) {
    randomlyRunLong();
    return licenseRepository.findByOrganizationId(organizationId);
}

4.2.2 回退模式

调用失败或调用的断路器失败时定义的替代代码路径

@HystrixCommand(
        // 设置回退
        fallbackMethod = "buildFallbackLicenseList",
)
public List<License> getLicensesByOrg(String organizationId) {
    randomlyRunLong();
    return licenseRepository.findByOrganizationId(organizationId);
}

// 回退
private List<License> buildFallbackLicenseList(String organizationId) {
    List<License> fallbackList = new ArrayList<>();
    License license = new License()
            .withId("0000000-00-00000")
            .withOrganizationId( organizationId )
            .withProductName("Sorry no licensing information currently available");

    fallbackList.add(license);
    return fallbackList;
}

4.2.3 舱壁模式

调用隔离在自己的线程池，防止吞噬所有资源

@HystrixCommand(
        // 线程池名称
        threadPoolKey = "licenseByOrgThreadPool",
        threadPoolProperties = {
                // 核心线程数
                @HystrixProperty(name = "coreSize", value = "30"),
                // 请求队列
                @HystrixProperty(name = "maxQueueSize", value = "10")
        }
)
public List<License> getLicensesByOrg(String organizationId) {
    randomlyRunLong();
    return licenseRepository.findByOrganizationId(organizationId);
}

启动类添加 @EnableZuulProxy 开启路由

Zuul 1 的定位是「逆向代理 + 过滤器链」：每个请求依次经过 pre → route → post → error 四类过滤器。它与注册中心直连，靠服务名自动映射路由，因此配置里只需引 eureka client。

迁移提醒：Zuul 1 是阻塞 IO 模型，每个待请求占一条线程，长连接与 SSE 场景下吞吐上不去；Netflix 之后的 Zuul 2 也未被 Spring Cloud 采纳。Spring Cloud Gateway 基于 WebFlux/Netty 异步模型，概念对应关系为：zuul.routes → routes[].uri/predicates/filters，前置/后置过滤器 → GatewayFilter 与全局 GlobalFilter，ignored-services → 不再自动暴露路由（默认只转发显式声明的 route）。

参考 Spring 整合 OAuth 2.0

分工上建议这样切：网关层只做「身份是否合法」（令牌校验、路由级权限、跨域与限流），细粒度资源权限留在业务服务里自己判。把两者都堆到网关会让网关成为全局瓶颈，也让服务无法单独部署。

    String INPUT = "inboundOrgChanges";

    @Input(INPUT)
    SubscribableChannel input();
}

消费者

@EnableBinding(CustomSink.class)
public class OrganizationChangeHandler {
    @StreamListener(CustomSink.INPUT)
    public void loggerSink(OrganizationChangeModel orgChange) {
        System.out.println(String.format("Received a message of type %s", orgChange.getType()));
        //...
    }
}

编程模型提醒：@EnableBinding、@Input / @Output、@StreamListener 这套接口式写法从 Spring Cloud Stream 3.0 起已被标为废弃（官方标记为 maintenance mode），新版推荐函数式模型：生产者声明一个 Supplier<String> Bean，消费者声明 Consumer<OrganizationChangeModel>，绑定名与 topic 靠 spring.cloud.function.definition 与 spring.cloud.stream.bindings.<函数名>.destination 配置。两个概念没有变（目标 topic、消费组 group、content-type），只是把「接口 + 注解」换成了「函数 + 配置」。另外 group 是必须项：不写 group 时每个实例都会收到全量消息，多实例部署下会造成重复消费。

@Component
public class ResponseFilter extends ZuulFilter {
    private final Tracer tracer;

    public ResponseFilter(Tracer tracer) {

    }

    //...

    @Override
    public Object run() throws ZuulException {
        System.out.println(String.format("Adding the correlation id to the outbound headers. %s", FilterUtil.getCorrelationId()));
        // 打印 tracer 信息
        FilterUtil.addCorrelationId(tracer.currentSpan().toString());
        System.out.println(String.format("Completing outgoing request for %s.", FilterUtil.getRequestURI()));
        return null;
    }
}

网关这里的 ResponseFilter 把自定义的 tmx-correlation-id 写回响应头，前端拿着它就能在日志里检索整条链路——这是 Sleuth 的 traceId 之外的业务级跟踪号，两者互补：前者只能服务端内部用，后者可以直接交给报障用户。

迁移提醒：Spring Boot 3 / Spring Cloud 2022 起 Sleuth 已由 Micrometer Tracing 接替（micrometer-tracing-bridge-brave 或 micrometer-tracing-bridge-otel，再配 zipkin-reporter-brave 上报），配置前缀从 spring.sleuth.* 改为 management.tracing.*。两处可见行为也随之变化：MDC 里的键名统一成小写的 traceId / spanId（早期 Sleuth 与原生 Brave 是 X-B3-TraceId / X-B3-SpanId，日志格式要跟着改），跨服务透传的 HTTP 头默认从 X-B3-* 换成 W3C 的 traceparent，需要与旧系统对接时可显式改回 B3 格式。

9 小结

  • 微服务的五个问题各自有对应组件，但它们之间是依赖关系而不是并列关系：网关依赖注册中心寻址，断路器包裹远程调用，链路跟踪需要所有组件配合透传头部。
  • 配置中心有两处容易配错：@RefreshScope 应标在具体业务 Bean 上，{cipher} 解密发生在哪一端取决于 server.encrypt.enabled。
  • 服务发现三种方式中，只有 DiscoveryClient 把选型工作交给开发者，其他两种已自动负载均衡；新代码推荐 Feign。
  • 断路器、回退、舱壁三个概念不依赖 Hystrix，在 Resilience4j 里一一对应，真正要重做的是参数名与线程池配置。
  • 事件驱动与链路跟踪都不保证投递与采样，上生产前要先确定至少一次还是至多一次、以及采样率。
  • 本文的组件选型已整体落后一个时代（Hystrix / Zuul 1 / Ribbon / Sleuth / @EnableBinding），但「配置 - 发现 - 容错 - 网关 - 事件 - 跟踪」这条拆解思路仍然成立。
