基于 MyBatis-Plus 插件实现字段填充

strr0 2024-12-29

1 概述

在实际开发过程中可能会频繁修改表中的某些基础字段数据（如更新人、更新时间等），通过 MyBatis-Plus 插件可以统一对其进行处理，减少冗余代码。

这类「审计字段」有三种层次的解法，成本与能力递增：

方案能覆盖的字段生效范围局限
数据库默认值（DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP）更新时间所有写入路径，包括手工 SQL解决不了「更新人」这类需要应用上下文的信息，且时间依赖 DB 时钟
MetaObjectHandler全部实体参数进入 MyBatis-Plus 通用方法时自定义 SQL 传 Map 参数时不生效
自定义 InnerInterceptor全部拦截到的所有 SQL改写 SQL 与参数映射，复杂且影响面大

本文给出后两种的实现（第一种作为兜底建议在表结构里同时保留），并说明各自的边界。

2 基础配置

2.1 依赖说明

依赖版本
Spring Boot3.1.7
MyBatis-Plus3.5.5

2.2 项目配置

依赖配置：

<dependency>
    <groupId>com.baomidou</groupId>
    <artifactId>mybatis-plus-boot-starter</artifactId>
</dependency>

<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
</dependency>

Spring Boot 3 项目要确认 starter 与 Boot 版本匹配：MyBatis-Plus 为 Boot 3 单独提供了 starter 坐标，若启动后出现自动配置不生效或 jakarta/javax 相关的报错，优先检查这里引的是哪一个。

application 配置：

spring:
  datasource:
    driver-class-name: com.mysql.cj.jdbc.Driver
    url: jdbc:mysql://localhost:3306/testdb
    username: root
    password: password

3 方案一：MetaObjectHandler

3.1 定义插件

public class MyMetaObjectHandler implements MetaObjectHandler {
    private static final Long DEFAULT_USER_ID = 1L;

    @Override
    public void insertFill(MetaObject metaObject) {
        if (metaObject != null && metaObject.getOriginalObject() instanceof BaseEntity baseEntity) {
            Date current = baseEntity.getCreateTime() != null ? baseEntity.getCreateTime() : new Date();
            baseEntity.setCreateTime(current);
            baseEntity.setUpdateTime(current);
            Long userId = baseEntity.getCreateBy() != null ? baseEntity.getCreateBy() : DEFAULT_USER_ID;
            // 当前已登录 且 创建人为空 则填充
            baseEntity.setCreateBy(userId);
            // 当前已登录 且 更新人为空 则填充
            baseEntity.setUpdateBy(userId);
        }
    }

    @Override
    public void updateFill(MetaObject metaObject) {
        if (metaObject != null && metaObject.getOriginalObject() instanceof BaseEntity baseEntity) {
            Date current = new Date();
            // 更新时间填充(不管为不为空)
            baseEntity.setUpdateTime(current);
            // 当前已登录 更新人填充(不管为不为空)
            baseEntity.setUpdateBy(DEFAULT_USER_ID);
        }
    }
}

三段设计意图值得注意：

  • insertFill 尊重已有值：createTime 非空时保留原值，便于数据迁移、补录历史数据；updateTime 与创建时间取同一时刻，保证新增记录两者一致。
  • updateFill 无条件覆盖：更新时间与更新人代表「最后一次改动」，必须每次刷新，所以不做判空。
  • DEFAULT_USER_ID 只是占位：注释写的是「当前已登录」，但代码里并没有登录态判断。真实项目应换成从请求上下文取当前用户（SecurityContextHolder、ThreadLocal 或自定义上下文 holder），并注意异步线程取不到值时的兜底策略。

3.2 注册插件

将插件注册为 Bean 即可启用插件：

@Configuration
public class MybatisPlusConfig {
    @Bean
    public MetaObjectHandler metaObjectHandler() {
        return new MyMetaObjectHandler();
    }
}

3.3 标注填充字段

在需要填充的字段添加注解：

public class BaseEntity implements Serializable {
    /**
     * 创建人
     */
    @TableField(fill = FieldFill.INSERT)
    private Long createBy;

    /**
     * 创建时间
     */
    @TableField(fill = FieldFill.INSERT)
    private Date createTime;

    /**
     * 更新人
     */
    @TableField(fill = FieldFill.INSERT_UPDATE)
    private Long updateBy;

    /**
     * 更新时间
     */
    @TableField(fill = FieldFill.INSERT_UPDATE)
    private Date updateTime;

    //...   
}

通过 @TableField 注解声明填充数据的字段会触发 MyMetaObjectHandler 插件填充数据。FieldFill 三个取值的含义：INSERT 只在新增时填、UPDATE 只在更新时填、INSERT_UPDATE 两者都填。

3.4 生效条件与局限

这条链路是「实体属性级」的填充，依赖 MyBatis-Plus 在参数对象上反射取值，因此：

  • 只对实体参数生效：metaObject.getOriginalObject() instanceof BaseEntity 是硬判断。用 UpdateWrapper 配合 Map 参数更新时，originalObject 不是实体，填充不会发生；
  • 只影响带 fill 注解的字段：漏注解 = 不填充，排查时先确认 @TableField(fill = ...)；
  • 不接管 set 语法：UpdateWrapper.set("update_time", ...) 这类手写赋值绕过实体，需要在 wrapper 上自己补；
  • 不修改 XML 里手写的列：自定义 SQL 若显式列出 create_time 并传 #{createTime}，值仍来自实体字段本身，只是填充时机在 SQL 组装前，因此只要参数是实体就依然有效。

4 方案二：InnerInterceptor

4.1 思路

该方式主要思路为拦截 MappedStatement，替换 SQL，再修改参数及参数映射。与方案一「填值」不同，这里是「改语句」——即使业务代码完全没提这些列，SQL 也会被补上。

4.2 定义插件

public class MyInnerInterceptor extends JsqlParserSupport implements InnerInterceptor {
    private static final Long DEFAULT_USER_ID = 1L;

    @Override
    public void beforePrepare(StatementHandler sh, Connection connection, Integer transactionTimeout) {
        PluginUtils.MPStatementHandler mpSh = PluginUtils.mpStatementHandler(sh);
        MappedStatement ms = mpSh.mappedStatement();
        SqlCommandType sct = ms.getSqlCommandType();
        if (sct == SqlCommandType.INSERT || sct == SqlCommandType.UPDATE) {
            PluginUtils.MPBoundSql mpBs = mpSh.mPBoundSql();
            mpBs.sql(parserMulti(mpBs.sql(), ms.getId()));
            // 设置参数映射
            List<ParameterMapping> mappings = Arrays.asList(new ParameterMapping.Builder(ms.getConfiguration(), "createBy", Long.class).build(),
                    new ParameterMapping.Builder(ms.getConfiguration(), "createTime", Date.class).build(),
                    new ParameterMapping.Builder(ms.getConfiguration(), "updateBy", Long.class).build(),
                    new ParameterMapping.Builder(ms.getConfiguration(), "updateTime", Date.class).build());
            List<ParameterMapping> parameterMappings = mpBs.parameterMappings();
            if (sct == SqlCommandType.INSERT) {
                parameterMappings.addAll(mappings);
            } else {
                // 添加到 where 条件之前
                parameterMappings.addAll(parameterMappings.size() - 1, mappings);
            }
            mpBs.parameterMappings(parameterMappings);
        }
    }

    @Override
    public void beforeUpdate(Executor executor, MappedStatement ms, Object parameter) throws SQLException {
        if (parameter instanceof Map map) {
            Date current = new Date();
            map.put("createBy", DEFAULT_USER_ID);
            map.put("createTime", current);
            map.put("updateBy", DEFAULT_USER_ID);
            map.put("updateTime", current);
        } else if (parameter instanceof BaseEntity baseEntity) {
            Date current = new Date();
            baseEntity.setCreateBy(DEFAULT_USER_ID);
            baseEntity.setCreateTime(current);
            baseEntity.setUpdateBy(DEFAULT_USER_ID);
            baseEntity.setUpdateTime(current);
        }
    }

    @Override
    protected void processInsert(Insert insert, int index, String sql, Object obj) {
        insert.addColumns(new Column("create_by"), new Column("create_time"),
                new Column("update_by"), new Column("update_time"));
        List<Expression> expressions = insert.getItemsList(ExpressionList.class).getExpressions();
        int size = expressions.size();
        expressions.add(new JdbcParameter(size + 1, false));
        expressions.add(new JdbcParameter(size + 2, false));
        expressions.add(new JdbcParameter(size + 3, false));
        expressions.add(new JdbcParameter(size + 4, false));
    }

    @Override
    protected void processUpdate(Update update, int index, String sql, Object obj) {
        ArrayList<UpdateSet> updateSets = update.getUpdateSets();
        int size = updateSets.size();
        updateSets.add(new UpdateSet(new Column("create_by"), new JdbcParameter(size + 1, false)));
        updateSets.add(new UpdateSet(new Column("create_time"), new JdbcParameter(size + 2, false)));
        updateSets.add(new UpdateSet(new Column("update_by"), new JdbcParameter(size + 3, false)));
        updateSets.add(new UpdateSet(new Column("update_time"), new JdbcParameter(size + 4, false)));
    }
}

四个方法各司其职：

  • beforePrepare：在预编译前改写 SQL 文本，并把新增的四个占位符按顺序登记到 parameterMappings；
  • beforeUpdate：保证参数容器里真的有这四个值（Map 与实体两种形态分别处理）；
  • processInsert / processUpdate：JSqlParser 回调，分别给 INSERT 补列与 VALUES 占位符、给 UPDATE 补 SET 片段。

4.3 注册插件

将插件注册为 Bean 即可启用插件：

@Configuration
public class MybatisPlusConfig {
    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        interceptor.addInnerInterceptor(new MyInnerInterceptor());
        return interceptor;
    }
}

4.4 风险清单

此方法为全局的拦截器，会对被拦截的 MappedStatement 的 SQL 语句进行解析，相较于常规方式可能会更消耗资源，所以应尽量缩小其作用范围，如只拦截指定的 MappedStatement（可在 beforePrepare 里用 ms.getId() 匹配 Mapper 方法名后再决定是否改写）。

除此之外，这套实现还有几个必须意识到的约束：

  • 所有被改写的表都要有这四列：拦截范围覆盖全部 INSERT/UPDATE，任何一张表缺 create_by 都会直接 SQL 报错。
  • UPDATE 会重写创建人与创建时间：processUpdate 与 beforeUpdate 都无条件写入 createBy / createTime，语义上「创建信息」不应被更新覆盖，落地前应把这两项从 UPDATE 分支剔除。
  • 参数顺序强耦合：parameterMappings 靠 size() - 1 插到 WHERE 之前，新增的 JdbcParameter(size + n) 序号也要与 SET 顺序一致。一旦业务 SQL 结构调整（多加一个 set 字段、把 where 换成 exists 子查询），错位就会变成「参数串位」而非报错，排查成本很高。
  • 批量插入可能失败：insert.getItemsList(ExpressionList.class) 只适配单组 VALUES 的写法，values (...), (...) 多行结构或 insert ... select 会取不到预期类型。
  • SQL 解析有开销：每次预编译都要解析一遍语句，热点写入下应结合 SqlParserList 缓存或限制拦截范围。

5 方案对比与选型

维度MetaObjectHandlerInnerInterceptor
改写对象实体字段值SQL 文本 + 参数映射
是否依赖注解是（@TableField(fill)）否
对 XML 手写 SQL 的效果实体参数有效，Map 参数无效有效（只要列存在）
性能开销反射赋值，可忽略每条 SQL 解析
出错影响面单条记录字段为空语句结构错位、全局报错
维护成本低高

结论：优先用数据库默认值兜住时间、用 MetaObjectHandler 填业务字段；只有「无法统一实体（大量手写 SQL、多来源写入）且所有表结构一致」时才考虑 InnerInterceptor，并且必须限定拦截范围。

6 小结

  • 审计字段填充有三个层次，能用低层方案就不要引入 SQL 改写。
  • MetaObjectHandler 的两个方法对应两种语义：新增保留已有值、更新强制覆盖，取值应来自真实登录上下文而非常量。
  • InnerInterceptor 能力更强但风险更高：列必须普遍存在、参数顺序强耦合、批量插入与更新覆盖创建信息都是需要处理的细节。
