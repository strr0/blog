MyBatis 浅显解读及基础 CRUD 封装

strr0 2023-12-15

1 缘起与目标

动手之前我读了一遍 MyBatis-Plus 的实现。它确实完善、功能齐备，但对 MyBatis 原有结构的改动也不小——Configuration、SqlSessionFactoryBuilder、MapperRegistry 等都有重写版本。我的诉求不同：希望在尽可能保留 MyBatis 原貌的基础上，用最少的代码补上「按实体自动生成基础 CRUD」这一件事。

于是要解决的问题被收敛成三个：

  1. 怎么在不改变 MyBatis 运行模型的前提下，把 SQL 塞进它的配置体系；
  2. 怎么让扫描器自动为我定义的 mapper 接口挂上这些方法；
  3. 结果集的列名与实体字段名不一致时，怎么让映射按我的注解走。

本文按这三个问题展开，最后再讲分页插件与几个必须注意的落地细节。

2 前置工作

2.1 MyBatis 是怎么跑起来的

2.1.1 简单理解

MyBatis 是一个基于 Java 的持久层框架，内部封装了 JDBC，省去了建立连接、执行、断开连接等繁琐操作。

它的运行链条可以拆成五步：

  1. SqlSessionFactoryBuilder 读取 XML 配置或 Java 配置（Spring Boot 项目里由 application 配置简化而来），构建出 SqlSessionFactory；
  2. 从工厂 openSession() 得到 SqlSession，它是一次会话的入口，也持有连接与事务边界；
  3. SqlSession 可以直接按 MappedStatement 的 id 执行 SQL；
  4. 也可以 getMapper() 拿到接口代理，由代理把「方法调用」翻译成第 3 步的执行；
  5. 执行结果交给 ResultSetHandler 映射成对象返回。

整份工作以 SqlSessionFactory 为中心展开，理解一个持久层框架的行为，往往就是理解「对象在哪一步被放进 Configuration」。

2.1.2 示例

直接执行：

SqlSession sqlSession = sqlSessionFactory.openSession();
List<Xxx> xxxs = sqlSession.selectList("xxx.xxx");  // xxx.xxx 为 MappedStatement 的 id

通过 mapper 执行：

SqlSession sqlSession = sqlSessionFactory.openSession();
XxxMapper xxxMapper = sqlSession.getMapper(XxxMapper.class);
List<Xxx> xxxs = xxxMapper.selectList();

两种写法的差别只在于「谁来生成 SQL 与 id 的对应关系」：前者要求调用方知道 id 字符串，后者由 MapperProxy 用 接口全限定名.方法名 拼出 id 去 Configuration 里查 MappedStatement。这正是本次封装可以利用的缝隙——只要往 Configuration 里注册好 MappedStatement，接口里凭空多出的方法就能被找到。

2.2 mybatis-spring-boot-starter 做了什么

mybatis-spring-boot-starter 的核心是 MybatisAutoConfiguration，它定义了默认情况下自动生成的 MyBatis 配置。

2.2.1 sqlSessionFactory 方法

该方法从 Spring Boot 中读取定义的 MyBatis 配置并生成 SqlSessionFactory 对象。

2.2.2 MapperScannerRegistrarNotFoundConfiguration 类

该类为默认 MyBatis 扫描器配置，扫描规则由导入的 AutoConfiguredMapperScannerRegistrar 定义。扫描器将扫描带有 @Mapper 注解的类，以及指定路径下的 Java 类，并为它们生成 Spring Bean。

最初的想法是通过自定义扫描器，对扫描到的类生成 Bean 及添加自定义的方法到 MyBatis 配置中，但是该方法生成的 Bean 会与 MyBatis 的默认配置冲突，为了避免冲突必须放弃 MyBatis 的配置，于是我放弃了这个方法。

改用的路子是不抢扫描，而是换 factoryBean：仍然使用官方的 @MapperScan，只把创建代理的工厂类换成自己的子类，在子类初始化时顺手把 MappedStatement 注册进去。这样既不干扰默认配置，又能精确控制哪些接口参与增强。

一个必须知道的副作用：一旦显式声明了 @MapperScan，starter 的自动扫描（AutoConfiguredMapperScannerRegistrar）就不再注册，此时只有 basePackages 覆盖到的接口会成为 Bean。项目里其他 mapper 需要一并纳入扫描路径，或再补一个 @MapperScan。

2.3 自定义注解

我对自定义注解的理解是：通过一个特殊的标志来标记类、字段或方法，在代码中可以对含有这些标志的对象做特殊处理。自定义注解通过关键字 @interface 实现，注解之上通常还有 @Target 和 @Retention：@Target 表示作用对象（类、字段或方法等），@Retention 表示生命周期。

本文的注解都要在运行期被反射读取，因此 RetentionPolicy.RUNTIME 是必需的——CLASS 与 SOURCE 级别的注解在字节码或源码之外不可见，扫描阶段拿不到。

3 核心实现

3.1 注解定义

3.1.1 @Table 注解

该注解用于定义表名：

@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
public @interface Table {
    String value();
}

3.1.2 @Column 注解

该注解用于定义字段名以及是否模糊查询：

@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Column {
    String value() default "";
    boolean fuzzy() default false;
}

fuzzy 用来在拼装 where 条件时决定该字段走 = 还是 like '%…%'，让「按参数查询」不必为每个字段单独写 SQL。

3.1.3 @Id 注解

该注解用于标记表的主键字段：

@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Id {
}

主键信息不能靠约定推断（列名可能是 id、user_id、uid），get / update / remove 三类操作都要用它来拼 where 条件。

3.2 三层封装

链路是自下而上的：SqlSource（SQL 从哪来）→ MappedStatement（注册进配置）→ FactoryBean（何时注册）。

3.2.1 CrudSqlSource 类定义

该类用于解析指定的类信息，并生成 SqlSource 对象，如：

public SqlSource listByParamSqlSource() {
    SqlNode sqlNode = listSqlNode();
    return new DynamicSqlSource(configuration, new MixedSqlNode(Arrays.asList(sqlNode, applyWhere)));
}
private SqlNode listSqlNode() {
    SQL sql = new SQL();
    for (Field field : fields) {
        sql.SELECT(ModelUtil.getColumn(field));
    }
    sql.FROM(table);
    return new StaticTextSqlNode(sql.toString());
}
  • SQL 是 MyBatis 自带的 builder，SELECT/FROM/WHERE 会拼成合法语句，不必手写字符串拼接。
  • 列名来自 ModelUtil.getColumn(field)：优先取 @Column 的值，没有注解时回落到字段名转换。
  • 用 DynamicSqlSource 而不是 RawSqlSource，是因为要挂 applyWhere 这个动态节点——按参数是否为空决定是否追加条件。

3.2.2 CrudMappedStatement 类定义

该类用于为指定的 mapper 类生成自定义 MappedStatement 并添加到 MyBatis 配置中，如：

public void addListByParamStatement() {
    SqlSource listByParam = crudSqlSource.listByParamSqlSource();
    MappedStatement.Builder mappedStatementBuilder = new MappedStatement.Builder(
            configuration,
            String.format("%s.listByParam", mapperInterface.getTypeName()),
            listByParam,
            SqlCommandType.SELECT
    );
    mappedStatementBuilder.resultMaps(resultMaps);
    configuration.addMappedStatement(mappedStatementBuilder.build());
}

这里最关键的是 id 的拼法：接口全限定名.方法名。它与 MapperProxy 运行时生成的 key 完全一致，所以接口里一个没有任何 XML、没有任何 @Select 的方法，调用时也能命中这条 MappedStatement。resultMaps 决定结果集往哪个类型映射，必须提前按实体构造好。

3.2.3 CrudMapperFactoryBean 类定义

该类为本次工作的核心，它的作用是对扫描到的 mapper 对象的处理，结合 MyBatis 自带的扫描注解 @MapperScan 完美实现对 mapper 对象添加自定义方法。

CrudMapperFactoryBean.java：

public class CrudMapperFactoryBean<T> extends MapperFactoryBean<T> {
    public CrudMapperFactoryBean() {
        super();
    }

    public CrudMapperFactoryBean(Class<T> mapperInterface) {
        super(mapperInterface);
    }

    @Override
    protected void checkDaoConfig() {
        super.checkDaoConfig();
        // 添加Crud方法
        CrudMappedStatement crudMappedStatement = new CrudMappedStatement.Builder(super.getSqlSession().getConfiguration(), super.getMapperInterface()).build();
        crudMappedStatement.addCrudStatement();
    }
}

MybatisConfig.java：

@AutoConfiguration
@MapperScan(basePackages = { "${mybatis.crud-mapper-package}" }, factoryBean = CrudMapperFactoryBean.class)
public class MybatisConfig {
    //...
}

选择 checkDaoConfig() 作为切入点是有讲究的：它在 FactoryBean 完成属性注入后被调用，此时 SqlSession 与 Configuration 都已就绪，且只执行一次。注册动作放在这里，等于搭了官方生命周期便车。

两个细节：

  • ${mybatis.crud-mapper-package} 必须有值，否则启动阶段就报占位符解析失败。稳妥写法是带默认值：${mybatis.crud-mapper-package:com.strr.mapper}。
  • addCrudStatement() 内部应先判断 configuration.hasStatement(id)。同一接口被多个 @MapperScan 覆盖、或单测里重复构建上下文时，重复注册会抛 MappedStatement ... already exists value。

3.3 基类方法封装

3.3.1 CrudMapper 类

该类与生成的 MyBatis 方法（MappedStatement）一一对应：

public interface CrudMapper<T, ID extends Serializable> {
    int countByParam(T param);
    List<T> listByParam(T param);
    int save(T entity);
    int update(T entity);
    int remove(ID id);
    T get(ID id);
}

业务 mapper 只需 extends CrudMapper<Xxx, Long>，六个方法即自动可用。方法名与 addListByParamStatement() 里注册的 id 后缀严格对应，改名必须两边同步。

3.3.2 CrudService 类和 CrudServiceImpl 类

CrudService.java：

public interface CrudService<T, ID extends Serializable> {
    int save(T entity);
    int update(T entity);
    int remove(ID id);
    T get(ID id);
}

CrudServiceImpl.java：

public abstract class CrudServiceImpl<T, ID extends Serializable> implements CrudService<T, ID> {
    protected abstract CrudMapper<T, ID> getMapper();

    @Override
    public int save(T entity) {
        return getMapper().save(entity);
    }

    @Override
    public int update(T entity) {
        return getMapper().update(entity);
    }

    @Override
    public int remove(ID id) {
        return getMapper().remove(id);
    }

    @Override
    public T get(ID id) {
        return getMapper().get(id);
    }
}

用抽象方法 getMapper() 而不是字段注入，是为了绕开泛型父类的注入歧义：@Autowired CrudMapper<T, ID> 在类型擦除后无法确定具体接口，子类实现 getMapper() 返回自己的 mapper 即可。

3.3.3 CrudController 类

public abstract class CrudController<T, ID extends Serializable> {
    protected abstract CrudService<T, ID> getService();

    @PostMapping("/save")
    public Result<T> save(T entity) {
        int r = getService().save(entity);
        if (r > 0) {
            return Result.ok(entity);
        }
        return Result.error();
    }

    @PutMapping("/update")
    public Result<T> update(T entity) {
        int r = getService().update(entity);
        if (r > 0) {
            return Result.ok(entity);
        }
        return Result.error();
    }

    @DeleteMapping("/remove")
    public Result<Void> remove(ID id) {
        int r = getService().remove(id);
        if (r > 0) {
            return Result.ok();
        }
        return Result.error();
    }

    @GetMapping("/get")
    public Result<T> get(ID id) {
        T t = getService().get(id);
        if (t != null) {
            return Result.ok(t);
        }
        return Result.error();
    }
}

三层各有一个抽象 getXxx()，构成 Controller → Service → Mapper 的模板继承链。落地时还要补两件事：入参校验（@Valid + 字段注解，基类拿不到子类的校验规则），以及事务边界——save / update / remove 应在 Service 层加 @Transactional，基类没写是留给子类的。

r > 0 这个判断值得留意：Connector/J 默认会带上 CLIENT_FOUND_ROWS，update 即便字段值没有实际变化也会返回匹配行数；一旦改用 useAffectedRows=true，「更新成功但值为 0 行」就会被这里误判成失败。

4 分页功能

4.1 分页类定义

Pageable.java：

public class Pageable {
    private Integer page = 1;
    private Integer size = 10;

    public Integer getPage() {
        return page;
    }

    public void setPage(Integer page) {
        this.page = page;
    }

    public Integer getSize() {
        return size;
    }

    public void setSize(Integer size) {
        this.size = size;
    }
}

Page.java：

public class Page<T> extends Pageable {
    private Integer total;
    private List<T> content;

    public Page(Integer page, Integer size) {
        super.setPage(page);
        super.setSize(size);
    }

    public Integer getTotal() {
        return total;
    }

    public void setTotal(Integer total) {
        this.total = total;
    }

    public List<T> getContent() {
        return content;
    }

    public void setContent(List<T> content) {
        this.content = content;
    }

    public static <T> Page<T> of(Pageable pageable) {
        return new Page<>(pageable.getPage(), pageable.getSize());
    }
}

Page 继承 Pageable 而不是并列，是为了让分页插件能从入参拿参数、从返回值放总数，一个类型贯穿两端。

4.2 分页插件定义

该插件通过拦截 Executor 的 query 方法，如果 mapper 方法带有 Pageable 参数，则执行分页查询：

@Component
@Intercepts({@Signature(
        type = Executor.class,
        method = "query",
        args = {MappedStatement.class, Object.class, RowBounds.class, ResultHandler.class}
), @Signature(
        type = Executor.class,
        method = "query",
        args = {MappedStatement.class, Object.class, RowBounds.class, ResultHandler.class, CacheKey.class, BoundSql.class}
)})
public class PageInterceptor implements Interceptor {
    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        //...

        // 分页参数
        Optional<Pageable> optional = ParameterUtils.getPageable(parameter);
        if (optional.isEmpty()) {
            return invocation.proceed();
        }
        Pageable pageable = optional.get();

        Page<Object> page = Page.of(pageable);
        MappedStatement countMs = buildCountMappedStatement(ms);
        Integer count = executeCount(executor, countMs, parameter, boundSql, rowBounds, resultHandler);
        page.setTotal(count);

        if (count > 0) {
            List<Object> list = pageQuery(executor, ms, parameter, rowBounds, resultHandler, boundSql, cacheKey, pageable);
            page.setContent(list);
        } else {
            page.setContent(Collections.emptyList());
        }

        return Collections.singletonList(page);
    }
}

三个设计点值得单独说：

  • 为什么要两个 @Signature：Executor.query 有两个重载，第一个是入口（由 BaseExecutor 内部再调第二个），第二个带 CacheKey 与 BoundSql、是真正走缓存与 JDBC 的那一层。只拦其中一个，另一条调用路径就会漏掉插件。
  • optional.isEmpty() 直接放行：没有 Pageable 参数的查询完全不受影响，这让插件是「增强」而不是「强制」。
  • count > 0 才查明细：总数为 0 时省掉一次数据库往返。

4.3 为什么返回 singletonList(page)

mapper 方法声明的返回类型是 Page<T>——不是 List。MyBatis 会把它当作「单条结果」处理，即内部调用 selectOne：Executor.query 必须返回 List，而 selectOne 要求这个 List 恰好只有一个元素。所以插件把 Page 包装成单元素 List 返回，selectOne 取出这个 Page 交给方法签名，于是「总数 + 当页内容」一次性回到了调用方。

这也是为什么不能直接 return page：拦截器改变的是 query 的返回契约，返回非 List 会在上层强转时抛 ClassCastException。

4.4 使用

public interface CrudMapper<T, ID extends Serializable> {
    //...

    // 分页
    Page<T> page(@Param("param") T param, @Param("page") Pageable pageable);
}

@Param 让多参数进入 Map 形式的参数对象，ParameterUtils.getPageable(parameter) 正是从这个 Map 里按类型搜出 Pageable。

5 结果集处理

5.1 从重写 handler 到只改一个方法

MyBatis 基础的 CRUD 方法封装完成之后，我发现还有一点瑕疵：我只生成了方法，但对结果集的处理并不会按照我所定义的注解来映射字段。

于是我打算再定义一个 ResultSetHandler 的插件来处理结果集，但后来发现这并不是一个明智的方法——在 ResultSetHandler 中，实际对结果集字段映射的代码只占据整个代码的一小部分，而我需要对整个 ResultSetHandler 重写才能实现这个功能。

在多次阅读代码后发现，字段映射的核心代码在于 MetaObject.findProperty，该方法往上最终调用 Reflector.findPropertyName。于是只需自定义 Reflector 的处理逻辑，并将 ReflectorFactory 添加到 MyBatis 配置中即可。

这段取舍比结论更有价值：扩展点选得越深越窄，代价越小。重写 ResultSetHandler 要复制上百行并从此与版本升级脱钩；替换 Reflector 只多了一个 findPropertyName 的查表动作。

5.2 AnnotationReflector

AnnotationReflector.java：

public class AnnotationReflector extends Reflector {
    private final Map<String, String> annotationPropertyMap = new HashMap<>();

    public AnnotationReflector(Class<?> clazz) {
        super(clazz);
        this.addAnnotationField(clazz);
    }

    private void addAnnotationField(Class<?> clazz) {
        Field[] fields = clazz.getDeclaredFields();
        for (Field field : fields) {
            // 下划线转驼峰
            String column = ModelUtil.getColumn(field).map(Column::value).map(value -> value.replace("_", ""))
                    .orElse(field.getName());
            annotationPropertyMap.put(column.toUpperCase(Locale.ENGLISH), field.getName());
        }
    }

    @Override
    public String findPropertyName(String name) {
        return Optional.ofNullable(annotationPropertyMap.get(name.toUpperCase(Locale.ENGLISH)))
                .orElse(super.findPropertyName(name));
    }
}

匹配是靠「双方归一化」达成的：建表时把注解列名去掉下划线再转大写，查表时把传入的列名也转大写。MyBatis 在 mapUnderscoreToCamelCase = true 时会先对列名 replace("_", "") 再调 findPropertyName，因此 test_key（列）与 @Column("test_key") 最终都能落在 TESTKEY 这个键上。

由此得出一条硬约束：这两件事必须成对出现。如果只设了自定义 ReflectorFactory 而没开 mapUnderscoreToCamelCase，传入的列名仍带下划线，查表必然落空，最后走 super.findPropertyName 静默返回 null，表现就是字段全是 null 但没有任何报错。

另外注意 getDeclaredFields() 只看当前类，不含父类字段——实体若把公共字段抽到基类，需要沿继承链向上收集。

5.3 AnnotationReflectorFactory

AnnotationReflectorFactory.java：

public class AnnotationReflectorFactory implements ReflectorFactory {
    private boolean classCacheEnabled = true;
    private final ConcurrentMap<Class<?>, Reflector> reflectorMap = new ConcurrentHashMap<>();

    @Override
    public boolean isClassCacheEnabled() {
        return this.classCacheEnabled;
    }

    @Override
    public void setClassCacheEnabled(boolean classCacheEnabled) {
        this.classCacheEnabled = classCacheEnabled;
    }

    @Override
    public Reflector findForClass(Class<?> type) {
        return this.classCacheEnabled ? MapUtil.computeIfAbsent(this.reflectorMap, type, AnnotationReflector::new) : new AnnotationReflector(type);
    }
}

Reflector 的构造需要反射遍历类结构，代价不低，所以缓存必须开着；关闭缓存只适合排查问题，不能上生产。

5.4 装配

MybatisConfig.java：

@AutoConfiguration
@MapperScan(basePackages = { "${mybatis.crud-mapper-package}" }, factoryBean = CrudMapperFactoryBean.class)
public class MybatisConfig {
    @Bean
    public ConfigurationCustomizer configurationCustomizer() {
        return config -> {
            config.setReflectorFactory(new AnnotationReflectorFactory());
            // 开启下划线转驼峰
            config.setMapUnderscoreToCamelCase(true);
            // 分页插件
            config.addInterceptor(new PageInterceptor());
        };
    }
}

ConfigurationCustomizer 是 starter 留出的官方口子，比自建 SqlSessionFactory 温和得多，也不会和自动配置打架。

注意 @Component 标注在 PageInterceptor 上又在这里 new 了一次：如果同时被 MyBatis 的自动收集（Interceptor[] 注入）命中，插件会执行两遍，count 查询也就发了两次。二选一即可。

6 落地检查清单

  • 注册幂等：addCrudStatement() 前判断 configuration.hasStatement(id)，避免重复构建上下文时抛异常。
  • @MapperScan 会关掉自动扫描：显式声明后，只有 basePackages 覆盖到的接口成为 Bean。
  • 占位符给默认值：${mybatis.crud-mapper-package:具体包名}。
  • 驼峰开关成对：自定义 Reflector 依赖 mapUnderscoreToCamelCase = true。
  • 插件只装一次：@Component 与 addInterceptor 不要重复。
  • 事务与校验：基类未提供 @Transactional 与入参校验，需要在子类补齐。
  • 影响行数语义：useAffectedRows 决定 r > 0 判断是否可靠。

7 小结

  • 整个封装没有改动 MyBatis 的任何行为，只做了三件事：往 Configuration 注册 MappedStatement、把接口方法名对齐 statement id、换掉 ReflectorFactory。
  • 侵入最小的扩展点往往是最有效的扩展点，checkDaoConfig 与 Reflector.findPropertyName 都是这个原则的产物。
  • 分页插件利用「单元素 List + selectOne」的契约，让返回类型可以是 Page<T> 而非 List<T>。
