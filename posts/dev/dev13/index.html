ShardingSphere 分库分表

strr0 2024-07-20

1 概述

Apache ShardingSphere 是一款分布式 SQL 事务和查询引擎，可通过数据分片、弹性伸缩、加密等能力对任意数据库进行增强。

单表数据量增长到一定规模后，索引层级变深、DDL 与备份代价飙升，此时才需要分片。分片要付出三类长期成本：跨库查询受限、分布式事务与主键、扩容迁移。选择 ShardingSphere 的理由是它把这些复杂度收敛到配置里，应用仍像操作一张逻辑表那样写 SQL。

它有两种主流接入形态：

  • JDBC（客户端）：本文方式，零额外部署，性能损耗小，但仅限 Java；
  • Proxy（代理）：伪装成 MySQL 服务，任何语言都能连，代价是多一套需要运维的组件。

2 快速上手

2.1 引入依赖

创建 Maven 项目，并引入依赖：

<dependency>
    <groupId>org.apache.shardingsphere</groupId>
    <artifactId>shardingsphere-jdbc-core</artifactId>
    <version>5.4.1</version>
</dependency>

2.2 构建数据源

5.x 版本把配置拆成五个要素，最终合成一个标准 DataSource：

String databaseName = "db"; // 指定逻辑 Database 名称
ModeConfiguration modeConfig = getModeConfig(); // 构建运行模式
Map<String, DataSource> dataSourceMap = getDataSourceMap(); // 构建真实数据源
Collection<RuleConfiguration> ruleConfigs = getRuleConfigs(); // 构建具体规则
Properties props = getProps(); // 构建属性配置
DataSource dataSource = ShardingSphereDataSourceFactory.createDataSource(databaseName, modeConfig, dataSourceMap, ruleConfigs, props);

关键点：返回的仍是 javax.sql.DataSource，因此可以和 MyBatis、JPA、事务管理器直接对接，业务代码无需感知分片存在。

2.3 使用数据源

try {
    DataSource dataSource = MyShardingSphereFactory.createDataSource();
    try (Connection conn = dataSource.getConnection(); Statement stmt = conn.createStatement()) {
        try (ResultSet rs = stmt.executeQuery("select id, test_key, value from my_demo where id = 11")) {
            while (rs.next()) {
                System.out.printf("id: %d, test_key: %s, value: %s\n", rs.getInt(1), rs.getString(2), rs.getString(3));
            }
        }
    }
} catch (SQLException e) {
    e.printStackTrace();
}

SQL 里写的是逻辑表 my_demo，路由到哪个真实表由规则决定。

3 五项核心配置

3.1 模式配置

运行模式决定元数据与状态存到哪里。

单机模式：

private ModeConfiguration createModeConfiguration() {
    return new ModeConfiguration("Standalone", new StandalonePersistRepositoryConfiguration("JDBC", new Properties()));
}

集群模式：

private ModeConfiguration createModeConfiguration() {
    return new ModeConfiguration("Cluster", new ClusterPersistRepositoryConfiguration("ZooKeeper", "governance-sharding-db", "localhost:2181", new Properties()));
}
  • Standalone：元数据落在本地，实例之间互不感知，开发与单实例部署够用。
  • Cluster：元数据集中存于 ZooKeeper（或 etcd、Consul），多实例共享配置并支持治理，生产环境必须用它，否则各节点配置漂移。

3.2 数据源配置

private Map<String, DataSource> createDataSources() {
    Map<String, DataSource> dataSourceMap = new HashMap<>();
    // 配置第 1 个数据源
    HikariDataSource dataSource1 = new HikariDataSource();
    dataSource1.setDriverClassName("com.mysql.jdbc.Driver");
    dataSource1.setJdbcUrl("jdbc:mysql://localhost:3306/ds1");
    dataSource1.setUsername("root");
    dataSource1.setPassword("");
    dataSourceMap.put("ds1", dataSource1);
    
    // 配置第 2 个数据源
    HikariDataSource dataSource2 = new HikariDataSource();
    dataSource2.setDriverClassName("com.mysql.jdbc.Driver");
    dataSource2.setJdbcUrl("jdbc:mysql://localhost:3306/ds2");
    dataSource2.setUsername("root");
    dataSource2.setPassword("");
    dataSourceMap.put("ds2", dataSource2);
    return dataSourceMap;
}

Map 的 key（ds1、ds2）就是后续 actualDataNodes 里引用的数据源名，必须严格对应。

3.3 表规则配置

配置表的逻辑名和实际节点等：

private ShardingTableRuleConfiguration getOrderTableRuleConfiguration() {
    ShardingTableRuleConfiguration config = new ShardingTableRuleConfiguration("t_order", "demo_ds_${0..1}.t_order_${[0, 1]}");
    config.setKeyGenerateStrategy(new KeyGenerateStrategyConfiguration("order_id", "snowflake"));
    config.setAuditStrategy(new ShardingAuditStrategyConfiguration(Collections.singleton("sharding_key_required_auditor"), true));
    return config;
}

actualDataNodes 的格式是「数据源名.表名」，用 Groovy 行表达式枚举真实节点：

片段含义展开结果
demo_ds_${0..1}区间，连续编号demo_ds0、demo_ds1
t_order_${[0, 1]}枚举，离散编号t_order_0、t_order_1

两者笛卡尔积即 4 个真实节点。如果表名没有规律也可以通过枚举的方式：

ShardingTableRuleConfiguration config = new ShardingTableRuleConfiguration("my_demo", "ds.test_demo,ds.test_demo_copy1,ds.test_demo_copy2,ds.test_demo_copy3,ds.test_demo_copy4,ds.test_demo_copy5");

另外两项：

  • keyGenerateStrategy：分片后不能再用单库自增主键，snowflake 生成全局唯一 ID。生产环境需要显式指定 worker-id，否则多实例可能算出重复 ID。
  • auditStrategy：校验 SQL 是否携带分片键。第二个参数是 softFail，为 true 时缺少分片键只告警并退化为全路由（能查但慢），为 false 时直接抛异常（快但可能中断业务）。

3.4 分片策略配置

3.4.1 配置策略

指定库名或表名分片策略（user_id 为分片字段，inline 为分片算法名称）：

config.setDefaultDatabaseShardingStrategy(new StandardShardingStrategyConfiguration("user_id", "inline"));

库和表的策略是分开的：DefaultDatabaseShardingStrategy 决定进哪个库，DefaultTableShardingStrategy 决定进哪张表，也可以按表单独覆盖。

3.4.2 配置算法

分片算法逻辑（定义 inline 算法，algorithm-expression 为表达式类型）：

Properties props = new Properties();
props.setProperty("algorithm-expression", "demo_ds_${user_id % 2}");
config.getShardingAlgorithms().put("inline", new AlgorithmConfiguration("INLINE", props));

INLINE 是取模分片最省事的写法，但它是「字面路由」——只能处理等值条件，between、in 等范围查询无法用表达式推导目标节点。需要范围支持时改用 HASH_MOD、RANGE 等内置算法。

3.4.3 配置自定义算法

自定义算法：

/**
 * 自定义分片算法
 */
public class MyTableShardingAlgorithm implements StandardShardingAlgorithm<Integer> {
    @Override
    public String doSharding(Collection<String> collection, PreciseShardingValue<Integer> preciseShardingValue) {
        Integer value = preciseShardingValue.getValue();
        if (value > 50) {
            return "test_demo_copy5";
        }
        if (value > 40) {
            return "test_demo_copy4";
        }
        if (value > 30) {
            return "test_demo_copy3";
        }
        if (value > 20) {
            return "test_demo_copy2";
        }
        if (value > 10) {
            return "test_demo_copy1";
        }
        return "test_demo";
    }

    @Override
    public Collection<String> doSharding(Collection<String> collection, RangeShardingValue<Integer> rangeShardingValue) {
        return null;
    }
}

两个 doSharding 重载分别对应等值与范围查询。这里范围方法返回 null 表示「不支持范围分片」，一旦线上出现 between 查询就会路由失败；正确做法是从入参 collection（候选真实节点）里挑出落在范围内的节点返回，或明确抛异常让调用方感知。

按值区间划分节点还有另一个问题：区间边界写死在代码里，数据分布变化（比如 50 以下的数据远多于以上）时无法自动均衡。

添加算法到配置中：

Properties props = new Properties();
props.setProperty("algorithmClassName", "com.strr.config.MyTableShardingAlgorithm");
props.setProperty("strategy", "standard");
config.getShardingAlgorithms().put("my-table-sharding-algorithm", new AlgorithmConfiguration("CLASS_BASED", props));

CLASS_BASED 是包装类型，strategy 指定它实现的接口形态（standard / complex / hint），配好后即可在策略里按名称引用。

4 注意事项

  • 分片键必须进 WHERE：不带分片键的查询会广播到所有节点再归并，性能断崖式下降。审计策略建议最终设为 softFail = false，把问题暴露在测试期。
  • order by + 分页跨库代价高：深分页需要各节点都取到 offset + limit 条再归并，应改用游标分页（where id > ?）。
  • 跨库事务：默认是 best-efforts 型 XA，无法保证强一致；涉及多库写操作时应引入业务补偿或改用 BASE 事务模型。
  • JOIN 与绑定表：分片键一致、分片算法相同的表要配置成绑定表（binding tables），否则会做笛卡尔积路由。
  • 主键不能依赖数据库自增：雪花算法需保证 worker-id / data-source-id 全局唯一。
  • 驱动类名：com.mysql.jdbc.Driver 在 Connector/J 8.x 已废弃，建议改为 com.mysql.cj.jdbc.Driver，并按需加时区参数。
  • 扩容是难点：取模分片扩容意味着几乎所有数据重新分布，规划时应预留成倍增长的节点数，或采用区间 / 一致性哈希方案。

5 小结

  • 配置分五层：模式（元数据放哪）、数据源（真实库）、表规则（逻辑表 ↔ 真实节点）、策略（按哪个字段）、算法（怎么算）。
  • INLINE 适合取模等值分片，范围查询要靠自定义算法或内置 RANGE。
  • 分片带来的跨库聚合、分页、事务和扩容问题不会消失，只是从代码转移到了配置，评估收益时要一并计入。
