Spring Batch 批处理框架

strr0 2024-03-14

1 概述

Spring Batch 是一个轻量级的、完善的批处理框架，旨在帮助企业建立健壮、高效的批处理应用。Spring Batch 的核心为一个作业启动器和一个作业主体（Job），一个作业主体会包含若干个步骤（Step），一个步骤可以是 Chunk 类型或 Tasklet 类型，作业启动器用于执行定义的作业。

值得用它而不是写 for 循环的原因有四点：可重启（跑完一半失败不必从头再来）、可追溯（每次运行的状态都落在元数据表里）、分块事务（按 chunk 提交，而不是一整个大事务或每条一提交）、可分区并行。

代价是必须先准备元数据表。Spring Batch 依赖 BATCH_JOB_INSTANCE、BATCH_JOB_EXECUTION、BATCH_JOB_EXECUTION_CONTEXT、BATCH_STEP_EXECUTION 等表记录运行状态，官方按数据库提供了 schema-mysql.sql、schema-postgresql.sql 等脚本。Spring Boot 默认 spring.batch.jdbc.initialize-schema=never，需要手工建表或临时设为 always 让框架初始化；同时 spring.batch.job.enabled=false 可避免应用启动时自动跑一遍所有 Job——这个默认值在「部署即执行」的场景下很容易踩坑。

2 核心概念

2.1 Job 配置

可以定义 JobListener 在 Job 执行期间监听 Job 的执行情况：

public interface JobExecutionListener {
    void beforeJob(JobExecution jobExecution);
    void afterJob(JobExecution jobExecution);
}

Job 配置示例如下：

public Job footballJob(JobRepository jobRepository) {
    return new JobBuilder("footballJob", jobRepository)
                     .listener(sampleListener())
                     //...
                     .build();
}

afterJob 拿到的是 JobExecution，可以从里面读 getStatus()、getExitStatus()、各 Step 的读写计数，告警与运行报表通常就挂在这里。

2.2 Step 配置

可以定义 StepListener 在 Step 执行期间监听 Step 的执行情况：

public interface StepExecutionListener extends StepListener {
    default void beforeStep(StepExecution stepExecution) {
    }
    default ExitStatus afterStep(StepExecution stepExecution) {
        return null;
    }
}

Step 配置示例如下：

// chunk 类型
public Step sampleStep(JobRepository jobRepository, 
		PlatformTransactionManager transactionManager) { 
	return new StepBuilder("sampleStep", jobRepository)
				.<String, String>chunk(10, transactionManager) 
				.reader(itemReader())
				.writer(itemWriter())
				.build();
}

// tasklet 类型
public Step step(JobRepository jobRepository, PlatformTransactionManager transactionManager) {
    return new StepBuilder("step", jobRepository)
    			.tasklet(myTasklet(), transactionManager)
    			.build();
}

两种类型的分工很明确：

类型执行模型事务边界适用
Chunkread → process → write 循环，攒满 chunkSize 触发一次写与提交每 chunk 一次事务大批量数据处理
Tasklet单个方法执行一次整个 step 一次事务建目录、清理临时文件、发通知、判断分支

chunk(10, transactionManager) 的含义是：读 10 条处理 10 条后一次性写出并提交。这个数字要权衡——太小则 IO 与提交开销占主导，太大则失败回滚范围和内存占用随之上升。

2.3 并行 Step 配置

public Job job(JobRepository jobRepository) {
    return new JobBuilder("job", jobRepository)
        .start(splitFlow())
        .next(step4())
        .build()        //builds FlowJobBuilder instance
        .build();       //builds Job instance
}

// flow1 flow2 并行
public Flow splitFlow() {
    return new FlowBuilder<SimpleFlow>("splitFlow")
        .split(taskExecutor())
        .add(flow1(), flow2())
        .build();
}

public Flow flow1() {
    return new FlowBuilder<SimpleFlow>("flow1")
        .start(step1())
        .next(step2())
        .build();
}

public Flow flow2() {
    return new FlowBuilder<SimpleFlow>("flow2")
        .start(step3())
        .build();
}

public TaskExecutor taskExecutor() {
    return new SimpleAsyncTaskExecutor("spring_batch");
}

结构是：flow1（step1 → step2）与 flow2（step3）并行执行，两条流都结束后再走 step4。注意 .build() 调了两次——第一次由 FlowJobBuilder 产出 Job 对象，这是 Flow 语法的固定收尾。

SimpleAsyncTaskExecutor 并不复用线程，仅适合演示；生产应换成有界的线程池，并留意线程数与数据库连接池大小要匹配，否则并行度提升只会把连接池打空。

并行 Step 与下面第 3 节的**分区（Partitioning）**是两件事：并行 Step 处理的是互不相同的业务步骤，分区则是把一个 Step 的数据切成多份并行消化。

2.4 作业执行

@SpringBootTest
public class JobLauncherTest {

    @Autowired
    JobLauncher jobLauncher;

    @Autowired
    Job job;

    @Test
    public void test() throws Exception {
        jobLauncher.run(job, new JobParameters());
    }
}

JobParameters 是 Spring Batch 识别「一次运行」的唯一依据，同一个 Job 用完全相同的参数第二次运行会抛 JobInstanceAlreadyCompleteException。new JobParameters() 是空参数，所以这段代码在原样重跑时会失败。解决办法是把时间戳或日期作为参数传入：

JobParameters params = new JobParametersBuilder()
        .addLong("time", System.currentTimeMillis())
        .toJobParameters();

定时调度天然适合用「批次日期」作为参数，这样同一天重复触发会被拒绝，跨天则正常开新实例。

3 实战：数据清洗作业

目标：从 PostgreSQL 读一张表，把列名由下划线转成驼峰，再写入 MySQL，并用分区并行加速。

3.1 项目配置

引入依赖：

<dependency>
    <groupId>org.springframework.boot</groupId>

    <version>3.1.5</version>
    <exclusions>
        <exclusion>
            <groupId>ch.qos.logback</groupId>
            <artifactId>logback-classic</artifactId>
        </exclusion>
    </exclusions>
</dependency>

<dependency>
    <groupId>com.baomidou</groupId>
    <artifactId>dynamic-datasource-spring-boot3-starter</artifactId>
    <version>4.2.0</version>
</dependency>

<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
    <version>8.0.31</version>
</dependency>

<dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <version>42.6.0</version>
</dependency>

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>

    <scope>test</scope>
</dependency>

排除 logback-classic 是为了换成项目统一的日志实现，避免两套 binding 冲突。

application 配置：

spring:
  datasource:
    type: com.zaxxer.hikari.HikariDataSource
    dynamic:
      primary: postgres
      strict: true
      datasource:
        mysql:
          type: ${spring.datasource.type}
          driver-class-name: com.mysql.cj.jdbc.Driver
          url: jdbc:mysql://localhost:3306/testdb
          username: root
          password: password
        postgres:
          type: ${spring.datasource.type}
          driver-class-name: org.postgresql.Driver
          url: jdbc:postgresql://localhost:5432/postgres
          username: postgres
          password: password

strict: true 表示找不到指定数据源就直接报错，而不是悄悄回退到 primary。批处理跨库写入时这种「宁错不默」的取值更安全——回退意味着数据被写进了另一个库。

3.2 定义分区器

用于将数据分成若干分区并行处理：

public class JdbcRownumPartitioner implements DataPartitioner {
    private Long total = 0L;  // 数据总数
    private Long pageSize = 5000L;  // 分页大小

    public void setTotal(Long total) {
        this.total = total;
    }

    public void setPageSize(Long pageSize) {
        this.pageSize = pageSize;
    }

    @Override
    public Map<String, ExecutionContext> partition(int gridSize) {
        Map<String, ExecutionContext> contextMap = new HashMap<>();
        int idx = 0;
        for (int row = 0; row < total; row += pageSize) {
            ExecutionContext context = new ExecutionContext();
            context.put("startRow", row);
            context.put("pageSize", pageSize);
            contextMap.put(String.valueOf(idx++), context);
        }
        return contextMap;
    }
}

partition 返回的 Map 是「分区名 → 该分区的 ExecutionContext」，框架会把每个 context 下发给对应的分区 Step 副本，读端再从中取 startRow 与 pageSize——这就是分区之间传递工作单元的方式。

gridSize（并行线程数）在这里没有参与切分，分区数量完全由 total / pageSize 决定。数据量大时这会一次创建成百上千个分区副本，实际使用应让 pageSize 随 gridSize 调整，或者按 ceil(total / gridSize) 分块。

3.3 定义读取器

从指定的数据源按一定规则读取数据：

public class JdbcPartitionReader extends AbstractItemCountingItemStreamItemReader<Map<String, Object>> {
    //...

    @Override
    protected Map<String, Object> doRead() throws Exception {
        synchronized (this.lock) {
            if (results == null || results.isEmpty()) {
                return null;
            }
            return results.remove(results.size() - 1);
        }
    }

    @Override
    protected void doOpen() throws Exception {
        fetchData();
    }

    private void fetchData() {
        if (dataSource == null || script == null || executionContext == null) {
            return;
        }
        JdbcTemplate jdbcTemplate = new JdbcTemplate(dataSource);
        int startRow = executionContext.getInt("startRow");
        long pageSize = executionContext.getLong("pageSize");
        results = jdbcTemplate.queryForList(String.format("%s limit %d offset %d", script, pageSize, startRow));
    }

    //...
}

实现细节带来的四个后果：

  • 继承 AbstractItemCountingItemStreamItemReader 自动获得计数与 restart 能力，代价是它要求 reader 是有状态的，doOpen 时才能拿到 context。
  • doOpen 一次性把整个分区的数据装进 results：pageSize 设 5000 意味着每个分区线程持有 5000 行的 Map，并行度高时这是主要的内存压力来源。改成游标（setFetchSize + 流式 ResultSet）或减小 pageSize 更稳。
  • remove(size() - 1) 是倒序消费：最后一条最先被读出。如果下游依赖原始顺序（例如按时间增量），应改为 remove(0)（或直接用迭代器），并注意 queryForList 返回的列表要可变。
  • limit ? offset ? 用字符串拼接：数值参数没有注入风险，但这是 MySQL / PostgreSQL 方言，SQL Server、Oracle 需要改写；大 offset 分页在源库上会随深度线性变慢，按主键区间切分（where id between ? and ?）比 offset 更划算。

分区并行处理有可能会遇到线程安全问题，可通过使用 ThreadLocal 等方式来避免读取脏数据。

这个问题在下一节（3.6）会更具体——根因是分区 Step 复用了同一个 reader 实例。

3.4 定义数据处理器

字段名称下划线转驼峰：

public class CamelCaseProcessor implements DataItemProcessor<Map<String, Object>, Map<String, Object>> {
    @Override
    public Map<String, Object> process(Map<String, Object> item) throws Exception {
        if (item == null || item.isEmpty()) {
            return null;
        }
        Map<String, Object> out = new HashMap<>();
        for (Map.Entry<String, Object> entry : item.entrySet()) {
            out.put(StringUtils.toCamelCase(entry.getKey()), entry.getValue());
        }
        return out;
    }
}

这一步不只是「顺手改个命名」。PostgreSQL 会把未加引号的标识符折叠为小写，queryForList 返回的 key 因此是 test_key；而写出器的 SQL 用的是命名参数 :testKey。处理器返回的 Map 的 key 必须与命名参数逐字对应，驼峰转换正是为了让两端对得上。

另外注意：process 返回 null 表示「丢弃该条」，它不会进入 writer 的 chunk，也不计入写条数——这里对空 Map 的处理符合预期，但如果源数据本身允许 null 值列，就不要误返回 null 而丢整行。

3.5 定义数据输出器

按一定规则将数据输出到指定数据源：

public class JdbcBatchWriter implements DataItemWriter<Map<String, Object>> {
    //...

    @Override
    public void write(Chunk<? extends Map<String, Object>> chunk) throws Exception {
        if (dataSource == null || script == null) {
            return;
        }
        List<? extends Map<String, Object>> items = chunk.getItems();
        NamedParameterJdbcTemplate jdbcTemplate = new NamedParameterJdbcTemplate(dataSource);
        for (Map<String, Object> item : items) {
            jdbcTemplate.update(script, item);
        }
    }
}

类名叫 BatchWriter，实现却是逐条 update——一次 chunk 会发出 N 条 SQL。批处理写场景应改用 batchUpdate(script, SqlParameterSource[])，让驱动合并成一次网络往返；同时 new NamedParameterJdbcTemplate(dataSource) 每次写都新建对象，提到字段上复用即可。

还有一点：write 里 dataSource == null 时静默返回，整块数据就这么消失了。写出失败必须抛异常，让 chunk 事务回滚并由框架记录 FAILED，否则「跑成功」的报表毫无意义。

3.6 作业主体配置

@Configuration
public class JobPartitionConfig {
    @Autowired
    private JobRepository jobRepository;
    @Autowired
    private PlatformTransactionManager transactionManager;
    @Autowired
    private DynamicRoutingDataSource dataSource;

    @Bean
    public Job job() {
        return new JobBuilder("testJob", jobRepository)
                .start(createPartStep())
                .build();
    }

    public Step createPartStep() {
        // 读取器
        JdbcPartitionReader reader = new JdbcPartitionReader();
        reader.setDataSource(dataSource.getDataSource("postgres"));
        reader.setScript("select test_key, test_value from test_demo");
        // 处理器
        CamelCaseProcessor processor = new CamelCaseProcessor();
        // 写出器
        JdbcBatchWriter writer = new JdbcBatchWriter();
        writer.setDataSource(dataSource.getDataSource("mysql"));
        writer.setScript("insert into test_demo(test_key, test_value) values(:testKey, :testValue)");
        // 分区器
        JdbcRownumPartitioner partitioner = new JdbcRownumPartitioner();
        partitioner.setTotal(reader.getCount());
        partitioner.setPageSize(10L);
        return new StepBuilder("testPartStep", jobRepository)
                .allowStartIfComplete(true)
                .partitioner("testPart", partitioner)
                .step(createStep(reader, processor, writer))
                .build();
    }

    public Step createStep(ItemReader<Map<String, Object>> reader, ItemProcessor<Map<String, Object>, Map<String, Object>> processor, ItemWriter<Map<String, Object>> writer) {
        return new StepBuilder("testStep", jobRepository)
                .allowStartIfComplete(true)
                .<Map<String, Object>, Map<String, Object>>chunk(10, transactionManager)
                .reader(reader)
                .processor(processor)
                .writer(writer)
                .build();
    }
}

这里有一个必须改的结构问题：reader、writer 是 new 出来的单实例，却被所有分区共用。分区执行时框架会派生多个 StepExecution 并行跑同一个 step 定义，如果 reader 是同一个对象，各线程的 results、游标位置会互相覆盖，表现就是「数据重复或丢失、条数对不上」。这正是 3.3 那句线程安全提示的具体成因。

正确做法是让每个分区拿到自己的 reader 实例——把它声明成 step 作用域或 prototype：

@Bean
@StepScope
public JdbcPartitionReader partitionReader(
        @Value("#{stepExecutionContext[startRow]}") Integer startRow,
        @Value("#{stepExecutionContext[pageSize]}") Long pageSize,
        DynamicRoutingDataSource dataSource) {
    JdbcPartitionReader reader = new JdbcPartitionReader();
    reader.setDataSource(dataSource.getDataSource("postgres"));
    reader.setScript("select test_key, test_value from test_demo");
    return reader;
}

@StepScope（本质是 prototype 加 SpEL 代理）会在每个分区 Step 打开时创建新实例，StepRuntimeData 里的 context 也就是该分区独有的；startRow 与 pageSize 直接从分区 context 注入，不再依赖 setter 赋值。

其余几处细节：

  • partitioner.setTotal(reader.getCount())：此刻 reader 还没 open，getCount() 依赖一次独立的 count(*) 查询；如果它返回 0，所有分区都不会建立，任务会「成功但没搬数据」。
  • partitioner.setPageSize(10L) 覆盖了默认的 5000，与内层 chunk(10, ...) 同值——此时每个分区只有一个 chunk，分区的意义只剩下并行调度，可以按实际数据量重新配比。
  • allowStartIfComplete(true)：允许重跑已完成的 Step。它与 committingInterval、restart 语义叠加后容易让同一批数据被写两遍，配合下面的 insert 语句会产生重复行；要么改用 insert ... on duplicate key update，要么保证 JobParameters 唯一。

DynamicRoutingDataSource 是 baomidou 的动态多数据源框架，用于指定作业读取及输出的数据源。

3.7 作业执行

@SpringBootTest
public class ApplicationTests {
    @Autowired
    private JobLauncher jobLauncher;
    @Autowired
    private Job job;

    @Test
    void loadContext() throws Exception {
        jobLauncher.run(job, new JobParameters());
    }
}

jobLauncher.run 默认同步阻塞，测试里这样最直接。定时任务里如果希望触发后立即返回，可换成 AsyncJobLauncher（配 TaskExecutor），但此时 JobExecution 的状态不能再同步读取，进度要改为查元数据表或走监听器上报。

4 小结

  • 用 Spring Batch 换取四件事：可重启、有运行记录、分块事务、可并行分区；成本是要维护元数据表。
  • Chunk 与 Tasklet 分别对应「海量数据循环」和「一次性动作」，不要混用。
  • JobParameters 决定能否重跑，空参数会让第二次运行直接失败。
  • 分区并行最容易翻车的地方是 reader/writer 实例被多分区共用，必须用 @StepScope 隔离。
  • 写出环节要么真批量（batchUpdate），要么显式失败，静默跳过是最坏的选择。
